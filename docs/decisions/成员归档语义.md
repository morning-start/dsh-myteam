# 决策：成员「归档」的语义（ADR 候选 · 待确认）

> 状态：`proposed`（等用户拍板，未实施）
> 日期：2026-11-24
> 上游：[界面依赖与搭建顺序 §3 G3](../features/界面依赖与搭建顺序.md) · [03-角色能力与工作流](../architecture/03-角色能力与工作流.md) · 设计稿 `design-v2/p-member-archive.html`
> 本文只回答问题「归档到底是干什么的」，**不改代码**。拍板后按 §6 的批次实施。

## 1. 为什么要单独定这件事

现在的实现里，「让一个成员不再接活」只有一条路：`memberRelease`（`member.released`，终态、
不可撤销）。但设计稿 `p-member-archive` 画的是另一件事——**归档**：

> 归档是「先排空、再归档」：名册里保留这条记录，记忆 bank 与证据都还在。
> 与「移除」的区别：移除不留名册记录，归档留，且能回放。

这两句把「归档」和「释放/移除」明确分开了。可代码里**没有归档这个动作**：
`MemberStatus` 只有 `appointed / active / paused / released`，`released` 是终态且不可逆。
如果直接把归档实现成 `released`，就会得到三个错：

1. 名册里那条记录还在（投影里 member 一直在），但**语义上被当成死了**——不能回放、不能复活；
2. 设计稿说的「归档后同名重建成员」失去意义：`released` 之后重建是**另一个 id**，
   和「同名重建、旧 attemptId 写入被拒」那套「同一身份换世代」不是一回事；
3. 记忆 bank 与证据「都还在」这件事没有任何东西守着——现在没人管释放后成员私有记忆去哪。

## 2. 先理清：现在到底有哪些「让成员不再接活」的路

| 概念 | 现实现状 | 可逆 | 名册留痕 | 记忆/证据 |
|---|---|---|---|---|
| **暂停** `paused` | `MemberStatus.paused` + 迁移规则在 `domain/teams/member.ts`，但**没有命令、没有面板写** | 可（`paused → active`） | 留 | 留 |
| **释放** `released` | `releaseMemberCommand` + 面板 `memberRelease`；要求**没有进行中的 Attempt** | 不可（`released` 无出边） | 留（member 记录还在） | 留（但没人管） |
| **归档**（设计稿） | **不存在** | 设计稿：可回放（≠ 恢复？见 §4） | 留 | 留 |
| **移除**（设计稿） | 设计稿说「不留名册记录」；**代码里没有真删除**（事件不可删，只能补一条墓碑） | 不可 | 不留（逻辑上） | ？ |

结论：**暂停缺命令、归档不存在、移除只是概念**。设计稿的一屏（`p-member-archive`）压在
一个不存在的状态上，所以那一屏点不动不是「没接界面」，是**底下没这东西**。

## 3. 三种可选语义（请你选一个）

### 选项 A：归档 = 「退役但可回放」（推荐）

新增 `MemberStatus.archived`，与 `released` 并列但**语义不同**：

- `archived`：不再接新活，但**记录、记忆 bank、证据、历史 Attempt 全部保留**，
  名册里以「已归档」显示并可从归档区回放历史；
- `released`：就是现在的终态，语义是「这个人离开了」，不回放；
- 归档**允许**先有进行中的 Attempt：由用户在归档时二选一（**先暂停** / **等这轮结束**），
  不满足条件就拒绝（与设计稿「先排空、再归档」一致）；
- 归档**要求子成员先处理**（归档或释放），级联要二次确认（与设计稿一致）；
- 「同名重建」= 归档后**新建一个 member**（新 id），但归档记录仍在；
  旧 `attemptId` 的写入按现有 `memberSessionGeneration` 规则被拒——这一条**现在就已经成立**，
  不需要新机制。

代价：`MemberStatus` 加一个值，要动 `MEMBER_TRANSITIONS`、投影、`t39` 的成员状态 chips、
面板 `memberRelease` 之外的第二个写动作 `memberArchive`。约 1 个能力层提交 + 1 个界面提交。

### 选项 B：归档 = 释放 + 额外记录（不新增状态）

不加 `archived`，而是让 `memberRelease` 多带一个 `archive: true` 标记，落
`member.released` 事件时在 payload 里记 `archived: true`。

- 好处：改动最小，不用动状态机；
- 代价：**语义塞进 payload 而不是状态**，投影里这个成员仍然是 `released`，
  以后所有「已释放」的判断都会把归档成员一起算进去（包括「不能有进行中 Attempt」这条
  硬约束——而归档本来允许先暂停）。**这就是把两个不同概念压成一个字段**，正是 00 里
  「每个实体只有一个权威存储」要避免的那种混。

### 选项 C：不做归档，只把 `p-member-archive` 那屏删掉

承认「归档」是过度设计：真正需要的是**暂停**（可逆）+ **释放**（终态），两者已经覆盖
「先排空、再归档」的所有诉求（排空 = 暂停或等结束；归档 = 释放）。

- 好处：不动领域模型，只补 `memberPause` 命令 + 界面，然后把设计稿那一屏标为「不实现」；
- 代价：设计稿里「同名重建、能回放」这条需求丢掉。**如果你认为回放有价值，就不能选 C。**

## 4. 无论选哪个，都要先想清的两个问题

1. **归档能恢复（unarchive）吗？**
   设计稿只写「能回放」，没写「能恢复」。我倾向：**归档可恢复**（`archived → active`），
   因为归档的前提是「记录都还在」——记录都在却不让人回来，等于用一个更麻烦的方式做了释放。
   但恢复要不要重绑会话、`generation` 怎么涨，得定。
2. **移除（真删除）做不做？**
   事件账本 append-only，物理删除等于改历史。我的判断：**不做真删除**；如果确实要「移除」，
   实现成 `archived` + 名册默认过滤掉已归档（视觉上像没了，账本里还在）。这样「移除」是
   一个**视图过滤**，不是一次写。

## 5. 我建议的答案（如果你没有别的偏好）

**选项 A + 归档可恢复 + 移除＝视图过滤**：

- `MemberStatus` 增加 `archived`；迁移表：`active → archived`、`paused → archived`、
  `archived → active`（恢复）、`archived → released`（彻底离开）；`archived` 不能直接接活。
- 归档前置：无进行中 Attempt（或用户显式选「先暂停」→ 先落 `paused` 再归档）；
  子成员必须已归档或已释放，否则报 `CONFLICT` 并列出子成员（对应设计稿的三条影响面）。
- 新增面板写 `memberArchive`（direct + confirm，和 `memberRelease` 同一种确认方式）；
  界面在名册每行「释放」旁边多一个「归档」，走影响面预览 + 输入成员名二次确认（照设计稿）。
- `memberRelease` 语义不变（终态），**不与归档合并**。
- 记忆：归档**不动** bank；释放也**不动**（现在就是不动，只是没人说过）；
  要在文档里写明「记忆随成员一起退役，但数据保留」，避免以后有人以为释放会清记忆。
