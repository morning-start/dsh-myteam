# 决策：团队计划批准（`team.plan.*`）

> 状态：`as-is`（P1–P6 已落地，2026-11-24）
> 日期：2026-11-24
> 关联：`docs/features/实现对齐.md` §2（待你确认）、`design-v2/p-team-new.html`、`design-v2/p-approval.html`

## 1. 问题

设计稿里「从蓝图建团队」的最后一步是：

> 生成团队计划与 5 个成员占位 → 进入「待你确认」→ **批准后才建 5 个会话** →
> 批准后开 Run 1，按模板落第一批任务 → **不批准：不产生会话，也不花钱**

这条流程在代码里**完全没有**：

- `TeamStatus` 只有 `active / archived / disbanded`，没有「草稿」；
- 权限表里有 `plan.approve`（HUMAN_ONLY），但**没有任何实现**（只在权限表与 v1 迁移映射里出现）；
- `createTeamCommand` 是**一步到位**：建团队 + 指定队长 + 落配置，没有「先提案、后批准」；
- `p-approval` 的三类里，这是唯一还画不出来的一类（门禁裁决、全局发布、队长接管都已通）。

所以这一块不是补界面，是补**一整条领域链路**。

## 2. 核心约束（来自设计稿，不能违背）

| 约束 | 出处 |
|---|---|
| 批准前**不建成员会话**、**不开 Run**、**不花钱** | `p-team-new`「会发生什么」 |
| 丢弃「不产生任何会话与花费」 | `p-approval` 计划卡 |
| 「批准后**不可回到草稿**」 | `p-approval` 计划卡 |
| 「计划内容 hash · **批准即绑定这一版**」 | `p-approval` 计划卡 |
| 队长**不可减、不可加**（每队一个任期） | `p-team-new` 队形说明 |
| 子成员不在建团这一步建（由队长后续派生） | `p-team-new` 队形说明 |
| 计划批准是**人类专属** | `p-team-new`「计划批准（人类专属）」 |

## 3. 三个方案

### 方案 A：团队直接以 `draft` 状态存在，成员先建占位

`TeamStatus += 'draft'`，提案时建 team + captain + N 个 `member.appointed`（`sessionId: null`），
批准时绑会话、改 active、开 Run。

- 优点：团队列表里能看到草稿。
- **缺点**：`MemberStatus` 已有 `appointed`（本来就允许「聘任了但还没会话」），
  语义上会与真实聘任混淆；丢弃后团队变成**残留的草稿壳**，要么加 `discarded` 状态
  （枚举再长一个），要么留在 draft 里永远不动 —— 两种都脏。
- 更要紧：**「批准前不产生任何会话与花费」用「先建占位再补」表达是反的** ——
  一旦建了实体，就得保证所有下游（看板、名册、配置、Run）都能容忍「无会话成员」，
  容错面铺得很大。

### 方案 B：计划是**独立聚合** `TeamPlan`，批准时才建团队（**采用**）

提案只落一条 `team.plan.proposed`，里面是**计划内容**（名字、目标、蓝图引用、
队形快照、工作流引用、队长会话、配置覆盖）。批准时**一个批次**建出 team + 成员 + 会话绑定 + Run。

- 优点：
  - 「批准前什么都没建」是**结构保证**，不是靠下游容错；
  - 丢弃只需清掉一条待确认记录，**没有任何残留实体**；
  - 不需要给 `TeamStatus` 加枚举，状态机不动；
  - 「批准后不可回到草稿」天然成立 —— 计划被消费掉了。
- 缺点：团队列表里看不到「草稿团队」。但设计稿本来就把计划放在**待你确认**里，
  不是放在团队列表里 —— 这个「缺点」其实符合设计。

### 方案 C：完全复用 `createTeamCommand`，加一个 `pending` 标记

- 缺点：等于在现有命令上打补丁，提案与执行搅在一起，「批准」变成改个字段，
  无法表达「批准即绑定这一版 hash」。

**决策：方案 B。**

## 4. 数据模型

```ts
/** 一份待人类批准的开队计划。批准后即被消费（不再存在）。 */
export interface TeamPlan {
  id: TeamPlanId
  /** 计划要建的团队名与目标。 */
  name: string
  goal: string
  /** 蓝图引用（含 revision：批准绑这一版）。 */
  blueprint: { id: BlueprintId; revision: number } | null
  /** 队形快照：蓝图 formation 允许在向导里改，改的是这份副本。 */
  formation: FormationSlot[]
  /** 默认工作流引用（第一次开 Run 用）。 */
  workflow: { id: WorkflowId; revision: number } | null
  /** 队长会话：提案人的会话。 */
  captainSessionId: SessionId
  /** 配置覆盖（蓝图默认 + 向导调整后的最终值）。 */
  overrides: ConfigOverrides
  /** 计划内容 hash：批准时校验，绑死这一版。 */
  planHash: string
  proposedBy: string
  proposedAt: string
}
```

**为什么 `planHash` 要单独算**：批准令牌的 `targetHash` 不能只绑「计划 id」——
计划内容（队形、工作流、配置）在预览与确认之间可能被人改过。
`planHash = hashContent({ name, goal, blueprint, formation, workflow, captainSessionId, overrides })`，
任何一项变了 hash 就变，令牌立刻失效。这与既有的「令牌绑影响面」是同一套思路。

**成员数量怎么来**：`formation` 里每个槽位 `count` 之和 = 计划成员数
（不含队长；队长单独一个任期）。批准时按槽位展开成成员。

## 5. 事件（三个，都要进 `EventType` 与 `EventPayloadMap`）

```ts
'team.plan.proposed':  { plan: TeamPlan }
'team.plan.approved':  { planId: string; teamId: string; planHash: string; runId: string | null }
'team.plan.discarded': { planId: string; reason: string; discardedBy: string }
```

**为什么批准事件要带 `teamId` 与 `runId`**：事后要能从账本追「这份计划最后建出了哪个团队、
开了哪个 Run」——否则计划被消费后，证据链就断了。

## 6. 批准的事务边界

`approveTeamPlanCommand` **一个 `runtime.commit([...])` 批次**内完成，顺序固定：

1. `team.plan.approved`（**先**清待确认：后面任何一步失败，批次整体不落，不会出现「计划没了但团队没建」）
2. `config.override.changed`（团队的配置快照）
3. `team.created`（`status: 'active'`，带 `captain` 与 `formation`）
4. N × `member.appointed`（按 formation 展开；`sessionId: null` → 成员 `appointed`）
5. ~~N × `member.session.bound`~~ —— **实测改掉**：这一层没有「创建宿主会话」的端口，
   也不该有（会话是执行载体，不是账本实体）。所以批准只建 `appointed` 成员，
   真正的会话由队长后续 spawn 时绑（既有 `member.session.bound` 路径）。
   「批准前不产生会话」这条约束仍然成立，而且更强：批准**当时**也不产生会话。
6. 若计划带 `workflow`：`run.created` + 首批任务事件（复用 `startWorkflowRunCommand` 的实例化逻辑）

> 关键：**批次原子性**是「不花钱」的保证 —— 任何一步抛错，整个批次回滚，
> 不会出现「建了 3 个会话然后失败」。

`discardTeamPlanCommand`：只落 `team.plan.discarded`，**不碰任何实体**（本来就没有）。

## 7. 权限

| 动作 | 谁能做 | 现有状态 |
|---|---|---|
| `plan.propose` | 队长（`CAPTAIN_ACTIONS`） | 需新增动作 |
| `plan.approve` | **人类专属** | ✅ 已在 `HUMAN_ONLY`，**无实现** |
| `plan.discard` | 人类 + 队长 | 需新增动作 |

`plan.approve` 走**令牌两段式**（预览出影响面 → 确认执行），与 `teamDisband` / `globalDefinitionSave` 同形。
令牌的 `targetHash` = `planHash`，`impactHash` = 影响面（几个成员、几个任务、开不开 Run）。

## 8. 读面与界面

- `pendingApprovalsView` 加 `kind: 'plan'`，`unsupported.planApproval` 改 `false`；
- 计划卡要显示设计稿那几项：**提出时间 / 提出人（队长）/ N 个任务 · M 名成员 / 批准后才建会话 /
  计划内容 hash 前 4 位 / 「丢弃不产生任何会话与花费」**；
- 三个动作：**改计划**（回到向导，本质是丢弃旧计划 + 重新提案）、**丢弃**、**批准并开跑**。

## 9. 不做什么（明确划界）

- **不做团队草稿态**（`TeamStatus` 不动）—— 方案 B 的理由见 §3；
- **不做「计划编辑」**：向导里改的是**提案前的表单**；已提交的计划不可改，
  只能丢弃再提（设计稿也没给「编辑已提交计划」）；
- **不做子成员预建**：设计稿明确「子成员不在这一步建，由队长后续派生」；
- **不做多工作流的 Run**：计划只带一个默认工作流（设计稿「第一次开 Run 用」）。

## 10. 验收判据

1. 提案后：`state.teamPlans` 有记录，`state.teams` **没有**新团队，`state.members` **没有**新成员，
   `state.runs` **没有**新 Run —— 「不产生会话与花费」是结构可验证的；
2. 批准后：team 为 `active`、成员数 = formation 之和、每个成员 `sessionId` 非空、
   （若带工作流）Run 已建且首批任务已落；
3. `planHash` 被改过 → 批准令牌失效（`CONFIRMATION_TARGET_CHANGED`）；
4. 丢弃后：待确认里消失，且**没有任何团队/成员/Run 被创建**；
5. 非人类 actor 调 `plan.approve` → `HUMAN_ONLY`；
6. 批准过的计划不能被再次批准（已消费）。
