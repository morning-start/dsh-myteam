# 设计：全局库编辑（I 组三页，写通道怎么开）

> 状态：`proposed`（方案，未实施）
> 日期：2026-11-24
> 上游：[界面依赖与搭建顺序 §4 I 组](../features/界面依赖与搭建顺序.md) · [contracts/panel-rpc](../contracts/panel-rpc.md) · `infrastructure/global-library/{library,write}.ts`
> 本文回答：**全局库（`$DSH_HOME/myteam/`）的编辑怎么写**，以及为什么不能拿现有的
> `definitionSave` 凑。

## 1. 先把已有的三条写路径摆清楚

| 路径 | 写什么 | 谁在用 | 有没有审计 |
|---|---|---|---|
| `definitionSave` | **项目副本**（`.dsh-myteam/events/project.jsonl` 里的定义事件） | 定义栏「保存定义」 | 有（项目账本） |
| `definitionPublish` | **全局库文件**（`$DSH_HOME/myteam/{roles,workflows,blueprints}/*.json`） | 定义栏「发布」 | 有（`audit/global-operations.jsonl`） |
| 无 | 全局库的**其它**编辑（改名、改内容但不经过项目） | — | — |

关键事实：**全局库唯一的写通道是「发布」**，而且发布是**从项目副本推上去**的：
项目里的定义 → 预览影响面 → 一次性令牌 → 写全局文件 + 记审计。
也就是说，现在想改全局库，**必须先在某个项目里有一份同名定义**。这正是 I 组三页
（`g-role-edit` / `g-workflow-edit` / `g-blueprint-edit`）点不动的原因：
它们要的是「直接在全局库上改」，而这条路不存在。

## 2. 为什么不能拿 `definitionSave` 凑

`definitionSave` 写的是**项目账本**。如果让它带一个 `scope: 'global'` 去写全局目录，
会同时坏三件事：

1. **真源错位**：全局库的权威是文件 + `global-operations.jsonl` 审计，不是项目账本。
   项目账本里出现一条「改了全局定义」的事件，会让「项目事件是唯一真源」这句话不再成立；
2. **审计漏掉**：全局写必须有操作审计（谁、改了哪个文件、改前改后 hash）。`definitionSave`
   不往 `global-operations.jsonl` 写，等于开了个没有留痕的全局写入口；
3. **权限口径错**：`definitionSave` 是 `definition.write`（队长也能做）。全局写必须更严
   （见 §4）。

## 3. 建议方案：在全局库端口上加「直改」，走同一份审计

### 3.1 端口扩一个方法（infrastructure 侧）

`GlobalPublicationPort` 现在只有 `exists` / `publish`。加两个：

```ts
export interface GlobalEditInput {
  kind: 'role' | 'workflow' | 'blueprint'
  id: string
  definition: unknown          // 完整定义本体（含 revision）
  operationId: string
  expectedHash: string         // 客户端看到的当前文件哈希：并发的保护伞
  editedAt: string
  editor: string               // 人类入口标识
}

export interface GlobalLibraryEditPort {
  readFileHash(kind, id): string | null        // 不存在返回 null；用于预览与冲突检测
  writeFile(input: GlobalEditInput): { file: string; globalHash: string }
}
```

`writeFile` 的实现和现在的 `publish` **共用同一段原子写**（临时名 → rename → 追加审计），
只把审计里的 `action` 从 `definition.publish` 换成 `definition.edit`，
并额外记 `previousHash`（旧文件 hash）。这样「全局库的每次变化都有一条审计」这条不变量
不会被新入口破坏。

**冲突检测**：`expectedHash` 与当前文件 hash 不一致就拒绝（`CONFLICT`），
对应界面上「你看到的版本变了，重新载入」那一屏（设计稿 `p-states` 里就有这张卡）。
这是防止两个窗口同时改同一个全局定义的关键。

### 3.2 应用层用例（application 侧）

新增 `editGlobalDefinition`：

```
读当前文件 hash → 与 expectedHash 比对 → 校验定义本体（复用 domain 的
normalizeRole/validateRole、normalizeWorkflow/validateWorkflow、normalizeBlueprint/validateBlueprint）
→ 写文件 + 记审计 → 返回新 hash
```

注意：**蓝图在全局库上引用的是全局角色 / 全局工作流**，所以 `validateBlueprint` 的解析器
要换成「读全局库目录」，不能复用项目的 `state.roles`。这一条容易漏，漏了会出现
「全局蓝图引用了项目角色」这种跨作用域脏数据。

### 3.3 面板写（panel-writes 侧）

新增三条写方法，或一条带 `kind` 的：

- 方案 A（三条）：`globalRoleSave` / `globalWorkflowSave` / `globalBlueprintSave`
- 方案 B（一条）：`globalDefinitionSave`（`params.kind` 决定写哪个目录）——**推荐 B**，
  和现有 `definitionSave` 的形状对称，界面也好写。

确认方式：**`token`（两段式）**，不是 `direct`。理由：改全局库会影响**所有项目**
（引用它的团队下次建团就拿到新版本），影响面比项目内定义大一个量级，值得走「先看影响面、
再凭一次性令牌写」。影响面预演要列出：哪些项目引用它、哪些团队蓝图在用、改完后哪些地方
会出现「有更新」。

### 3.4 权限

| 动作 | 人类 | 队长 | 成员 |
|---|---|---|---|
| `globalDefinitionSave`（写全局库） | ✅（令牌） | ❌ | ❌ |

理由：全局定义是**跨项目**资产，队长只对自己项目负责。现在的 `definitionPublish` 已经
是「人类专属」（`definition.publish.confirm` 在 `HUMAN_ONLY` 里），全局直改应当同级或更严。
建议新增 `definition.global.write` 动作，放进 `HUMAN_ONLY`。

### 3.5 界面（I 组三页）

- `g-role-edit` / `g-workflow-edit` / `g-blueprint-edit` 复用**项目侧**那两个表单组件
  （`RoleEditBox` / `BlueprintEditBox`），加一个 `scope: 'global'` 属性决定提交到哪条写方法；
  这是 L1「同一块信息不要写两套」的延续，不新写三页表单；
- 提交前先拉 `globalLibrary` 拿到当前 `content` 与 hash 放进表单（现在 `GlobalEntry.content`
  已经带着正文了，够用）；
- 影响面预演 + 令牌确认沿用 `TokenAction`（`definitionPublish` 用的就是它）。

## 4. 要你拍板的三个点

1. **确认方式**：我建议 `token`（两段式、先看影响面）。如果你觉得「改个全局角色描述」
   不值得每次都看影响面，可以退一步：**内容只改文本字段时用 `direct`，改动结构（能力集 /
   队形 / 模板）时用 `token`** —— 但这个「哪些字段算结构性」的分界线以后会扯皮，我更倾向一刀切 `token`。
2. **谁能写**：我建议**只有人类**（`HUMAN_ONLY`）。如果你希望队长也能改全局库（比如
   队长维护自己团队的角色模板），那要再定「队长只能改自己发布过的那些」——这需要一个
   `owner` 字段，成本更高。
3. **冲突策略**：我建议 `expectedHash` 不一致就**拒绝**（不做自动合并）。全局库是 JSON 文件，
   自动合并两个并发编辑最容易产出「字段都在但语义不通」的结果，宁可让人重载。

## 5. 实施批次（拍板后）

| 批次 | 内容 | 验收 |
|---|---|---|
| **G1 端口** | `GlobalLibraryEditPort`（`readFileHash` / `writeFile`），与 `publish` 共用原子写与审计 | 新测试：写成功后文件与审计都在、`previousHash` 正确、`expectedHash` 不符时拒绝且不落盘 |

| **G4 界面** | 三个 `g-*-edit` 复用项目表单 + 影响面预演 | t39 三条 + 可视化截图 |

## 6. 本文不做

- 不写代码（`plugin/src`、`plugin/client`、`design-v2` 一律不动）；
- 不决定「队长能不能改全局库」（只给建议，见 §4-2）；
- 不动 `definitionPublish` 的现有语义 —— 发布（项目 → 全局）和直改（全局 → 全局）是两条路，
  各走各的审计 action，不合并。
