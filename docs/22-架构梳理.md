# 22-架构梳理（实测）

> **本文的性质**：不是设计意图，是**一次体检的快照**。所有数字由 `node tools/arch-report.mjs` 从
> `plugin/src/**/*.ts` 现算得出 —— 代码一变数字就旧，所以本文只保留「结构判断」与「判断依据」，
> 数字标注了取数方式；有疑问时**跑一遍脚本**，不要引用正文里的旧值。
>
> 采集时点：`plugin/src` 56 个模块 / 144 条依赖边 / 23,024 行；单测 913 条全绿。

## 1. 怎么取数

```bash
node tools/arch-report.mjs           # 人读报告
node tools/arch-report.mjs --json    # 机器可读（重建表格用）
node tools/arch-report.mjs --selftest # 解析器自检（6 条边界，改解析器前先跑）
node tools/check-architecture.mjs    # 另一件事：A1–A5 五条硬红线门禁（违规退 1）
```

两者分工不同，**不要互相替代**：

| 工具 | 性质 | 输出 | 退码 |
|---|---|---|---|
| `check-architecture.mjs` | 门禁 | 只报 5 类违规 | 有违规 = 1 |
| `arch-report.mjs` | 体检 | 分层、边、环、枢纽、体量、导出面、子域矩阵 | 恒 0 |

体检不做判红，是因为**大部分结构数字没有对错**：`index` 出边 21 是聚合层的必然代价，不是缺陷。
把它做成门禁只会逼人加豁免注释。

## 2. 实测分层

| 层 | 模块 | 行数 | 占比 | 职责 |
|---|---|---|---|---|
| 入口层 | 4 | 7,770 | **33.7%** | `host.ts` / `panel.ts` / `smoke.ts` / `host-workspace.ts` |
| 远程面 | 2 | 806 | 3.5% | `remote/service.ts`（typert 方法门面）、`remote/plan-feedback.ts` |
| 工具声明 | 1 | 916 | 4.0% | `tools/defs.ts`（64 个工具的 schema 与档位） |
| 共享内核 | 1 | 265 | 1.2% | `core/errors.ts`（`MT_*` 码表，唯一） |
| 基础设施 | 2 | 577 | 2.5% | `core/fs/`（原子写原语 + 记账本） |
| 核心装配 | 2 | 1,067 | 4.6% | `core/service.ts`（单写者提交管线）、`core/lifecycle.ts` |
| 领域子域 | 44 | 11,623 | 50.5% | `core/<子域>/` 共 17 个子域 |

判定口径（在脚本 `LAYERS` 里，改口径就要改这张表）：

- **层深**：入口 0 → 远程/工具 1 → 核心装配 2 → 领域/基础设施 3 → 共享内核 4。
  合法依赖只能「向下或同层」；`depth(from) > depth(to)` 才算逆向边。
- **`core/errors.ts` 单列共享内核**：它是最通用的常量表，任何层依赖都合法，不因为物理上躺在
  `core/` 里就算越界。
- **`import type` 与 value 边分开算**：type 边运行时被擦除，不会造成装载顺序问题，但仍是耦合，
  所以单独报、不混进环。

## 4. 依赖方向

144 条边里 value 122、type 22。层间分布（全部为正向或同层）：

```
entry   -> domain    50        domain -> domain        40
domain  -> domain(t) 16        domain -> infra         11
core-root -> domain   8        domain -> shared         1 / (t) 3
entry   -> core-root  2        entry  -> remote         2
remote  -> domain     2 /(t)1  infra  -> shared  (t) 1 /  infra -> infra 1
tools   -> domain     1        entry  -> {infra,tools,entry} 各 1
```

- **逆向边（value）：0 条。**
- **环形依赖（value 边，运行时会真的互相装载）：0 个。**
- **环形依赖（仅 type 边）：1 个** —— `host.ts ⇄ remote/service.ts`。`host.ts` value 依赖
  `remote/service.ts`（装载时注册门面），`remote/service.ts` 只 `import type { MyTeamHost }`
  反指入口。运行时被擦除，**没有装载风险**，但接口耦合是真的：`MyTeamHost` 一改，两边同时动。
  想解就把这个类型抽成 `core/host/contract.ts` 之类的纯接口，让远程面对"入口类的形状"不再知情。
- **入口不可达（疑似死代码）：0 个。**
- **悬空说明符：0 条。**

这三项是本文最正面的结论：**分层纪律靠 `check-architecture.mjs` 的 A1 守住了，没有靠人自觉。**

## 5. 六条结构性判断

### ① 唯一真实的结构风险：入口层占 33.7%，`host.ts` 是上帝模块

```
6210 行  host.ts          fan-out 44   27 exports
1355 行  panel.ts         fan-out 12
 916 行  tools/defs.ts
```

`host.ts` 一个文件承担：64 个工具的 handler 装配、成员 spawn 生命周期、plan 提交、门禁接线、
角色/预设/知识/贡献/归档/导出的编排、token 侧车。它的 fan-out 44 意味着**任何子域改接口，
第一现场都可能在它这里**。

这不是"设计错了"——它是 ADR-001~016 一路长出来的编排层。但它是**唯一**会随功能线性变大的文件，
也是 `lib/host.mjs` 的唯一入口。真要动，动法是按端点族拆 `host/<域>.ts`（薄适配层，不改
`MyTeamHost` 的对外形状），而不是把逻辑往 `core/` 里搬——搬进去就变成第二个 `service.ts`。

### ② 四个枢纽，`workspace` 与 `fs` 已经超出"工具模块"的分量

| 枢纽 | 入边 | 性质 |
|---|---|---|
| `core/workspace/layout.ts` | 15 | 路径真源（`storeLayout()` / `resolveProjectRoot()`） |
| `core/fs/write-log.ts` | 12 | 写盘出口（CHG-174 之后成为全局依赖） |
| `core/scheduler/state.ts` | 9 | 状态机与投影类型 |
| `core/roles/role-store.ts` | 7 | 角色三来源 |

前两个是**刻意的单点**：路径与写盘都只该有一条路。代价是它们一改就全仓动 —— 所以
`layout.ts` 的 29 个导出、`write-log.ts` 的 12 个入边**必须保持窄**，加导出前先问
「这是不是又在给全仓开一个口子」。

### ③ `gates` 与 `tools` 是干净的纯叶

出边都是 **0**：`core/gates/**`（4 个模块 807 行）只吃类型、只吐判定，`tools/defs.ts` 只声明
schema。**这是本文最健康的一处**——质量判定与工具声明都没有反向抓业务状态。任何给它们加
出边的改动都值得在 review 里被问一句。

### ④ `index` 出边 21 是聚合层的必然代价，但别让它被反向依赖

`core/index/`（3 模块 1,435 行）把 config / presets / roles / scheduler / ledger / workspace
全拉进来，为的是"不构造 `TeamService` 也能出看板"（A9 冷启动重连）。出边 21 是这个目标的
直接代价，**不是缺陷**。

风险在另一侧：它目前入边 7。**只要有人开始 import `offline-view.ts` 干不是"离线只读"
的事，聚合层就会变成第二个上帝模块。** 判据：`index` 只被 `host.ts` / `remote/service.ts` /
测试引用；新增引用方需要说明为什么不能走 service 投影。

### ⑤ 基础设施成为枢纽是新的耦合面（CHG-174 的双刃）

`core/fs/` 两个模块 577 行，入边 12 —— 迁移后它是全仓第三大被依赖点。这符合"唯一写盘出口"
的设计，但它带来一个新的纪律要求：**`atomic-write.ts` 的导出面必须极稳**。当前 8 个导出
（`ensureDir` / `writeTextAtomicRaw` / `appendTextSync` / `fsyncDir` / `fingerprint` / `snapshot` /
`restore` / `removeIfExists`）已够用，**再往里加"顺手功能"就是给 12 个调用方同时加耦合**。

### ⑥ 子域互依赖有一个双向对，量都很小

跨子域边里唯一的双向对是 `tasks ⇄ scheduler`（各 1 条）。`tasks` 只 329 行、出边 1，
`tasks/graph.ts` 与 `scheduler/state.ts` 的职责边界在"任务定义 vs 任务状态"上，两者互看一次
是合理的。**不需要动**，但如果这个对涨到各自 3 条以上，就该并成一个子域。

其余跨子域边都是单向且集中：`index -> scheduler`(6) / `index -> config`(4) /
`contributions -> roles`(3) —— 都符合"上层聚合下层"。
