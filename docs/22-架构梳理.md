# 22-架构梳理（实测）

> **本文的性质**：不是设计意图，是**一次体检的快照**。所有数字由 `node tools/arch-report.mjs` 从
> `plugin/src/**/*.ts` 现算得出 —— 代码一变数字就旧，所以本文只保留「结构判断」与「判断依据」，
> 数字标注了取数方式；有疑问时**跑一遍脚本**，不要引用正文里的旧值。
>
> 采集时点：`plugin/src` **72 个模块 / 229 条依赖边（value 173 · type 56） / 26,083 行**；
> 单测 **950 条**全绿；客户端 `plugin/client/client.js` **13,343 行 / 45 个源码片段**。

## 1. 怎么取数

```bash
node tools/arch-report.mjs           # 人读报告
node tools/arch-report.mjs --json    # 机器可读（重建表格用）
node tools/arch-report.mjs --selftest # 解析器自检（6 条边界，改解析器前先跑）
node tools/check-architecture.mjs    # 另一件事：A1–A5 五条硬红线门禁（违规退 1）
```

两者分工不同，**不要互相替代**：

| 工具 | 性质 | 输出 | 退码 |
|---|---|---|---|
| `check-architecture.mjs` | 门禁 | 只报 5 类违规 | 有违规 = 1 |
| `arch-report.mjs` | 体检 | 分层、边、环、枢纽、体量、导出面、子域矩阵 | 恒 0 |

体检不做判红，是因为**大部分结构数字没有对错**：`index` 出边 21 是聚合层的必然代价，不是缺陷。
把它做成门禁只会逼人加豁免注释。

判定口径（在脚本 `LAYERS` 里，改口径就要改这张表）：

- **层深**：入口 0 → 远程/工具 1 → 核心装配 2 → 领域/基础设施 3 → 共享内核 4。
  合法依赖只能「向下或同层」；`depth(from) > depth(to)` 才算逆向边。
- **`core/errors.ts` 单列共享内核**：它是最通用的常量表，任何层依赖都合法，不因为物理上躺在
  `core/` 里就算越界。
- **`import type` 与 value 边分开算**：type 边运行时被擦除，不会造成装载顺序问题，但仍是耦合，
  所以单独报、不混进环。

## 5. 六条结构性判断

### ① 唯一真实的结构风险：入口层占 30.7%，`host.ts` 是上帝模块

```
4377 行  host.ts          fan-out 55   23 exports
1400 行  panel.ts         fan-out 12
 992 行  tools/defs.ts
```

`host.ts` 一个文件承担：68 个工具的 handler 装配、成员 spawn 生命周期、plan 提交、门禁接线、
角色/预设/知识/贡献/归档/导出的编排、token 侧车。它的 fan-out **55** 意味着**任何子域改接口，
第一现场都可能在它这里**。

这层已经从 33.7% 降到 **30.7%**（CHG-174 之后 `host/*.ts` 拆出了 plan / tasks 等端点族，
A6 行数棘轮锁在 4,377）。真要再动，动法仍是按端点族拆 `host/<域>.ts`（薄适配层，不改
`MyTeamHost` 的对外形状），而不是把逻辑往 `core/` 里搬——搬进去就变成第二个 `service.ts`。

### ② 四个枢纽，`workspace` 与 `fs` 已经超出"工具模块"的分量

| 枢纽 | 入边 | 性质 |
|---|---|---|
| `core/workspace/layout.ts` | 15 | 路径真源（`storeLayout()` / `resolveProjectRoot()`） |
| `core/fs/write-log.ts` | 12 | 写盘出口（CHG-174 之后成为全局依赖） |
| `core/scheduler/state.ts` | 9 | 状态机与投影类型 |
| `core/roles/role-store.ts` | 7 | 角色三来源 |

前两个是**刻意的单点**：路径与写盘都只该有一条路。代价是它们一改就全仓动 —— 所以
`layout.ts` 的 29 个导出、`write-log.ts` 的 12 个入边**必须保持窄**，加导出前先问
「这是不是又在给全仓开一个口子」。

### ③ `gates` 与 `tools` 是干净的纯叶

出边都是 **0**：`core/gates/**`（4 个模块 807 行）只吃类型、只吐判定，`tools/defs.ts` 只声明
schema。**这是本文最健康的一处**——质量判定与工具声明都没有反向抓业务状态。任何给它们加
出边的改动都值得在 review 里被问一句。

### ④ `index` 出边 21 是聚合层的必然代价，但别让它被反向依赖

`core/index/`（3 模块 1,435 行）把 config / presets / roles / scheduler / ledger / workspace
全拉进来，为的是"不构造 `TeamService` 也能出看板"（A9 冷启动重连）。出边 21 是这个目标的
直接代价，**不是缺陷**。

风险在另一侧：它目前入边 7。**只要有人开始 import `offline-view.ts` 干不是"离线只读"
的事，聚合层就会变成第二个上帝模块。** 判据：`index` 只被 `host.ts` / `remote/service.ts` /
测试引用；新增引用方需要说明为什么不能走 service 投影。

> **CHG-193（T160）补记**：`index` 的**界面消费方已接线**——面板「任务」tab 的四视图统一吃
> `getBoard({}).project`（派生索引），索引不可用/为空时回落 `getProject().tasks`（降级不白屏）。
> 这一条此前在架构讨论里一直写成「`getBoard().project` 无消费方」的待办，但**仓库里从来没有
> 这条待办条目**（`t140` 只钉了索引本身的不变量）——按事实补记，而不是划掉一条不存在的行。
> 接线方式守住了 ④ 的边界：客户端只做**一次性投影**（`resolveProjectTasks` 纯函数），
> 不缓存、不回写、不参与计算，`index` 的入边没有因为这次接线而增加（`client.js` 不经模块图）。

### ⑤ 基础设施成为枢纽是新的耦合面（CHG-174 的双刃）

`core/fs/` 两个模块 577 行，入边 12 —— 迁移后它是全仓第三大被依赖点。这符合"唯一写盘出口"
的设计，但它带来一个新的纪律要求：**`atomic-write.ts` 的导出面必须极稳**。当前 8 个导出
（`ensureDir` / `writeTextAtomicRaw` / `appendTextSync` / `fsyncDir` / `fingerprint` / `snapshot` /
`restore` / `removeIfExists`）已够用，**再往里加"顺手功能"就是给 12 个调用方同时加耦合**。

### ⑥ 子域互依赖有一个双向对，量都很小

跨子域边里唯一的双向对是 `tasks ⇄ scheduler`（各 1 条）。`tasks` 只 329 行、出边 1，
`tasks/graph.ts` 与 `scheduler/state.ts` 的职责边界在"任务定义 vs 任务状态"上，两者互看一次
是合理的。**不需要动**，但如果这个对涨到各自 3 条以上，就该并成一个子域。

其余跨子域边都是单向且集中：`index -> scheduler`(6) / `index -> config`(4) /
`contributions -> roles`(3) —— 都符合"上层聚合下层"。

## 6. 客户端（`plugin/client/`）—— 与 `plugin/src` 分开算

客户端**不在**上面的模块图里（它跑在浏览器，由宿主 `__ModuleLoader__` 装载，不走 TS 编译）。
CHG-202j/k 之前它是一个 **13,819 行的单文件**；现在拆成 **45 个源码片段 + 构建产物**。

### 6.1 为什么是「纯文本拼接」而不是 ESM / 打包器

| 约束 | 后果 |
|---|---|
| 宿主 `__ModuleLoader__` 只提供 `react` / `react/jsx-runtime` 这类**裸模块名** | 没有跨文件 `require` |
| `client.js` 被 `new Function('window','document',source)` 当**脚本**执行 | 不能用 `import` / `export` |
| 131 个测试断言 `source.includes('...')` | 任何转译（压缩 / 重命名）都会让断言失效 |

所以 `scripts/build-client.mjs` 只做一件事：按文件名排序**拼接**。产物与片段一致由
`npm run check:client` 守（CI 里跑，漂移即红）。

### 6.3 依赖方向门禁（`tools/check-client-arch.mjs`）

片段被拼进**同一个闭包**，编译器不会拦「底层引用高层」。这个脚本补上这道墙：
**片段只能引用更早片段声明的名字**（`00 → 10 → … → 79 → 90`）。

首轮抓出 **23 处历史倒挂**（11 处 TDZ + 12 处 hoisting），CHG-202j~q 全部还清：
`PROJECT_COLUMNS` 等 helpers 提到 `45-panel-helpers.js`，`fmtClock` / `dagChipOf` /
`sumBuckets` / `hitRateOf` 也移过去，`EditHistory` → `46-`、`DiagChips`/`DiagFix` → `47-`、
`pendingNav`/`openWorkbench`/`takePendingNav`/`resolveNavForSession` → `21-entry-nav.js`。
**棘轮基线已锁 0 / 0** —— 新增向上依赖立刻红。

> **取词必须用词法扫描，不能用「正则替换」**：先前的实现「先剥注释再剥字符串」，
> 字符串里的 `//`（如 `'narrows only, never widens'` 附近的 URL）会被当成行注释、
> 把引号一起吃掉，导致后续**全部错位**、误报 5 处根本不存在的倒挂。现在用单遍状态机
> （注释 / 单双引号串 / 模板串 `${}` 递归 / 标识符），只取**代码态**标识符。

### 7.1 `host.ts` 拆分施工说明（CHG-202p/q/r 五次失败换来的）

`host.ts` 的前 585 行是**顶层纯函数**（零副作用、不碰 `this`），是最安全的切入点。但**不要用脚本正则搬代码**——五次尝试五次失败，每次都是「修好一个坑、暴露下一个」：

| # | 失败原因 |
|---|---|
| 1 | 导入插到了**类内部**（找「最后一条 import」时匹配到了类里的动态 import） |
| 2 | 相对导入没重基（`helpers.ts` 在 `src/host/` 下，`./core/x` 要变 `../core/x`） |
| 3 | 只复制**第一组** import（`host.ts` 的 import 分散在 100 多行里，`truncateOutput` 在 L77） |
| 4 | body 内部还夹着一条未重基的 import → 与顶部重复声明 |
| 5 | `merge-imports` 按模块合并时把 `sessionCwdOf` 的绑定弄丢 |

**正确姿势（编译器驱动，不要猜）**：

```bash
# 1) 先拆：把 L150-L584 原样搬进 src/host/helpers.ts（导入段留空）
# 2) 让 TS 报错，拿到完整缺失符号清单
cd plugin && npx tsc --noEmit 2>&1 | grep "Cannot find name"
# 3) 按清单一次性手写 helpers.ts 的 import（约 25 个符号，5 分钟）
#    注意：值是 import { x }，类型是 import type { T }
# 4) host.ts 只需 import 它用到的「私有」符号（原来没 export 的那 10 个）
# 5) 全量：npm test && node ../tools/check-architecture.mjs
```

**为什么值得拆**：不是为了「行数少」，而是 `host.ts` 是**唯一会随功能线性变大**的文件（A6 棘轮锁在 4,377）。拆成薄适配层后，新增端点族只动 `host/<域>.ts`。

**为什么可以先不做**：`host.ts` 4,377 行**不是坏代码**——它是 ADR-001~016 一路长出来的编排层，`check-architecture.mjs` 的 A1 已经守住了分层方向（逆向边 0、环 0）。拆它是**可读性优化**，不是正确性修复。
