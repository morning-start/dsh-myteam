# 01 · 系统架构

> 状态：`proposed`（四段设计已获用户逐段确认，待整本文档评审）
> 架构基线：[00-现状与决策基线](00-现状与决策基线.md)
> 本文边界：定义目标系统的资源、真源、组件、权限、配置、恢复与兼容边界；不展开具体工具参数、RPC 字段或 UI 控件。

## 1. 架构目标

myteam 是 DSH 内的通用多智能体团队运行时。目标不是把更多功能塞进队长会话，而是建立三个清晰层次：

1. **全局复用层**：用户明确管理的角色与 TeamBlueprint。
2. **项目定义与运行层**：项目资产、多个团队、项目任务 DAG、配置、知识和长期记忆。
3. **DSH 执行层**：队长/成员会话、子代理、模型调用、工具执行与 Session Log。

### 1.1 必须成立的能力

- 一个项目可并行运行多个团队；
- 项目只有一张完整任务看板和一个完整依赖图；
- 任务可跨团队依赖，图修改具有一致的项目 revision；
- 队长、成员、面板和离线查询看到同一份业务事实；
- 项目资产可跨会话与重启恢复，全局资产可复用但不隐式同步；
- 全局写不可由 agent 伪造确认；
- 配置、知识和运行历史可审计，缓存可重建；
- 成员可长期记忆，但只能访问自己有权的 memory bank。

### 1.2 非目标

- 不做全局任务、跨项目任务 DAG 或全局运行中团队；
- 不做全局行为默认配置；
- 不做全局与项目之间的自动双向同步；
- 不把 DSH AgentPreset 当作业务团队模板；
- 不复制 DSH Session Log 来建立第二份会话真相；
- 不由 myteam 代管 MCP 凭据、连接或宿主全局技能；
- 不在本轮引入运行时 SQLite、向量检索、跨机器分布式调度或多 Workspace 联合事务；
- 不用“跳过坏事件并显示空状态”代替权威数据修复。

## 2. 统一术语与资源模型

### 2.1 核心实体

| 实体 | 定义 | 作用域 | 唯一权威 |
|---|---|---|---|
| `RoleDefinition` | 职责、提示词、能力引用、模型与委派约束的可复用定义 | global / project | 全局文件或项目事件 |
| `TeamBlueprint` | 建团蓝图：队形、角色引用、默认流程与配置 | global / project | 全局文件或项目事件 |
| `Project` | 一个工作区内的全部 myteam 定义与运行事实 | project | 项目事件日志 |
| `Team` | 项目内一个实际协作团队及其生命周期 | project | 项目事件日志 |
| `CaptainAssignment` | 某团队当前队长会话及任期世代 | project | 项目事件日志 |
| `Member` | 团队对角色的一次聘任，含父子关系与运行绑定 | project | 项目事件日志 |
| `Task` | 项目工作项，含 AC、交付物、依赖、门禁与状态 | project | 项目事件日志 |
| `Participation` | 任务与团队的主责/协作关系 | project | 项目事件日志 |
| `Attempt` | 成员认领任务的一次执行世代与能力票据 | project | 项目事件日志 |
| `GateVerdict` | 对任务某一检查点的结构化裁决与证据 | project | 项目事件日志 |
| `KnowledgeEntry` | 经策展的项目知识、证据和修订关系 | project | 项目事件日志 |
| `MemoryEntry` | 团队或成员的长期私有记忆 | project | 项目 SQLite |
| `ArtifactRef` | 对项目工作区交付物的路径、hash 与验证引用 | project | 事件引用；正文在交付物文件 |
| `SessionRef` | 对 DSH 会话与事件位置的引用 | project / DSH | myteam 存引用，DSH 存会话事实 |
| `Effect` | 已提交事件驱动的 spawn、消息、门禁或生成动作 | project | 请求/结果在事件中，外部执行事实在 DSH |

### 2.2 TeamBlueprint 不是 AgentPreset

| 对比 | TeamBlueprint | DSH AgentPreset |
|---|---|---|
| 回答的问题 | “要组建什么团队？” | “这个 Agent 会话由哪些宿主插件与能力组成？” |
| 示例 | 需求分析 + 实现 + 审查的团队蓝图 | `myteam-captain`、`myteam-member` |
| 生命周期 | 全局/项目定义，可复制、发布、版本化 | 由 DSH bundle patch 声明与装载 |
| 是否含任务/成员会话 | 不含运行任务或既有会话 | 不含业务团队任务 |
| 修改者 | 项目 agent；全局仅用户确认 | 插件开发者/用户配置，按 DSH 权限治理 |

### 2.3 身份与引用规则

- `projectId` 在初始化时生成并写入 manifest，不因工作区移动而改变；
- `roleId`、`blueprintId` 在同一作用域内唯一；跨作用域以 `scope + id` 区分，并用 `origin` 记录复制来源；
- `teamId` 在项目内唯一；
- `taskId` 在项目内唯一，不再用 `teamId/taskId` 才能定位；
- 成员使用 `teamId + memberId` 作为项目内复合身份；宿主 `sessionId` 是外部绑定，不代替成员身份；
- `attemptId` 表示一次执行认领，`attempt generation` 表示新旧顺序，二者不可混用；
- `projectSeq` 是项目全序，`entityRevision` 是单实体版本，`configRevision` 是配置版本，三者用途不同；
- 迁移数据保留 `legacyId` 与原始位置，不能为了形状统一而丢失追溯能力。

### 2.4 定义、快照与运行实例

```text
Global Definition
   │ copy to project（项目事件，记录 origin + source hash）
   ▼
Project Definition Revision
   │ instantiate（记录 definition revision）
   ▼
Team / Member / Effective Config Snapshot
   │ runtime events
   ▼
Attempts / Gates / Messages / Artifacts
```

- 修改全局定义不影响项目副本；
- 修改项目角色只影响之后的新聘任；
- 修改 TeamBlueprint 只影响之后的新团队；
- 既有实例需要采用新定义时，必须显式执行相应动作并留下事件；
- 上游有新版本时可以显示 `updateAvailable`，但不自动 rebase，也不隐式覆盖项目修改。

项目定义的来源与发布状态采用以下口径：

- `origin {scope,id,initialRevision,initialHash}` 是最初复制来源，保持为不可变 lineage；
- `baseHash` 是用于三方比较的共同基准：复制时等于来源 hash，显式 rebase 后等于新基准 hash，发布成功后等于全局实际写入 hash；
- `contentHash` 是当前项目定义的规范化内容 hash；项目内容变化才推进 `definitionRevision`；
- `lastPublication {operationId,target,definitionRevision,globalHash,publishedAt}` 由发布 outcome 更新，它属于发布 lineage，不另造项目定义内容 revision；
- `upstreamChanged = globalLatestHash !== baseHash`，`localChanged = contentHash !== baseHash`；只有上游已变且全局最新内容不等于项目内容时显示 `updateAvailable`，本地可发布变化单独显示为 `publishAvailable`，两者同时成立即 `diverged`，必须显式处理，不把三者混为一个“已过期”标记；
- 全局定义不存在或 hash 无法取得时显示明确的 `unavailable/unknown`，不能靠猜测更新状态。

## 3. 作用域与权限

### 3.1 作用域矩阵

| 数据/能力 | 全局级 | 项目级 |
|---|---|---|
| RoleDefinition | ✅ 复用库 | ✅ 可编辑定义，运行实例化来源 |
| TeamBlueprint | ✅ 复用库 | ✅ 可编辑定义 |
| 运行中 Team / Captain / Member | ❌ | ✅ |
| Task / DAG / Attempt / Gate | ❌ | ✅ |
| 行为配置 | ❌ | ✅ 项目默认、蓝图默认、团队覆盖 |
| Knowledge | ❌ | ✅ |
| Memory | ❌ | ✅ |
| 看板、索引、生成配置、导出 | ❌ | ✅ 派生或输出 |
| Skill / MCP / 工具连接本体 | 由 DSH/用户管理 | myteam 只保存引用，不复制管理权 |

### 3.2 写权限矩阵

| 操作 | Captain | Member | Human |
|---|---|---|---|
| 读取授权范围内项目视图 | ✅ | ✅ 本团队/自身范围 | ✅ |
| 新建/修改项目角色、蓝图、配置 | ✅ | 默认 ❌，可提案 | ✅ |
| 创建/重规划/分派项目任务 | ✅ | 仅授权子集或提案 | ✅ |
| 认领、进度、证据、 escalate | 按队长职责 | ✅ 仅合法 Attempt/任务 | ✅ 可介入 |
| 复制全局定义到项目 | ✅ | 默认 ❌ | ✅ |
| 提出全局发布请求（仅记录意图，不写全局） | ✅ | 默认 ❌ | ✅ |
| 发布/覆盖/删除全局定义 | ❌ | ❌ | ✅ 人类专属入口 + 确认 |
| 批准计划、队长接管、解散团队 | 只能提案 | 只能 escalate | ✅ |
| 知识提案 / 采纳 | ✅ 采纳 | ✅ 提案 | ✅ |
| 记忆读取/写入/归档 | 团队 bank | 仅授权 bank | 按授权 |
| 全局 Skill/MCP/连接管理 | 不经 myteam | 不经 myteam | DSH 用户管理面 |

### 3.3 人类确认不可伪造

人类专属动作必须同时满足：

1. 来自 DSH 不提供给模型调用的用户操作入口；
2. 先返回影响面预览，包括目标、内容 hash、占用/引用和不可逆后果；
3. 确认令牌绑定操作、目标、影响面、hash、过期时间与一次性 nonce；
4. 服务端在提交时重新验证调用来源、令牌和最新 revision；
5. 工具 schema 不注册该能力，服务端仍执行相同鉴权，不能只靠隐藏工具。

`actor:'human'`、`confirm:true`、`confirmGlobal:true` 只是普通数据，不能证明用户意图。

Captain 或 Human 可以先在项目中记录发布 `proposed`，它只表示**待确认意图**，不是全局写授权，也不会自动触发全局 Effect。只有 Human 完成预览与确认后，GlobalDefinitionLibrary 才能执行；Member 默认只能提出普通项目修改提案，不能创建全局发布请求。

确认时记录全局目标的当前 hash。若上游在预览后发生变化，原令牌和预期 hash 立即失效，必须重新生成差异预览并再次确认，不得自动 rebase 或覆盖。审计只保存确认摘要，不保存确认令牌本体。

### 3.4 能力只收窄

- 角色与成员的工具 allow 只能收窄，deny 不能重新开放已被上层禁止的能力；
- 子成员工具集必须是父成员有效工具集的子集；
- 委派权限、普通 CM 操作权限和记忆 bank 权限分别判断，不能共用一个含混的 allow 字段；
- 工具不可见只是体验层，应用服务鉴权才是安全边界，DSH 文件沙箱是另一层独立边界。

## 4. 系统容器与组件

```text
┌─ DSH Root Host ─────────────────────────────────────────────────┐
│                                                               │
│  MyTeamRuntime（按 projectId 管理）                            │
│  ├─ Application Command Services                              │
│  ├─ Application Query Services                                │
│  ├─ Project Writer / Writer Lease                             │
│  ├─ Projection Engine                                         │
│  ├─ Effect Runner                                             │
│  └─ Memory Store                                              │
│                                                               │
│  GlobalDefinitionLibrary                                      │
│  HumanAuthorizer                                              │
└─────────────▲─────────────────▲─────────────────▲─────────────┘
              │                 │                 │
      Captain Adapter     Member Adapter      Panel / RPC Adapter
      tools + persona     tools + abilities   query + user actions
```

### 4.1 Root MyTeamRuntime

负责：

- 按 `projectId` 打开、恢复和关闭项目实例；
- 将 captain、member、human 的调用映射为显式 `CommandContext`；
- 提供统一命令与查询入口；
- 管理项目写者、事件提交、投影、Effect 和记忆；
- 在队长离线时仍接受成员合法的证据、进度与消息持久化；
- 队长离线期间暂停新的派遣与生命周期副作用。

它不再属于任何一个 captain preset。

### 4.2 Captain / Member Adapter

Captain preset 只包含队长 persona、队长工具与必要的会话能力。Member preset 只包含成员工具、角色能力和提示词装配。

二者都通过 Root Runtime 调用应用服务，不保存业务投影，不拥有账本，不通过父会话寻找另一个业务服务。

成员身份由 `sessionId + project binding` 解析并验证；不能只靠工具参数声明 `memberId/teamId`。

### 4.3 Panel / RPC Adapter

- 将 RPC 转换为应用命令或查询；
- 区分模型调用与可信用户操作；
- 处理协议版本、输入输出 schema 和错误映射；
- 不直接读账本、配置或成员卡形成另一套视图；
- 不直接写生成文件；
- 在线和离线都使用同一个 Query Service。

### 4.4 GlobalDefinitionLibrary

- 读取内置、插件贡献和用户全局定义；
- 将全局定义复制为项目定义事件；
- 仅在 HumanAuthorizer 验证通过后写全局文件；
- 同一全局目标的写入必须串行；预期 hash 核验与定义替换位于同一互斥临界区，防止两个已确认操作互相覆盖；
- 每次全局写使用 `operationId`，先把确认摘要、目标和预期 hash 写入 `$DSH_HOME/myteam/audit/global-operations.jsonl`，再写定义并追加结果；该审计日志只记录操作，不作为定义读取源；
- 从项目发起发布时按明确状态对账：`proposed(awaiting-human)` 只是待确认意图；人类确认后进入 `authorized`（这时才形成可执行 Effect 的 `requested`），全局操作审计 intent durable 后进入 `started`，最后记录成功或失败的 `outcome`；
- Effect Runner 在启动和重试前只扫描 `authorized/started` 且缺失 `outcome` 的操作。未确认的 `proposed` 保持 pending，可过期或由授权者取消，审计缺失不会使它变成执行故障；`authorized` 但尚无全局 intent 的操作必须重新验证确认有效性与目标 hash 后才能启动；
- 对已 `started` 的操作，只有操作审计与全局文件实际 hash 都证明同一 `operationId + content hash` 已成功，才按 operationId 幂等补记结果并更新 `baseHash/lastPublication`；审计缺失、hash 不符或匹配歧义一律转为人工处理，不盲目重复发布；
- **一个 `operationId` 只写一个全局目标**。多资产发布拆成多个独立操作并分别确认、执行和对账，不承诺跨文件原子成功；汇总预览可以一起展示，但部分成功必须逐项如实呈现；
- TeamBlueprint 发布不得隐式发布其引用角色；预览必须列出引用、缺失项和版本差异，引用无法解析时阻断，实际操作的目标与内容必须与用户确认的影响面一致；
- 不记录项目清单，不保存运行态，不建立跨项目任务索引。

### 4.5 Effect Runner

负责事件提交后的外部动作：

- 创建、恢复、暂停和释放子代理；
- 投递消息与唤醒；
- 执行命令门禁；
- 生成配置、知识 Markdown、索引与导出；
- 同步 token 观测数据。

Effect 不是事件提交前的前置条件。每个 Effect 必须有事件派生的幂等键，并声明 `idempotent / reconcilable / non-idempotent` 的重试类别；结果必须回写为事件。幂等键只用于关联和去重，**不能替代外部结果核验**：

- `requested` 且没有执行开始记录，才可在权限与租约复验后启动；
- `started` 但没有 accepted/completed 时先进入 `outcome-unknown`，通过 childId、messageId、外部操作记录、Session Log、进程结果或交付物 hash 对账；
- 证明未执行才允许以同一幂等键重试，证明已成功只补记结果；无法确定时转安全验证或人工处理，不盲目重放，也不直接标成功；
- 外部系统不支持幂等或对账的非幂等操作，不得在结果未知时自动重试。

## 5. 目标代码边界与依赖方向

```text
src/
├── composition/          # DSH 装载、依赖注入、effect 生命周期
├── contracts/            # 事件、工具、RPC、错误码、schema 版本
├── application/          # 用例命令、查询、权限校验、Effect 编排
├── domain/               # 纯领域规则，不 import DSH / fs / client
│   ├── definitions/
│   ├── teams/
│   ├── members/
│   ├── tasks/
│   ├── config/
│   ├── knowledge/
│   └── permissions/
├── infrastructure/
│   ├── event-store/
│   ├── projections/
│   ├── memory-store/
│   ├── dsh/
│   ├── materializers/
│   └── migration/
└── client/               # 展示与交互，不算领域规则、不直写存储
```

依赖方向：

```text
Client / Tools / RPC
        ↓
Application → Domain
        ↓
       Ports
        ↑
Infrastructure implementations
        ↑
Composition Root 负责装配
```

约束：

- Domain 不知道 Cordis、Agent、Session、文件路径或 React；
- Application 不直接拼文件路径，也不直接调用 DSH 具体实现；
- Infrastructure 可依赖端口与领域类型，但不能反向拥有应用规则；
- Composition 是唯一知道“哪个实现配哪个端口”的地方；
- Client 不重新实现 DAG、状态机、配置合并或权限判断；
- `host.ts` 只做装配，`panel.ts` 只做协议，`member.ts` 不 import `host.ts`。

## 6. 项目事件真源

### 6.1 一个项目一个逻辑事件流

项目定义、配置、知识、团队、成员、任务、参与关系、Attempt、门禁和业务消息都进入同一项目事件日志。

这并不意味着“所有数据都放同一个文件”：

- 长期记忆是独立 SQLite 权威；
- DSH 会话与 token 原始事实由 Session Log 持有；
- 交付物正文在 project workspace；
- 全局定义由全局库持有；
- 生成文件和缓存都不是权威。

“唯一数据源”的准确含义是：**同一实体只有一个权威与写入口，而不是强行把所有外部事实复制到一个数据库。**

### 6.2 事件信封的架构字段

```text
schemaVersion       事件格式版本
eventId             全局唯一且可幂等识别
projectId           项目身份
projectSeq          项目严格递增序号
batchId/batchIndex  原子批次定位（单事件命令也视为一批）
type                领域事件类型
actor               经适配器验证的 human/captain/member/system
occurredAt          记录时间
causationId         可选：造成本事件的命令/事件
correlationId       可选：同一用例链
entity              实体类型与项目内身份
entityRevision      可选：实体乐观锁版本
configRevision      可选：本事件使用的配置版本
payload              lossless JSON 领域载荷
legacy              可选：迁移来源、原 seq/ts/type 与 hash
```

字段缺省必须是明确缺省，不能输出 `undefined`。事件持久化后不可原地修改；纠错通过新事件表达。

### 6.3 原子事件批次

一个命令需要同时改变多个实体时，使用一个原子批次。这里的“原子”指**投影可见性与恢复后的业务原子性**，不承诺底层一次 OS 写永远不会撕裂：

- 批次内事件共享 `batchId` 和整体 hash；
- 有明确的批次完整标记、事件数量和规范化 batch hash；**只有完整 commit record 通过 hash、数量和项目序号校验，才构成 durable 提交点**，调用方是否收到成功返回不改变这一事实；
- 投影只应用完整批次；恢复时发现完整有效 commit record，即使调用方崩溃前没收到成功，也必须保留并应用；
- 只有位于最后一个有效事件帧之后、连续到 EOF 且按协议不可能构成完整 commit record 的尾部字节，才可先备份隔离再作为 torn tail 截断；截断是显式修复操作并留下报告，不是正常启动的静默动作；
- 任何中间坏帧、hash/count/projectSeq 不符、commit record 后还有无法解释的数据、或无法证明损坏仅限未提交尾部的情况，都必须停止整个项目写入并转人工修复，不得截断或跳过。

跨团队任务创建、依赖重接、主责变更和批量取消都按这一边界处理。

## 7. 持久化布局与数据分类

```text
<project>/.dsh-myteam/
├── manifest.json                  # projectId、布局版本、schema 版本
├── events/
│   └── project.jsonl              # 项目唯一业务事实源
├── config/                        # 生成视图，可 review，禁止直接写
│   ├── project.config.json
│   ├── roles/<roleId>.json
│   ├── team-blueprints/<blueprintId>.json
│   └── knowledge/<entryId>.md
├── memory/
│   └── memory.db                  # 长期私有记忆的唯一真源
├── state/
│   ├── projections/               # 可重建投影与 checkpoint
│   └── writer.lock                # 写者协调，不是业务事实
├── history/                       # token、归档等历史输出，不反哺运行时
├── export/                        # 显式导出
└── scratch/                       # 临时工作区
```

### 7.1 分类规则

| 分类 | 例子 | 可否作为业务权威 | 失败处理 |
|---|---|---|---|
| 权威事实 | `events/project.jsonl`、全局定义文件、`memory.db` | ✅ | 按各自权威边界停写并显式修复；项目事件损坏时整个项目停写 |
| 生成视图 | `config/roles/*.json`、知识 Markdown | ❌ | 从权威重建并告警 |
| 派生缓存 | 看板、索引、成员卡、投影 checkpoint | ❌ | 校验血缘，失效自动重建并告警 |
| 不可变输出 | 归档、导出 | ❌ | 不反哺运行；源保留期内可再生成 |
| 外部事实 | DSH Session Log、交付物、MCP 连接 | 各自系统内 ✅ | myteam 保存引用并诚实报告不可用 |
| 协调状态 | writer lock、进程内 Effect handle | ❌ | 通过租约、对账和恢复协议处理 |

`events/` 与生成的 `config/` 可随项目 review；`memory/`、`state/`、`history/`、`export/`、`scratch/` 默认不入库。凭据不得进入任何事件或生成文件。

## 8. 配置架构

### 8.1 生效顺序

```text
平台/插件安全上限：最终钳制，业务配置不可突破

内置默认
  ← 团队创建时的项目默认快照
  ← TeamBlueprint 默认快照
  ← 团队运行覆盖事件
= 团队 Effective Config Revision
```

### 8.2 配置规则

1. 全局没有行为默认层；
2. 项目默认是项目定义事件，修改后影响之后创建的团队；
3. 既有团队采用新项目默认必须显式 rebase，并生成团队配置事件与差异；rebase 必须携带 `expectedConfigRevision`，若与并发团队覆盖冲突则拒绝，读取最新差异后重试，不自动合并；
4. 蓝图默认在创建团队时固化，不随后续蓝图编辑自动改变；
5. 团队运行覆盖只通过事件修改，不写另一份独立权威文件；
6. 数组合并、字段校验、安全上限和未知键兼容策略由同一领域模块定义，Schema 与运行时共用语义；
7. 团队创建及每次有效配置变化都生成一个不可变、规范化的 **Effective Config Snapshot**，其中包含完整生效值、合并算法版本、安全上限版本和内容 hash；`configRevision` 必须能在项目事件中解析到该快照，不能只指向当前生成文件；
8. **cutover 后新产生的**、行为依赖配置的任务事件、Attempt、门禁与 Effect 请求都**必须**携带 `configRevision`；信封对纯消息等无关事件才允许缺省。迁移历史事件无法证明当时配置时按迁移蓝图显式标为不可考，不为满足形状而伪造 revision；
9. 新认领的 Attempt 使用认领时的最新 revision；进行中的 Attempt 继续绑定开始时的 revision，不被中途切换；新配置只影响后续新 Attempt 和新命令；
10. 已排队 Effect 保留请求时的 revision，但执行前必须重新校验最新安全上限、权限、Captain generation 和写者租约；不再合法时明确取消或转人工，不偷偷换配置执行；
11. 配置变化不追溯改写历史，也不自动取消在途 Attempt；安全上限收紧只阻止新的不合法动作，破坏性清理由用户另行确认；
12. `config/project.config.json` 与生效配置输出都是生成视图，手工改动不会被当成新配置。

## 9. 统一写入与读取

### 9.1 命令写路径

```text
Adapter 验证调用身份与项目绑定
  → Application 解析命令、权限与目标 revision
  → 获取/验证项目写者租约和 fencing token
  → 读取必要尾部并核对投影
  → Domain 校验不变量、DAG、状态机、配额与 Attempt
  → 在隔离副本上试应用完整批次
  → append + fsync 原子事件批次
  → 切换内存投影与 project revision
  → 发布变更并调度 Effect
  → Effect 结果另写事件
```

任一 durable 前失败都不执行副作用，也不改变当前投影。durable 后的 Effect 失败不能伪装成命令未提交。

### 9.2 并发前置条件

项目写者提供串行化，但业务命令还必须声明自己基于什么状态：

- 所有命令在写者内都以最新 projectSeq 重新核对投影，不能只相信 Adapter 读到的旧快照；
- DAG 创建、修改、重接和取消必须携带 `expectedGraphRevision` 及涉及实体的 `entityRevision`；`graphRevision` 只随图结构变化递增，避免无关消息造成全项目冲突；
- 团队/成员命令必须携带对应 `entityRevision`，队长命令还必须携带当前 Captain generation；
- 配置修改与 rebase 必须携带 `expectedConfigRevision`；
- Attempt 的进度、证据和完成必须携带当前 `attemptId` 与 generation；
- `entityRevision` 在通用事件信封中可缺省，是因为批次可跨多个实体；对上述命令类别，前置条件不是可选的；
- 前置条件不匹配时拒绝并返回当前 revision。DAG、配置、handoff 等冲突不得自动合并，调用方必须重读、重建意图后显式重试；真正不冲突的命令可在最新投影上校验，不做无意义的全项目冲突。

### 9.3 查询路径

- 热路径读取统一内存投影；
- 冷启动由事件与合法 checkpoint 恢复；
- 磁盘缓存只在 `derivedFrom` 与当前 project revision 匹配时作为加速读面；
- 缓存缺失、损坏或过期时从权威事件自动重建并告警；重建必须同时校验事件帧、批次 hash、数量和 projectSeq，不能把源错误当成普通缓存错误；
- 只有证明是 cache-only 的损坏或写失败，才可回退到完整权威投影并继续；重建中出现权威日志损坏、不可读或原因无法区分时，**整个项目的业务写入与 Effect 全部停止**，所有团队都不能继续基于不完整事实提交；
- 源完整性未确认前只能返回带 `observedProjectSeq` 和损坏告警的最后已知视图，不能返回看似正常的空看板或最新状态；
- 在线与离线面板走相同 Query Service；
- 未取得写者租约的进程进行强一致读时，必须转发给当前写者或先核对权威日志尾部；返回视图携带 `observedProjectSeq`，不能把本地旧投影说成最新；
- 读操作可以触发显式重建，但不能顺手迁移权威事件。

### 9.4 项目写者与团队队长是两种锁

**项目写者**防物理分叉：

- Root Host 内按 projectId 单写；
- 跨进程通过 writer lease + fencing token；
- 每次追加都验证租约和最新 projectSeq；
- **fencing generation 的单调生成、最新 projectSeq 核验和事件追加必须处于同一互斥临界区，或由唯一写入通道顺序执行**；“先检查、离开锁后再追加”不成立；
- 未取得租约的进程只读或转发。

**Captain Assignment**防业务指令冲突：

- 一个团队同时只有一个队长任期；
- Captain 可以提出 handoff，Human 必须显式确认后才会推进 captain generation；旧队长是否在线不影响这一授权要求，旧队长同意也不能替代用户确认；
- handoff 后旧队长的后续命令因 generation 陈旧而被拒；
- 项目写者不能替代队长任期，队长在线也不能替代项目写者。

## 10. 任务、成员与副作用

### 10.1 项目任务 DAG

- 任务直接归项目，主责团队一个，协作团队可为多个；
- 任务正文、AC、交付要求和主责指派由主责团队 Captain 管理；协作团队只能处理本团队获授权的执行子集或提出修改提案，Human 可介入；
- 依赖引用项目 `taskId`，允许跨团队；依赖边归**下游任务**（发起依赖的一方）所有，其主责 Captain 可增删本任务的依赖，上游团队通过项目事件获知影响，不需要双写或双方账本；
- 主责团队变更需要原主责与接收主责双方 Captain 确认，或由 Human 裁决；协作关系退出前必须处理本团队仍在运行的 Attempt；
- 创建、修改、重接和取消都进行全项目防环与引用校验；
- 任务认领要求成员属于合法参与团队，并满足角色、状态、配置和 Attempt 约束；
- 跨团队图修改是一个项目原子批次，不写“主责团队账本 + 协作团队副本”；
- 看板、列表、流程图、依赖图与统计都来自同一项目投影。

### 10.2 成员与子代理

- Member 是项目事件中的聘任与运行关系，DSH subagent 是执行载体；
- 优先使用 DSH `subagents`；兼容回退只存在于 infrastructure adapter；
- 子代理 preset 必须显式指定，防止继承队长工具面；
- 父子成员在同一团队，能力只收窄，深度和子数受配置与安全上限约束；
- 成员会话可以被释放，Member 与 Memory 不随 live handle 消失；
- 队长离线时允许成员提交合法事实，但暂停新的派遣与生命周期 Effect。

### 10.3 Effect 状态语义

```text
requested  → accepted  → completed
    │            │          │
    │            │          └─ 外部动作已产生可核验结果
    │            └─ 外部系统已受理，例如 inbox messageId
    └─ myteam 事件已 durable，准备执行

failed / blocked / cancelled 均与 accepted 分开记录
```

消息 `sent` 不能代表 consumed，子代理 live handle 存在不能代表 Effect 已完成，任务完成不能只看成员一句文本声明。

### 10.4 队长离线与成员会话恢复

**队长可用性**由 Captain Adapter 的注册就绪状态和 DSH Agent/Session 生命周期观测共同判定，属于运行时协调事实，不另建业务权威。恢复在线只能是原 Captain Assignment 对应会话重新就绪，或经 Human 确认完成 handoff。

队长离线期间：

- 新的任务分派、新 Attempt 认领、成员 spawn/resume/release 等生命周期命令在 durable 前明确拒绝，不先把看板写成已派单；Human 的紧急停止不受此限制；
- 已经 durable 的相关 Effect 保持 `pending + captainOffline`，不得显示为 delivered 或 in_progress；
- 已开始 Attempt 的成员可继续提交进度、证据和 escalate，但不能开始新的 Attempt；已激活成员之间的必要协调消息按原权限持久化和投递；
- 队长恢复后，逐项复验 pending Effect 的任务状态、Attempt、configRevision、Captain generation 和项目写者租约；已过期或不再合法的请求记录取消/失效结果，不能原样盲放。

成员会话失效时：

- 活跃 Attempt 立即失效并记录 `attempt.revoked(reason=session-lost)`；已提交证据保留，旧 attemptId 的后续写入一律拒绝，恢复后必须创建新的 attempt generation；
- 若原 SessionRef 能精确恢复，必须核验 team/member 绑定、Captain generation、member preset、原 roleRevision 以及不存在另一个 live 执行体，之后才能建立新的 Attempt；
- 若原 SessionRef 不能恢复，只有证明旧会话不可用或已 dispose、没有重复 live 执行体后，才能以原 `teamId + memberId` 创建新的子代理 SessionRef，并追加包含旧/新 sessionId、当前 Captain generation、原 roleRevision 和 `memberSessionGeneration + 1` 的绑定事件；
- 不得仅凭相同名字、instanceName 或 cwd 把新会话认成原 Member；成员私有 memory bank 不变，旧 memberSessionGeneration 的消息和写入不得进入新任期。

## 11. 知识与记忆

### 11.1 Knowledge

- 知识提案、采纳、正文、证据、修订与矛盾关系都进入项目事件；
- Captain 可采纳，Member 可提案，Human 可介入；
- `config/knowledge/*.md` 是生成的人读视图；
- 生成失败只表示派生物过期，不改变已提交的知识事实；
- 提示词索引由当前知识投影生成，条目按需读取，避免全文倾倒；
- 修订通过新事件完成，旧断言与演化历史不可被静默覆盖。

### 11.2 Memory

- `memory.db` 是项目内团队/成员长期记忆的唯一权威；
- bank 至少区分 `team:<teamId>` 与 `member:<teamId>:<memberId>`；
- remember/recall/forget 都验证调用者对 bank 的所有权；
- evidence 必填，修订采用 supersedes + 软归档；
- SQLite 不与项目事件互写副本；需要关联时只保存 task/event/session 引用；
- 旧 `memory.md` 只用于一次性迁移或用户显式导出，不参与正常召回；
- 成员文件记忆目录被删除时，SQLite bank 不得被隐式连带删除。

## 12. DSH 与交付物边界

### 12.1 Session Log

DSH Session Log 是模型可见消息、工具调用、模型输出和原始 token 使用事实的权威。myteam：

- 保存 `sessionId`、必要的 `sessionSeq` 与子代理关系引用；
- 不用自建账本重放模型上下文；
- 不新增破坏 Session 重开兼容性的事件类型；
- 需要会话投影时使用宿主支持的 projection 能力；
- token 侧车只是观测输出，不用于决定业务任务是否完成。

### 12.2 交付物

交付物正文在项目工作区，事件只保存：

- 路径与必要的绝对/相对根语义；
- 内容 hash 与产生者；
- 验证命令、退出码和结构化证据；
- 对应 task/attempt/config revision；
- 归档或导出位置。

交付物路径必须显式相对项目根或声明的另一个根，成员不能靠会话 cwd 猜测。

## 13. 故障与恢复矩阵

| 场景 | 系统行为 |
|---|---|
| 权威事件日志损坏 | 停止整个项目业务写入与 Effect；指出位置与修复入口；只提供带水位的损坏视图 |
| 派生缓存损坏/过期 | 从权威重建并校验源完整性；只有 cache-only 故障允许降级，源损坏或原因不明按上行处理 |
| 写者租约失效 | 拒绝追加与 Effect；重新取得租约并核对尾部后才能继续 |
| 第二队长接管 | 必须经 Human 确认 handoff；旧 generation 的命令全部拒绝 |
| 队长离线 | 新派遣/新 Attempt/生命周期命令 durable 前拒绝；已有相关 Effect 标 pending；进行中的合法提交允许 |
| 成员会话冷/被释放 | 原 Attempt 失效；精确核验原 SessionRef 或显式换绑新 generation 后新建 Attempt；记忆 bank 不变 |
| 陈旧 Attempt | 拒绝进度、证据与完成写入，不产生部分事件 |
| Effect 结果未知 | 先按外部 id/Session Log/产物对账；证明未执行才重试，证明成功只补结果，不确定不盲放也不伪成功 |
| 生成配置/Markdown 失败 | 保留已提交事实，标派生物过期并重建 |
| 全局发布失败 | 项目定义不变；全局不产生半写文件；返回明确失败 |
| 迁移发现未知事件/引用 | 阻断 cutover，输出具体清单，不静默跳过 |

## 14. 性能与演化边界

初版继续使用 append-only JSONL，而不是为了“重写”无谓更换数据库：

- 热查询使用项目内存投影；
- checkpoint 只用于减少冷启动重放；
- 所有批量查询由统一投影产生，不在 UI 重算；
- 保留 EventStore 端口，使未来可替换物理实现而不改变领域语义。

出现实测触发条件时再评估 SQLite 或其他 EventStore：例如大项目下 p95 提交延迟、冷启动恢复或审计区间查询已不满足明确指标。不得以旧文档中的理论数字代替本项目测量，也不允许新旧存储长期双写。

## 15. 架构验收场景

1. 两个团队并行工作，项目看板完整显示双方任务与状态。
2. 团队 A 的任务依赖团队 B 的任务；全项目防环、解锁、取消与重接结果一致。
3. 两个 captain 会话指向同一团队时，第二会话不能静默接管；旧 generation 写入失败。
4. 两个进程尝试写同一项目时，只有一个有效 fencing generation 能追加。
5. 队长离线后，成员已开始的合法提交仍可持久化，新派遣 durable 前失败；恢复后 pending Effect 逐项复验，过期项不得执行。
6. Agent 直接调用全局写路径、伪造 `actor:'human'` 或重放确认令牌均被拒绝。
7. 成员尝试归档其他成员或其他团队的 memory entry 时被拒绝。
8. 删除全部派生缓存后，看板、配置与知识视图重建结果与权威重放一致；重建时源损坏必须停止整个项目写入。
9. 手工修改生成的配置文件不会改变系统行为，随后被识别并重建。
10. 在事件提交前后、Effect 执行前后分别注入崩溃：完整 commit record 不丢，只有可证明的未提交尾部可修复，结果未知的 Effect 不盲放也不伪成功。
11. 成员原 SessionRef 失效后，旧 Attempt 写入被拒绝；换绑错误名字/cwd 不被接受，新 SessionRef 只能以新 generation 创建新 Attempt。
12. 旧团队账本迁移后，任务/依赖/成员/会话绑定与旧投影对账一致，来源 hash 可追溯；旧在途 Attempt 不得直接沿用，旧 Effect 不得因导入重放。
13. DSH Web 真机中，队长/成员/面板使用同一 Runtime，成员无 Lead 工具泄漏，核心链路可完成。

## 16. 下一阶段拆分

架构书面评审通过后，按以下顺序编写功能实现设计，而不是直接改代码：

1. 定义库、复制与全局发布；
2. 建队、Captain Assignment、成员与生命周期；
