## 1. 目标与完成定义

目标不是继续修补旧 Host，也不是把旧文档换目录，而是完成一个可独立理解、运行、迁移和验收的 v2 系统。

完成时必须同时成立：

1. 现行 product/architecture 中的全部 v2 能力已经在代码中实现；
2. 旧 Runtime、工具/RPC、事件和旧 UI 不再参与生产运行；
3. 旧数据经过显式、可验证的一次性迁移，异常和索引孤儿已由用户确认；
4. DSH Web 核心场景、完整测试、权限负面对抗和仓库门禁通过；
5. 新文档独立覆盖理解、安装、使用、配置、契约、迁移、恢复与验收；
6. 删除 `historical/`、as-is v1 契约和被替代的旧审计后，系统与文档仍完整，全部检查继续通过。

**最终成功不是“历史被删除”，而是“历史已经没有必要存在”。**

## 2. 已确认的边界决策

| 编号 | 决策 |
|---|---|
| R-01 | 彻底 v2，只保留一次性数据迁移，不维护长期 v1 兼容适配器 |
| R-02 | 功能范围以现行 product/architecture 为准，不逐项平移旧 PRD 和旧页面 |
| R-03 | 在隔离 worktree 中建立全新 v2 源码树，按垂直切片交付，最终整体替换旧实现 |
| R-04 | `migration/v1` 只负责读取旧格式，不是 v1 Runtime；它可长期保留且拥有自包含文档 |
| R-05 | 索引孤儿只报告、不伪造；真实异常必须进入迁移影响面并由用户确认 |
| R-06 | 历史文档只有在 v2 实现、迁移、文档和真机验收全部完成后才删除 |
| R-07 | 旧数据备份与历史文档分开处理，旧数据不随文档自动删除 |
| R-08 | `design-v2/` 的既有未提交改动留在原工作区，不纳入重构提交 |
| R-09 | 先书面设计和详细计划，再创建 worktree 写代码；真实 cutover 和历史删除另行确认 |

## 3. 实施路径选择

### 3.1 选择：隔离工作区 + 全新源码树 + 垂直切片

从当前 HEAD 创建 `complete-v2-rewrite` worktree，旧实现只留在 Git 历史和迁移读取器中。按契约、领域、基础设施、应用用例、DSH 适配器、面板、迁移和清理逐阶段构建，每阶段都有独立测试和提交。

这不是长期双版本：

- 新旧 Runtime 不双写；
- v2 不导入旧 Host、旧 TeamService 或旧客户端；
- v1 只作为迁移输入和 Git 历史存在；
- 最终主分支只保留 v2 与迁移读取器。

### 3.2 不采用的方案

- **一次性全部删除再重写**：长时间没有可运行出口，契约、迁移和真机风险集中到最后；
- **保留旧 Host 逐步换内核**：旧 `host.ts / panel.ts / TeamService` 继续决定系统边界，无法完成真正的替换；
- **长期 v1 适配层**：旧工具、RPC、文档和测试必须继续维护，与“历史可删除”冲突；
- **旧功能逐项平移**：把已被新架构淘汰的范围重新变成依赖，扩大重写而没有架构收益。

## 4. 当前基线与真实迁移输入

### 4.1 代码基线（重写前，v1 —— 历史输入）

> 这一节记的是**动工前**的基线，用来解释为什么要重写。R0～R7 已完成，现行树是 62 模块五层
> （`contracts / domain / application / infrastructure / composition`），见 [00 §3](00-现状与决策基线.md)。
> 下面提到的 `host.ts` / `panel.ts` 等文件在现行树里已不存在。

动手前的基线为 `main@115d5c3`，插件约有 83 个源码模块、28,836 行源码；`host.ts` 4,375 行、`panel.ts` 1,459 行。主要结构问题包括：

- 业务 Host 属于 captain preset，不能形成项目级单写者；
- 成员工具通过 parentSession 寻找队长服务，并反向依赖入口 Host；
- 团队分账本与项目级任务/跨团队 DAG 目标冲突；
- 配置、知识、成员卡、身份快照和索引存在多份权威与非原子写；
- 面板在线/离线存在多条读写路径；
- 旧文件记忆与 SQLite 双记忆面并存；
- Lead 确认参数不能构成可信人类授权。

这些问题不能靠继续追加工具或缩短单个文件解决。

## 5. 最终代码架构

```text
plugin/src/
├── composition/          # DSH 装载、Root Runtime、Captain/Member/Panel 装配
├── contracts/            # v2 事件、工具、RPC、Schema、错误码
├── application/          # 用例命令、查询、权限、Effect 编排
├── domain/
│   ├── definitions/      # Role / WorkflowDefinition / TeamBlueprint
│   ├── teams/
│   ├── members/
│   ├── workflows/        # WorkflowRun，不复制 Task 状态
│   ├── tasks/
│   ├── config/
│   ├── knowledge/
│   └── permissions/
├── infrastructure/
│   ├── event-store/
│   ├── projections/
│   ├── memory-store/
│   ├── dsh/
│   ├── materializers/
│   └── migration/v1/     # 只读旧格式，不是 v1 Runtime 兼容层
└── client/               # 只消费 v2 RPC，不计算领域规则
```

### 5.1 依赖方向

```text
Client / Tools / RPC
        ↓
Application → Domain
        ↓
       Ports
        ↑
Infrastructure implementations
        ↑
Composition Root 负责装配
```

### 5.2 强制边界

- Domain 不知道 Cordis、Agent、Session、文件系统或 UI；
- Application 不直接拼路径或调用 DSH 具体实现；
- `host.ts` 只做宿主装配，不再承担业务入口集合；
- `member.ts` 不 import `host.ts`，只通过 Root Runtime 调用；
- `panel.ts` 只做 RPC、协议版本与可信用户操作，不维护另一套离线状态机；
- Captain、Member、Panel 使用同一个项目 Runtime；
- v1 工具、RPC、事件格式不进入 v2 命名空间；
- `migration/v1` 可以读取旧文件，但不得反向成为 v2 的运行依赖。

## 6. v2 功能范围

### 6.1 定义资产

- RoleDefinition = RoleProfile + CapabilitySet；
- CapabilitySet 只保存 Tool/MCP 权限与 SkillRef；
- WorkflowDefinition 包含 TaskTemplate、初始依赖、角色要求、门禁和完成条件；
- TeamBlueprint 只保存 Role/Workflow 引用和默认配置；
- 全局资产复制到项目后才能实例化，origin/baseHash/contentHash 可追踪；
- 全局写只有 Human 确认，发布请求与授权分离。

### 6.2 团队与成员

- 一个项目允许多个团队；
- Captain Assignment 防止旧队长继续发指令；
- Member 使用 DSH subagent，RoleSnapshot 在聘任时固化；
- 父子成员能力只收窄，组织委派与普通工具授权分开；
- 队长离线时，进行中的合法成员事实可持久化，新派遣与生命周期 Effect 暂停；
- SessionRef 失效后旧 Attempt 失效，新会话必须显式换绑 generation。

### 6.3 Workflow 与项目任务

- WorkflowRun 仅属于项目，复用统一 Task DAG；
- 单成员、跨成员、跨团队只是参与拓扑；
- 一个 Task 最多归属一个 Run，跨 Run 通过依赖协作；
- 动态增删任务、重接依赖和重分配使用项目原子批次、graphRevision 和全项目防环；
- 完成规则变化生成 completionRevision；
- Attempt、门禁、证据和交付物不复制进 WorkflowRun 状态。

### 6.4 配置、知识与记忆

- 配置由项目默认快照、蓝图默认和团队覆盖生成不可变 Effective Config Snapshot；
- 进行中的 Attempt 绑定开始时 configRevision，已排队 Effect 执行前复验安全约束；
- 知识提案、采纳、正文、证据和修订进入项目事件，Markdown 为生成视图；
- SQLite 是长期记忆唯一权威，严格校验 bank 所有权；
- DSH Session Log 是模型执行事实权威，myteam 只保存引用。

### 6.5 面板与迁移

v2 面板覆盖项目看板、团队、Workflow、定义库、知识/记忆、配置和迁移。它只消费 v2 RPC，不重新实现 DAG、配置合并或权限判断。

明确不逐项移植：旧单角色调用、27 屏 UI、旧归档回放、旧 token 侧车、旧动态工具创建及其他未进入现行 product/architecture 的功能。

## 7. 数据与副作用架构

- 项目定义、配置、知识和运行事实统一进入 `events/project.jsonl`；
- `config/` 是生成视图，不直接接受写入；
- 项目只有一个逻辑写者，跨进程使用租约与 fencing；
- DAG、配置和实体操作使用对应 revision 前置条件；
- 原子批次以完整 commit record 为提交点，不完整或不可证明的尾部不得静默截断；
- Effect 在事件 durable 后执行，按幂等性与可对账性分类；
- `requested / accepted / completed` 分离，结果未知不盲放、不伪造成功；
- 缓存可作加速读面，权威损坏或原因不明时整个项目停止业务写入；
- 全局写使用 operationId、目标 hash、Human 确认和独立操作审计。

## 8. 一次性迁移设计

### 8.1 支持输入

1. `.team-workplace/`；
2. `.dsh-myteam/tasks/<teamId>/ledger.jsonl`；
3. `.dsh-myteam/state/teams/<teamId>/ledger.jsonl`；
4. 角色、团队模板、配置、知识、SQLite、memory.md、identity 和成员卡；
5. 全局角色与旧全局团队格式；
6. 可验证的 DSH Session Log 引用（若可用）。

### 8.2 流程

```text
Analyze（只读）
  → Import Candidate（候选 v2，不写旧文件）
  → Verify（投影、引用、hash 全量对账）
  → 用户审阅影响面并确认 cutover
  → v2 成为唯一写者
  → 旧数据保留独立只读备份
```

候选导入不得启动 Effect、spawn 或消息投递。若先在快照上分析，cutover 前必须停止旧写并对增量重新分析和验证。

### 8.3 实体规则

- 多团队旧账本按 `(ts, teamId, seq, sourceLine)` 形成可重复的迁移顺序，并标记为合成顺序；
- 旧任务 id 重映射为项目唯一 id，所有依赖、Attempt、证据和消息引用同步更新；
- 原 sessionId 保留，但旧 Attempt 全部失效，继续工作必须新 claim；
- 角色映射为 RoleProfile + CapabilitySet；
- 只有旧 `taskPlanning:'template'` 的明确线性规则可转换为 WorkflowDefinition；
- 既有任务可以不属于 WorkflowRun，不按 teamId 或标题伪造；
- 当前配置可计算为迁移快照，历史配置不可考时明确缺省；
- 知识正文与证据进入项目事件；
- SQLite 独立备份迁移，memory.md 一次性去重导入；
- 未完成 Effect 不自动重放，结果未知先对账；
- 全局库不自动改写，必须生成转换预览并经 Human 确认。

### 8.4 索引孤儿与异常

- 没有账本的 active index 条目不得创建 active 团队或任务；
- 名称、目标、计数等只写入迁移报告；
- 重复规则事件保留源行并只初始化一次；
- 无法证明的字段不填假默认值；
- 索引孤儿、重复事件和不可考项必须进入 cutover 影响面，由用户明确确认。

### 8.5 回滚

- cutover 前可删除候选输出，旧系统不变；
- cutover 后没有新写时可由管理员明确切回；
- cutover 后已有新写时不做自动反向回滚，只能向前导出和修复；
- SQLite 或投影对账失败禁止 cutover；
- 代码 Git 回滚不等于业务数据回滚。

## 9. 历史删除门禁

只有全部满足以下条件才执行历史清理：

1. v2 全部功能契约、实现和测试完成；
2. DSH Web 核心场景、权限负面对抗与恢复测试通过；
3. 实际旧数据迁移完成，索引孤儿和异常已由用户确认；
4. 新文档覆盖理解、安装、使用、配置、工具/RPC、事件、迁移、恢复和验收；
5. `contracts/` 中只有 v2 与自包含迁移契约；
6. `historical/` 的有效信息已提炼或明确判定不再适用；
7. 新 v2 验收报告已经产生，旧 v1 审计不再承担现行证明；
8. 除 `migration/v1` 外，代码不再依赖旧实现或旧文档；
9. 删除后重新运行完整测试、生成器、文档链接和全部仓库门禁。

最后清理对象：

- `docs/historical/`；
- as-is v1 API、配置和贡献契约；
- 被 v2 验收替代的旧审计资料；
- 旧 Runtime、旧测试和不再使用的辅助资产。

旧数据备份不随文档删除，只有用户另行确认才清理。

## 13. DSH 宿主约束

当前安装版本已通过运行时 Inspect 复核：

- `subagents.startActivation` 支持 childId、agentPreset、agentOptions，返回 Activation 与消息受理信息；
- `subagents.sendMessage` 返回 inbox acceptance，不代表消息已消费；
- `agents` 支持 create/resume 和 live Agent 查询；
- `agentPresets` 支持 preset mount、serviceFor 与隔离组合查询；
- `tools` 支持注册、restrict、schema、execute 与 guard；
- `sessionProjections` 支持受控投影、checkpoint 和恢复，不新增自定义 Session 事件类型；
- `commands` 是当前安装版本的 Human-command registry，Remote `execute` 直接调用已注册 handler、不会把命令发送给模型，并记录 `command/run` 与 `command/done`；可作为显式用户操作通道；
- `actionCards` 提供 Remote `act(agent, callId, verb, payload)`，裁决绑定已记录的 propose_action callId，同一卡片的并发操作被串行化；可承载计划批准、全局发布和队长接管等用户裁决卡；
- `commands` 与 `actionCards` 只提供用户入口，不自动证明任意写操作已获授权。v2 仍须绑定 operationId、目标内容 hash、影响面、过期时间与一次性 nonce，并在服务端复验；普通工具参数中的 `actor:'human'` 或 `confirm:true` 不被接受。

兼容回退只能存在于 DSH infrastructure adapter，不进入领域模型。

## 14. 风险与控制

| 风险 | 控制 |
|---|---|
| 重写范围过大导致长期无出口 | 垂直切片、每阶段独立提交与测试 |
| 旧测试绑定旧架构 | 只保留行为 fixtures，新测试围绕 v2 契约编写 |
| 索引孤儿被误迁移 | 只报告、不伪造，用户确认影响面 |
| 新旧双写 | cutover 前候选只读，cutover 后只有 v2 写者 |
| 面板再次长业务逻辑 | Client 只消费 v2 RPC，架构门禁限制依赖方向 |
| 真机与测试桩语义不同 | DSH 集成和 Web 真机分别验收 |
| 历史过早删除 | 历史清理放在最后，并重新跑全部门禁 |
| 原工作区其他改动被混入 | 独立 worktree，逐文件暂存和最终 diff 审查 |
