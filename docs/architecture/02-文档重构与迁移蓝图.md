# 02 · 文档重构与迁移蓝图

> 状态：`proposed`（四段设计已获用户逐段确认，待整本文档评审）
> 上游文档：[00-现状与决策基线](00-现状与决策基线.md) · [01-系统架构](01-系统架构.md)
> 本轮范围：文档落地与后续施工蓝图；不执行代码改写或用户数据迁移。

## 1. 文档重构目标

旧文档的问题不是数量太少，而是：

- 多份文件同时自称同一事项的“唯一权威”；
- 目标、现行设计、草案、历史实施和真机记录混写；
- 新决策只追加在后文，旧决策没有显式 superseded；
- 工具数、事件数、目录和状态在多处手工复制；
- 导航先把读者带进 API 和历史需求，而不是先讲系统边界。

本次重构遵循：

> **先架构，再功能实现设计，再契约与代码；历史保留，但历史不得继续冒充现行权威。**

## 2. 文档生命周期与权威规则

### 2.1 六种状态/轨道

| 状态 | 含义 | 能否指导新实现 |
|---|---|---|
| `proposed` | 已提出，正在评审 | 只能作为评审对象，不能作为施工承诺 |
| `accepted` | 已完成评审，是当前有效目标设计 | ✅ |
| `as-is v1` | 当前旧实现的契约，用于兼容和迁移 | 仅旧 Runtime；不能当目标设计 |
| `superseded` | 已被指定的新文档/ADR 替代 | 仅理解决策演化 |
| `historical` | 某时点的实现、审计、验收或研究记录 | 仅作证据，不反推当前架构 |
| `generated` | 由代码、schema 或事件定义生成 | ✅，但只能改生成源 |

每份主干文档头部必须标状态；被替代时写明 `supersededBy`，替代者写明 `supersedes`。禁止再使用“定稿草案”“待定案但唯一权威”这类自相矛盾的状态。

### 2.2 权威分层

```text
用户已确认的目标与原则
  ↓
accepted 系统架构与 ADR
  ↓
accepted 功能实现设计
  ↓
contracts / generated schema 与代码实现
  ↓
测试、真机验收与 historical 证据
```

- 代码事实与设计不一致时，不能悄悄选一边：若是实现偏差则修实现，若是设计变更则先评审并更新设计。
- 调研、审计与旧验收报告不能反向改变架构。
- 工具数、RPC 数、事件数、错误码和 schema 从代码生成，不在多份 Markdown 中手工维护。
- 当前测试是否通过只认本次可复现命令结果，不引用旧会话数字冒充当前结果。

## 5. 旧数据迁移总原则

迁移是**显式、可验证、单方向切换**：

```text
analyze（只读）
  → import（生成候选新日志，不改旧文件）
  → verify（投影与引用对账）
  → 用户确认 cutover
  → 新 Runtime 成为唯一写者
  → 旧布局保留只读备份
```

禁止：

- 启动时无提示地把旧账本改成新格式；
- 新旧 Runtime 同时接受写入；
- 为追求“迁移成功”而静默丢弃未知事件；
- 用当前角色/配置伪造过去不可考的历史版本；
- 让旧索引、成员卡或 identity 覆盖账本事实；
- 自动改写用户全局库。

## 7. 事件顺序、id 与历史真实性

### 7.1 多团队旧账本顺序

旧系统没有项目全局 seq。迁移按 `(ts, teamId, seq, sourceLine)` 形成确定顺序，并写入：

- 原 teamId、seq、ts、type 和源文件行号 sourceLine；
- 新 projectSeq；
- 源文件与源文件 hash；
- `ordering:'synthesized-at-migration'`。

该顺序只用于可重复迁移，不声称它是原始跨团队真实时序。

### 7.2 id 重映射

- 旧 `teamId` 在项目中保留；
- 旧任务 id 只在团队内唯一，因此生成项目唯一的新 `taskId`；
- 每条任务保存 `legacyId:{teamId,taskId}`；
- deps、参与关系、Attempt、证据、消息和门禁中的任务引用统一重映射；
- member 采用 `teamId + memberId` 复合身份；
- 原 `sessionId` 保持不变，重建 Captain/Member 与 DSH 会话的绑定；
- 所有映射写入迁移报告，不能只存在于一次性脚本内存。

### 7.3 历史配置与角色

- 能由旧事件和有效快照证明的内容按证据导入；
- 只有当前角色文件时，标记为“迁移时当前定义”，不虚构历史 revision；
- 只有当前团队配置时，导入为迁移快照，历史事件不补写虚假的 configRevision；
- 每个旧团队都导入一份**迁移时实际 effective config 快照**（内置默认、项目层、团队层与安全上限的合并结果），同时保留可证明的原始层来源，避免 cutover 后新项目默认改变旧团队行为；
- 该快照必须使用旧实现对应的合并算法、内置默认和安全上限实际计算，并记录算法版本、各输入 hash 与计算结果；无法确定旧算法或输入时列为阻断项，不靠人工猜默认值补齐；
- 无法证明的历史字段保留缺省并进入迁移说明，而不是填一个看似完整的默认值；迁移时的“当前可计算”与历史上的“当时可证明”必须分开；
- **legacy 不可考是新事件强制携带 `configRevision` 的明确例外**：迁移快照只供 cutover 后的新 Attempt、新命令和新 Effect 使用，不回绑旧 Attempt、旧门禁或旧任务事件；历史视图必须显示“配置不可考”，不能显示成迁移快照就是当时配置。

### 7.4 在途 Attempt、Effect 与队长任期

- Analyze 必须单列所有未终态 Attempt、未收到终态结果的 Effect、活跃 Captain/Member 会话和可能仍在运行的外部进程，纳入 cutover 影响面；
- 旧 Runtime 停止前仍在执行的 Attempt 必须明确结束、撤销或标记 `requires-new-attempt`；cutover 后旧 attemptId 进入失效集合，任何旧进度/证据/完成写入都不能直接进入新 Runtime，已有历史证据仍保留；
- 未完成任务需要继续时，在成员与队长绑定恢复后创建新的 attempt generation；不得把旧 claim 当成仍然有效的执行授权；
- 旧 spawn、消息、命令门禁等未完成 Effect 不得因导入自动执行。能证明未执行的可在复验后重新发起，能证明成功的只保留结果，结果未知的转对账或人工处理；
- 新 Captain Assignment 使用新的 migration generation，旧 Runtime 的 Captain generation 与写者租约均无效；原 sessionId 只有通过当前 preset、team/member、roleRevision 和无重复执行体校验后才能重新绑定；
- 无法证明旧外部执行体已经停止、或其结果已经可以安全对账时，阻断 cutover，不能靠“切换 manifest”掩盖仍在运行的旧工作。

### 7.5 WorkflowDefinition / WorkflowRun

- 旧 `pipeline.stages` 若只用于看板、泳道或布局，继续作为配置，不转换成 Workflow；
- 只有旧 `taskPlanning:'template'` 明确以 stages 生成线性任务时，才生成带 `origin:'legacy-task-planning'` 的 WorkflowDefinition，并保存原始输入 hash 和 templateKey 映射；
- 既有旧任务可以不属于任何 WorkflowRun，不得按 teamId、标题或显示顺序猜测并伪造 Run；
- 用户若显式选择把旧任务归入 Run，必须单独确认完成条件并生成映射事件，不能修改历史任务事件；
- 新 WorkflowRun 继续使用项目统一 taskId、graphRevision 和依赖映射，不建立迁移专用任务引擎。

## 8. 迁移步骤与门禁

### M0 · 冻结基线

- 记录源布局、代码版本、插件版本与文件 hash；
- 暂停旧 Runtime 写入，或由迁移工具在只读快照上工作；若先在快照上分析，cutover 前仍必须停止旧写，并对快照后的增量重新分析、导入和验证，不能直接切换旧快照；
- 不修改源文件。

**出口**：输入清单完整，包含隐藏文件、SQLite WAL 相关文件和旧布局。

### M1 · Analyze

- 识别每个团队、事件类型、任务、成员、配置、知识和记忆；
- 输出未知事件、坏行、重复 seq、引用缺失、id 冲突、会话绑定和源 hash；
- 区分阻断项与可保留告警。

**出口**：报告可重复生成；任何未知事件都不能被“成功”吞掉。

### M2 · Import Candidate

- 生成候选 `project.jsonl` 与独立 SQLite 迁移结果；
- 旧目录保持不变；
- 生成角色/蓝图/知识生成视图和 id 映射；
- 不启动 Effect，不 spawn，不发消息。

**出口**：候选输出可确定性重建；相同输入产生相同业务内容。

### M3 · Verify

至少比较：

- 团队数、成员数、任务数和各状态数量；
- 任务输入、依赖、参与关系、Attempt 与门禁；
- 角色引用与配置快照；
- 知识正文和证据；
- memory bank 归属与条目数；
- `sessionId` 绑定；
- 旧投影与迁移后投影在声明兼容字段上的等价性。

**出口**：阻断项为零；告警逐项有解释；用户看到完整影响面。

### M4 · Cutover

- 用户显式确认；
- manifest 写入新 runtime generation；
- 新 Runtime 取得项目写者租约；
- 旧 Runtime 不再接受任何写入；
- 旧文件保持只读备份，不做自动删除。

**出口**：只有一个写者；首个新事件可追溯到 migration generation。

### M5 · Post-cutover Validation

- 在新 Runtime 上完成只读看板、任务详情、成员和知识检查；
- 执行一次无副作用的权限负面对抗；
- 再执行受控的 DSH Web 核心场景；
- 观察无重复消息、重复 spawn 和旧路径回写。

**出口**：核心场景通过后，旧实现才进入退役流程。

## 9. 回滚与故障策略

- **cutover 前**：删除候选输出即可，旧系统未改变；
- **cutover 后且尚无新写**：可由管理员明确切回旧 generation；
- **cutover 后已有新写**：不做自动反向回滚，避免双历史；通过向前导出与修复继续演进；
- **候选导入失败**：旧数据不动，报告具体输入位置；
- **投影对账失败**：禁止 cutover；
- **生成视图失败**：不阻断权威恢复，但必须标记并重建；
- **SQLite 迁移失败**：使用备份恢复，不能与事件日志做半套切换。

每一批次都可独立评审和回退代码，但**数据 cutover 只能按第 9 节规则处理**，不能用 Git 回滚代码来假装业务数据也已回滚。

## 11. 验证矩阵

| 层 | 必测内容 |
|---|---|
| Domain 单元测试 | 项目 DAG、防环、状态机、配置合并、权限、Attempt、知识修订 |
| EventStore 测试 | 原子批次、commit record 提交点、fsync 顺序、可证明 torn tail、完整批次保留、hash、确定性重放、未知事件 |
| 写者并发测试 | 多 captain、多进程租约、fencing、陈旧 generation、revision 冲突 |
| 迁移黄金测试 | 旧账本/配置/知识/SQLite fixtures、id 映射、未知事件、legacy 配置不可考例外、在途 Attempt/Effect 不重放、重复执行确定性 |
| 派生物测试 | 删除/篡改缓存、手工改生成配置、重建等价、源损坏整项目停写、降级不伪空 |
| Effect 故障测试 | durable 前后崩溃、spawn/message 重试、重复受理、outcome-unknown 对账、未证明不盲放 |
| 权限负面对抗 | 伪造 human、重放令牌、agent 写全局、跨 bank 记忆删除、跨团队越权 |
| DSH 集成测试 | 真实 subagents/preset/Remote/Session Log；成员无 Lead 工具泄漏 |
| DSH Web 真机验收 | 建队、跨团队 DAG、门禁、打回、重启恢复、队长接管、面板一致性 |

真机测试继续采用“桌面端写代码、独立 Web 实例做活体验收”的分工；Web 测试实例不能共享旧 Runtime 的写者，除非测试目的就是验证租约竞争。
