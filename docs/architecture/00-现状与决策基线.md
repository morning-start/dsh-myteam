## 1. 阅读规则

本文使用三类标签：

- **事实**：本次从代码、运行时 Inspect 或命令输出直接核到的事实。
- **历史**：旧文档曾经作出的约定；可能已被后续实现或新决策推翻。
- **决策**：用户在本次架构重写中明确选择的目标口径。

本文不根据“文档写着已完成”推断代码已经完成，也不根据“测试曾全绿”推断当前行为正确。多进程重复 seq 等风险若只做了静态推导，会明确标注，不伪装成实机复现。

## 2. 本次确认的目标与边界

### 2.1 用户已确认的四项前置选择

| 编号 | 选择 | 架构后果 |
|---|---|---|
| D-01 | 允许内部重构，提供一次性迁移 | 工具/RPC 可以升级版本；旧数据经显式迁移进入新架构，不做长期双写 |
| D-02 | 一个项目允许多个团队并行 | 项目必须成为共享查询与写入协调边界，不能继续以单团队为全局边界 |
| D-03 | 允许跨团队任务依赖 | 任务 id、依赖防环和图修改必须在项目层统一处理 |
| D-04 | 采用“项目事件真源 + 定义资产” | 项目运行与定义历史统一进入项目事件日志；可读配置文件成为生成视图 |

### 2.2 四条总原则

1. **全局级负责跨项目复用**：全局 RoleDefinition、WorkflowDefinition 与 TeamBlueprint；任何进入或修改全局的动作必须由用户确认。
2. **项目级负责本项目跨会话、跨时间复用**：项目角色、蓝图、团队、任务、配置、知识与记忆，agent 是主要操作者。
3. **每个实体只有一个权威存储和一个写入口**：副本必须标明是生成视图、可重建缓存、不可变快照或外部引用。
4. **先系统架构，再功能实现设计，最后才改代码**：本轮只形成文档，不通过继续堆工具或补丁代替架构重写。

长期记忆是独立的 SQLite 库（[D-16](#6-已确认的目标架构决策)），不在这六个位置里。

### 3.3 运行时装载：Root 承重，preset 只做适配

装入口是 [cordis.patch.yml](../../plugin/cordis.patch.yml)，三条线：

1. **裸包 carrier（root）** —— 把客户端带进装载图，本身不持业务；
2. **面板门面（root）** —— 必须挂 root：preset 内会被 isolate，网关看不到
   （注释里记了这条踩坑）；
3. **队长 preset** —— 服务与工具只在队长会话 scope 激活，避免泄漏审计报
   `Preset services require isolate realms`；
4. **成员工具** —— 不在 preset 层注册，由 `setup(agentCtx)` 在成员作用域内注册。

这与 §6 的 D-14（Root Host 提供共享 Runtime；captain/member/panel 只是适配器）一致：
**能承重的在 root，preset 里只放"只能在 preset 里活"的东西。**

> 重构中移出工作树（完整保存在标签 `v1-backup`），因此这里不再用可点链接，避免把
> 已删除的文件伪装成可核对证据。

**v1 体量**：模块 83、依赖边 265（value 204 / type 61）、源码 28,836 行、入口层占比 30.2%；
`host.ts` 4,375 行 / fan-out 62、`panel.ts` 1,459 行 / fan-out 14；value 环 0、逆向 value 边 3
（均与成员工具的入口依赖有关）。

**v1 存储**（迁移输入）：项目根 `<project>/.dsh-myteam/`；全局根 `$DSH_HOME/myteam/`；
团队/成员/任务/依赖/门禁/消息同放 `tasks/<teamId>/ledger.jsonl`（**逻辑上宣称项目级，
物理上按团队分账本**，跨团队图没有统一事务）；项目默认配置 `config/team.config.json`
与团队配置 `tasks/<teamId>/team.config.json` 各成一份文件权威；团队索引 `state/teams.json`；
看板索引 `state/index/tasks.json`；知识 `config/knowledge/*.md` + 账本提案/采纳事件；
长期记忆 `history/memory.db` 与 `memory.md` **双记忆面**。

**v1 运行时**：根级裸包 carrier + 根级 `MyTeamPanelFacade`（经 `agentPresets.serviceFor()`
找队长 preset 内的隔离服务）+ captain preset 内的 `MyTeamHost/MyTeamRemote` + member preset 内的成员工具。
成员工具靠 `member Agent → parentSession → captain Agent → serviceFor(captain,'myteam')`
反查队长服务，造成两个后果：队长不在线时成员无法持久化工作事实；成员模块反向依赖入口层。

**v1 为什么必须重写**（结论仍然成立，只是对象已换）：

- 单写者边界不成立：每个 captain preset 都能造自己的 Host/Service，同一项目被多个队长会话
  打开时各持 `nextSeq` 与内存投影，「单 Host 内单写者」推不出「项目单写者」；
- 人类确认不是可信边界：`enforceTier:false`、`actor:'human'`、`confirm:true` 都只是参数；
- 跨文件操作没有原子性：知识采纳先提交事件后写 Markdown，可出现「事件已采纳、正文写失败」；
- 派生逻辑与权限规则分叉：任务图、配置校验、返回形状各有多套实现。

四条都在 v2 里被结构性解决（项目单写者 + 租约、人类入口与模型工具分离、事件真源 +
生成视图、统一查询入口），证据见 [07 §2](07-文档现状对账-2.0.0.md)。

## 5. 权限与一致性风险：为什么必须重写而非补文案

以下均为静态代码事实或可直接由代码路径推出的风险；未宣称本次已做全部实机复现。

### 5.1 单写者边界不成立

每个 captain preset 都可创建自己的 `MyTeamHost/TeamService`；同一项目同一团队被多个队长会话打开时，各自持有 `nextSeq` 和内存投影。账本追加没有项目级协调者，因此“单 Host 内单写者”不能推出“项目单写者”。

### 5.2 人类确认不是可信边界

- Lead 通道默认 `enforceTier:false`，H 档并非不可绕过的人意证明；
- `actor:'human'`、`confirm:true`、`confirmGlobal:true` 都只是参数；
- 全局角色创建/修改存在队长工具入口；
- A 档技能/工具创建可写全局 preset 目录。

因此，目标架构必须把“人类专属入口”和“模型工具入口”分开，并在服务端再次鉴权。

### 5.3 跨文件操作缺少原子性

知识采纳先提交事件、后写 Markdown；配置、成员卡、身份快照和索引又各有独立读写路径。单文件原子写只能保证“这个文件不写坏”，不能保证“多个文件表达同一事实”。

### 5.4 派生逻辑和权限规则存在分叉

任务图、配置校验、配置返回形状和离线/在线视图各有多套实现。目标架构必须统一领域计算与查询入口，而不是给每套实现再补一份文档。

### 5.5 记忆所有权需要服务端校验

当前 `myteam_forget` 按 entry id 归档，缺少 entry 是否属于调用者 bank 的校验。新 Memory Store 必须把 bank 所有权作为命令权限的一部分，而不是依赖调用者自律。

## 7. 旧 ADR 的继承与替代

| 旧决策 | 处置 | 新口径 |
|---|---|---|
| ADR-001 根会话成员 | **superseded** | 子代理优先，兼容回退隔离在 DSH adapter |
| ADR-002 团队账本单写者 | **superseded，保留原则** | 项目事件日志 + 项目写者；保留 append-only、先算后写、可重放投影 |
| ADR-003 preset 内服务与工具 | **修订** | preset 只保留工具/persona/能力适配，业务服务上移 Root Host |
| ADR-004 token 侧车 | **保留为派生输出** | DSH Session Log 是原始计量事实，侧车不反哺业务状态 |
| ADR-005 装载组合 | **修订** | 增加 Root Runtime；carrier/facade 等宿主约束在功能设计中逐项验证 |
| ADR-006 面板数据流 | **修订** | 在线/离线统一 Query Service，写操作仍共用应用管线 |
| ADR-007 结构化证据 | **保留** | 证据是结构化领域数据，不依赖全文语义猜测 |
| ADR-008 成员配额 | **保留原则** | 配额进入版本化配置与安全上限 |
| ADR-009 文件记忆 | **superseded** | SQLite 长期记忆；md 只作一次性导入或显式导出 |
| ADR-010 团队/临时委派/单 Agent 选择 | **保留** | 团队仍用于跨会话、可审计、需角色隔离的工作 |
| ADR-011 任务与团队解耦 | **扩展** | 任务升级为项目事件内实体，支持跨团队依赖 |
| ADR-012 因果唤醒 | **保留原则** | 唤醒改为项目事件后的 Effect，不轮询 |
| ADR-013/014 任务取消与批量 | **保留领域候选** | 在任务功能设计中重审契约，迁移到项目 DAG |
| ADR-015 成员树 | **修订** | 保留只收窄与同团队树，运行事实改存项目事件 |
| ADR-016 项目共享看板 | **扩展** | 看板直接由统一项目投影生成，不再聚合多个权威账本 |

[27-成员子代理化与SQLite记忆](../audits/27-成员子代理化与SQLite记忆.md) 标题中的“ADR-010 草案”与现有 ADR-010 编号冲突，后续不再沿用该编号；其实机验证记录转为历史证据。

## 8. 不可丢弃的兼容约束

1. `.dsh-myteam` v1 与更早 `.team-workplace` 都必须有只读迁移入口。
2. 旧事件类型、`rules.version.adopted`、成员树字段迁移和未知字段不能静默丢弃。
3. 原子写、fsync、唯一临时名、拒符号链接仍是文件基础设施底线。
4. 旧 `sessionId` 必须保留，否则无法重新关联 DSH 会话与子代理树。
5. 角色 `origin`、项目副本、能力只收窄和成员协调工具不可被角色策略关闭，仍是安全不变量。
6. DSH 的 Session Log、subagents、agentPresets、tools 与 Remote 能力必须以**当前安装版本**重新核验，不能照搬旧版本探针。
7. 旧工具/RPC 可以做版本升级，但必须先生成现有契约表征与迁移映射，不能直接删除调用方仍依赖的形状。
