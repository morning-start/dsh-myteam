# 03 · 角色能力与工作流

> 状态：`accepted`（Role / Workflow 定义与 Run 均已实装；未做项见 [01](01-系统架构.md) §16）
> 上游：[01-系统架构](01-系统架构.md)
> 本文主题：Role、Skill、Workflow、TeamBlueprint、Task 的边界；不展开具体 JSON 字段或工具参数。

## 1. 一页结论

```text
RoleDefinition
= RoleProfile（角色设定）
+ CapabilitySet（能力集合）
  ├─ Tool / MCP 权限
  └─ SkillRef 集合

WorkflowDefinition（可复用定义）
        │ instantiate
        ▼
WorkflowRun（一次真实执行，仅项目）
        │ 生成、引用、动态调整
        ▼
项目统一 Task DAG
        │ 分配
        ▼
Member / Team
```

五条不变量：

1. **RoleDefinition 是独立真源，不是 Role Skill 的副本**；Skill 是被引用的外部能力。
2. **Workflow 独立于人，也独立于 Skill**；Role 不拥有流程，Skill 不管理流程运行状态。
3. **Definition 与 Run 分离**；全局只能保存可复用 Definition，Run 永远只属于项目。
4. **一个项目只有一张 Task DAG**；WorkflowRun 引用其中一组任务，不建立第二套任务状态机。
5. **动态调整只改变 Run 与项目 DAG**；不回写 Definition，复用必须经过显式保存或发布。

## 2. 为什么不再采用 Role Skill 作为唯一真源

早期方案曾考虑把角色设定、能力声明与提示词全部放入一个特殊 Skill。最终选择独立 RoleDefinition，原因是：

- 全局/项目复制、origin、baseHash、definitionRevision 需要稳定的定义身份；
- 队长标记、模型偏好、兴趣词、组织委派不是普通 Skill 的固有语义；
- myteam 必须在成员上岗时强制计算权限，而不是依赖 Skill 正文自律；
- Skill 由 DSH 管理，若同时充当 Role 真源，会把两套版本、发布和权限边界重新合并；
- TeamBlueprint 需要引用稳定 Role，而不是引用一组没有整体身份的 Skill。

因此，RoleDefinition 保留为定义资产；`RuntimeRoleSnapshot` 是成员上岗时生成的装配结果，不是第二份人工维护的角色定义。

## 3. RoleDefinition：只有两个顶层部分

### 3.1 RoleProfile · 角色设定

回答“这个成员是谁、长期怎样工作、组织上能做什么”。

| 内容 | 语义 | 不属于它的内容 |
|---|---|---|
| 身份 | id、名称、职责描述、是否队长 | 成员实例 id、会话 id |
| 长期设定 | 职责边界、工作方式、汇报与记忆纪律 | 某次任务的完整执行计划 |
| 执行偏好 | 可选模型路由、兴趣词等调度信号 | 临时在线状态、token 用量 |
| 组织授权 | delegation、可派生范围等 | 普通工具调用本身 |

### 3.2 CapabilitySet · 能力集合

回答“这个角色被允许使用哪些能力”。

| 内容 | 语义 | 强制边界 |
|---|---|---|
| Tool policy | 基础工具可见范围与收窄规则 | 只能收窄；应用服务仍需鉴权 |
| MCP references | 已连接能力的引用与可见范围 | 不保存连接本体或凭据 |
| SkillRef 集合 | DSH Skill 的 id、可选版本或内容 hash | 不复制 Skill 正文，不因引用自动扩权 |

**基本工具不应伪装成 Skill。** 工具是有输入、输出和副作用的执行动作；Skill 是使用这些动作完成某类事情的方法。Skill 可以声明依赖工具，但无权自行把工具授予角色。

### 3.3 不进入 Role 的内容

- WorkflowDefinition / WorkflowRun；
- Task、Attempt、Gate、Evidence；
- Team、Member、CaptainAssignment；
- SessionRef、在线状态、运行句柄；
- 项目知识正文与私有记忆；
- 项目绝对路径和实际交付物。

### 3.4 与当前代码字段的概念映射

当前 [RoleDefinition](../../plugin/src/application/bootstrap.ts#L28-L50) 可按下表理解；这是一份**概念映射，不代表新 schema 已实现**。

| 当前字段 | 目标归属 |
|---|---|
| `id/name/description/systemPrompt/isCaptain` | RoleProfile |
| `model/interestWords` | RoleProfile 的执行与调度偏好 |
| `delegation` | RoleProfile 的组织授权 |
| `toolPolicy/mcpAllowlist` | CapabilitySet |
| `skills` | CapabilitySet 的 SkillRef 集合 |
| `origin/version` | 定义存储元数据，不是第三个顶层部分 |

## 4. Skill 的合理复杂度

Skill 应当**内聚**，而不是机械地短：

- 能独立触发、复用、测试或演进时可以拆分；
- 永远一起执行且没有独立复用价值的步骤不必拆成多个微型 Skill；
- 组合型 Skill 可以编排一个 Task 内的固定方法步骤；
- Skill 不管理跨任务状态、独立 Attempt、跨主体分配、动态 DAG 或持久化恢复。

判断边界：

| 过程 | 承载方式 |
|---|---|
| 一个 Task 内、步骤固定、无需独立状态 | Skill 或组合型 Skill |
| 节点是独立交付项、需要门禁或不同负责人 | Workflow |
| 依赖会随结果变化、需要暂停恢复或重规划 | Workflow |

## 5. WorkflowDefinition：定义可以复用什么

WorkflowDefinition 描述初始工作结构或生成约束，不描述真实运行。

可包含：

- 目标与完成条件；
- TaskTemplate 节点及初始依赖；
- 角色要求、门禁和交付要求；
- 固定/骨架/动态的初始定义完整度；
- 是否允许增删节点、重分配、重接依赖等调整约束。

不得包含：

- projectId、teamId、memberId、sessionId、attemptId；
- 真实 taskId、任务状态、Attempt、证据和实际交付物；
- 项目绝对路径、私有知识、记忆或凭据。

### 5.1 TaskTemplate 不是 Task

TaskTemplate 只是定义节点，具有模板 key、标题、AC、交付要求、模板依赖和角色要求。它没有真实执行身份。

实例化时才生成项目 taskId，并建立 `templateKey → taskId` 映射；后续重规划必须保留该映射，不能靠标题猜测节点关系。

### 5.2 定义完整度不是三种 Workflow 类型

| 完整度 | 初始定义 | 实例化后的处理 |
|---|---|---|
| 固定型 | 节点和依赖基本完整 | 按定义生成任务 |
| 骨架型 | 只有阶段和关键节点 | 执行中补全任务与依赖 |
| 动态型 | 目标、约束与完成条件为主 | 逐步生成和调整任务 |

三者共用同一 Definition/Run 模型，不新增独立执行引擎。

## 6. WorkflowRun：一次真实执行

WorkflowRun 只属于项目，保存：

- 所用 WorkflowDefinition revision 与 hash；
- 本次目标、完成条件和 completionRevision；
- 关联 taskIds 与 `templateKey → taskId` 映射；
- 参与成员/团队及协调者绑定；
- 动态变更历史和当前 graphRevision 引用。

WorkflowRun **不复制任务状态**。任务状态、Attempt、门禁、证据和交付物仍由项目统一事件与投影管理。

### 6.1 参与范围不是类型

| 参与拓扑 | 表现 |
|---|---|
| 单成员 | 所有任务最终分配给同一个 Member |
| 单团队跨成员 | 任务分配给同一团队的不同 Member |
| 跨团队 | 任务由不同 Team 主责或协作 |

WorkflowRun 统一属于项目。参与范围变化只是任务分配和参与关系变化，不需要转换 Run 类型。

### 6.2 临时任务与跨 Run 依赖

- 手工创建的 Task 可以不属于任何 WorkflowRun；
- **一个 Task 最多归属一个 WorkflowRun**，避免多个 Run 同时拥有同一任务的完成权；跨 Run 合作用依赖表达，不复制任务，也不共享所有权；
- 不同 Run 的任务可以建立依赖，仍进入同一项目 DAG、同一防环和 revision 机制；
- Run 的完成条件只评估自己声明的任务集合，不把其他 Run 的下游任务隐式算入。

## 7. 动态调整与完成条件

允许的动态操作包括：增加、拆分、取消任务，增删依赖，重新分配成员/团队，以及根据证据生成后续任务。

每次操作必须：

1. 以项目原子事件批次提交；
2. 携带所需 `expectedGraphRevision` 与实体 revision；
3. 通过全项目防环、权限、状态和配置校验；
4. 保留变更原因、前后差异和 causation/correlation；
5. 不修改已发生的历史，不用循环依赖表达返工。

### 7.1 完成条件必须可判定

- Definition 给出初始完成条件；
- Run 实例化时固化为 completionRevision；
- 动态新增必要任务或改变完成规则时，必须显式生成新的 completionRevision 并说明原因；
- Run 只有在完成规则满足、必要任务均到合法终态且所声明门禁完成后才可完成；
- “不断新增任务”不能被隐式当作完成，也不能让完成条件无记录地漂移。

## 8. TeamBlueprint 如何组合

```text
TeamBlueprint
├── 引用 RoleDefinition（队形与成员槽位）
├── 引用 WorkflowDefinition（可选默认流程）
└── 默认行为配置
```

- Blueprint 只保存引用与版本约束，不拥有 Role 或 Workflow 正文；
- 实例化 Blueprint 时，分别解析并固化项目定义 revision；
- 多团队使用同一 Blueprint 会产生不同 Team、WorkflowRun 和 Task；
- Blueprint 的 `pipeline` 若只是看板/泳道展示配置，就不是 WorkflowDefinition；
- Role、Workflow、Blueprint 分别复制、发布和进行引用校验，不隐式打包修改全局资产。

## 9. 全局级与项目级

| 概念 | 全局级 | 项目级 |
|---|---|---|
| RoleDefinition | ✅ 值得跨项目复用 | ✅ 本地定义与实例化来源 |
| WorkflowDefinition | ✅ 值得跨项目复用 | ✅ 本地定义与实例化来源 |
| TeamBlueprint | ✅ 值得跨项目复用 | ✅ 本地定义与实例化来源 |
| SkillDefinition | 由 DSH 管理 | 由 DSH 管理，myteam 只保存 SkillRef |
| Tool / MCP 连接 | 由 DSH/用户管理 | myteam 只保存收窄规则与引用 |
| Team / Member | ❌ | ✅ 协作与运行事实 |
| WorkflowRun | ❌ | ✅ 一次真实执行 |
| Task / DAG / Attempt / Gate | ❌ | ✅ 项目工作事实 |
| Knowledge / Memory | ❌ | ✅ 项目知识与长期记忆 |
| 行为配置 | ❌ 全局默认层 | ✅ 项目默认、蓝图默认、团队覆盖 |

**内置与插件贡献是 origin，不是额外作用域。** 作用域仍只有 global / project。

## 10. 权限与发布

- Captain 可以创建和修改项目 Role、WorkflowDefinition、TeamBlueprint；
- 全局复制到项目只读全局并写项目定义事件；
- 全局发布请求与实际写全局分离，只有 Human 确认后才能执行；
- 发布 Blueprint 时预览 Role/Workflow 引用、缺失项和版本差异，不隐式发布被引用资产；
- 一个 operationId 只写一个全局目标，多资产发布是多个独立操作；
- 既有 Member、Team、WorkflowRun 继续绑定原定义快照；
- 动态调整 Run 不是修改 Definition，也不需要全局确认；只有将调整结果显式保存为定义或发布时才进入定义权限流程。

## 11. 迁移规则

1. 旧 `config/workflow.json` 若没有生产读写消费者，只作为预留输入检查，不自动当成权威 WorkflowDefinition。
2. 旧 `pipeline.stages` 若只用于视图或泳道，保留为配置，不转换成 Workflow。
3. 只有旧 `taskPlanning:'template'` 明确使用 stages 生成线性任务时，才生成带 `origin:'legacy-task-planning'` 的 WorkflowDefinition，并记录原始输入 hash。
4. 既有旧任务可以不属于 WorkflowRun；不得根据 teamId 或标题猜测并伪造 Run。
5. 若用户显式选择为旧任务建立 Run，必须生成独立映射事件并确认完成条件，不直接修改历史任务事件。
6. 旧 Role 字段按 §3.4 做概念映射；无法证明的历史角色版本继续遵守“不可考”规则。

## 12. 验收场景

1. 创建一个只含角色设定与 SkillRef/Tool/MCP 的 Role，成员上岗后获得正确快照，Skill 不可导致隐式扩权。
2. 全局 WorkflowDefinition 复制到项目后，上游更新不改变项目副本和既有 Run。
3. 同一 Definition 分别实例化单成员、跨成员和跨团队 Run，任务都进入同一项目 DAG。
4. 动态增加任务、重接依赖和拆分任务后，旧 Definition 不变，图版本与变更原因可回放。
5. 两个 Run 之间建立任务依赖时不产生第二套任务状态，项目防环仍有效。
6. 完成规则变化生成新 completionRevision，不能因新增任务无记录地推迟或提前完成。
7. 蓝图只展示 pipeline 时不产生 Workflow；旧 template 任务规划仅在满足证据条件时迁移为 Definition。
8. 发布 Blueprint 不会隐式发布 Role 或 Workflow，全局写仍需要独立 Human 确认。
