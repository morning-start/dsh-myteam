## 0. 一页结论

myteam 只做两件事，而且**必须分开做**：

| 部分 | 管什么 | 资源 | 落盘 |
|---|---|---|---|
| **① 团队与成员** | 把「角色」聘任成成员，成员再派生更小的子 Agent | **角色**（全局 / 项目两级） | 全局 → `$DSH_HOME/myteam/roles/`；项目 → `<ws>/.dsh-myteam/config/roles/` |
| **② 任务与看板** | 任务作为项目级工作项，用**一张看板**同步整套进度 | **任务**（项目级，唯一作用域） | `<ws>/.dsh-myteam/tasks/<teamId>/ledger.jsonl` |

**两条铁律**：

1. **角色是可复用的能力模板**：全局角色到处能用（复制源），项目角色只在本项目用；运行时只认项目库，全局 → 项目**单向复制**，绝不自动同步。
2. **任务是项目级资源**：不存在「全局任务」；任务只属于项目，团队通过「参与」接手，看板在**最外层**聚合全部任务。

**目标树（三层）**：

```
北极星：让「角色」和「任务」都成为一等资源——角色可复用、可聘任、可再分工；任务可聚合、可追踪、可审计。
├─ 支柱一（FR-32）角色即资源 → 子 Agent 编队
│   └─ 成员从角色派生，父子树可配深度，能力只收窄，账本可追溯
├─ 支柱二（FR-33）任务即资源 → 项目共享看板
│   └─ 一张项目看板聚合全部团队/层级任务，最外层一眼看完整套进度
└─ 支撑目标（S1~S5）
    ├─ S1 作用域：全局 / 项目两级，落盘与复制方向固定（docs/17、19）
    ├─ S2 权限：C5 只收窄，子 Agent 能力 ⊆ 父级
    ├─ S3 审计：append-only 账本唯一权威，任何派生视图可重建
    ├─ S4 成本：成员树配额（深度 / 每层人数 / 总量）硬上限
    └─ S5 单一事实源：看板数字全部从账本派生，不建第二份缓存
```

## 1. 为什么现在要重梳理

v3.0 把四件事混在一起讲，导致四个具体问题（都是用户这次点到的「各种各样的问题」）：

| # | 混同 | 现状 | 后果 |
|---|---|---|---|
| 1 | **角色 = 配置** | 角色库只是「配置单元」，不是一等资源 | 跨项目复用的语义靠「复制」补丁，没有资源生命周期 |
| 2 | **成员 = 实体** | 成员是 spawn 出来的会话，投影里只有 `roleId` 没有父子 | 团队一大就全部平铺，上下文膨胀、职责漂移 |
| 3 | **子 Agent = 禁止** | `limits.memberMaxDepth` **硬上限 0**（FR-3.9）、PRD §1 非目标「不引入成员管理成员的递归权限」、ADR-010 反模式 #4 | 任何「再分工」需求都只能压回队长，队长上下文成为唯一瓶颈 |
| 4 | **任务 = 团队的一部分** | 任务已升项目级（CHG-64~68），但看板仍挂在「项目 · 任务」tab，团队视图只列本团队参与 | 「最外面看到整套任务」不成立：要逐个团队点开才知道全局进度 |

**这次重梳理做的不是加功能，是换口径**：把「角色 / 任务」当资源管，把「成员 / 团队」当聘任关系管，把「子 Agent」从禁止项改成受控项。

## 2. 资源模型（用户定案）

### 2.1 两类资源、一条关系

```
资源 A：角色（Role）                       资源 B：任务（Task）
├─ 全局角色  $DSH_HOME/myteam/roles/       └─ 项目任务  <ws>/.dsh-myteam/tasks/<teamId>/ledger.jsonl
│   └─ 可到处复用（复制源，只读/人类可写）
└─ 项目角色  <ws>/.dsh-myteam/config/roles/
    └─ 只在本项目用（运行时唯一真相）

关系：团队（Team）= 聘任容器
  └─ 成员（Member）= 角色 × 团队的聘任记录（**不是资源**）
      └─ 子成员（Sub-member）= 成员再聘任一次角色（**同一团队内**的父子树）
```

### 2.2 四条裁决

| # | 裁决 | 含义 |
|---|---|---|
| R1 | **成员不是资源** | 成员是「角色 × 团队」的聘任记录（快照固化，C3）；资源只有角色与任务 |
| R2 | **任务只有项目作用域** | 不存在全局任务；跨项目看任务 = 跨 workspace，属于宿主层，不在本插件 |
| R3 | **角色两级、单向流动** | 全局 → 项目（复制下来用）；反向只有「发布」，人类专属不可逆 |
| R4 | **子 Agent 仍在团队内** | 子成员不建子团队、不另开账本；父子关系记在成员上，深度可配、硬上限 2 |

### 2.3 落盘与作用域（与 [17](17-项目级存储架构.md) / [19](19-资源模型与能力矩阵.md) 对齐）

| 资源 | 全局（用户数据） | 项目（项目文件夹） | 运行时真相 |
|---|---|---|---|
| 角色 | `$DSH_HOME/myteam/roles/*.json` ✅ 可到处复用 | `<ws>/.dsh-myteam/config/roles/*.json` ✅ 仅本项目 | **项目库** |
| 团队定义 | `$DSH_HOME/myteam/teams/*.json`（复制源） | `<ws>/.dsh-myteam/state/teams/<teamId>/` | **项目内团队** |
| 任务 | **不存在** | `<ws>/.dsh-myteam/tasks/<teamId>/ledger.jsonl` | 账本 |
| 成员 | 不存在（团队内） | `.../members/<memberId>/`（身份快照 + 私有记忆） | 账本 `member.spawned` |

> **判据**：`$DSH_HOME` 内的路径一律不是项目（`rejectProjectRoot`）；`resolveProjectRoot()` 是唯一入口。

## 3. 支柱一（FR-32）：角色即资源 → 子 Agent 编队

### 3.1 现状（已有什么）

| 能力 | 现状 | 位置 |
|---|---|---|
| 角色两级 + 三来源 | `builtin` / `plugin` / `global` / `project` 四态；复制即 fork、发布即单向 | `core/roles/role-store.ts`、`role-ops.ts` |
| 成员两阶段 spawn | 先落 `provisioning` 再建 child，失败落 `failed`，启动可对账 | `host.ts` `spawnMember` |
| 工具收窄 | `buildToolMask()` 只收窄（C5），团队工具永不可关 | `core/members/member-setup.ts` |
| 能力隔离 | 角色 `skills` / `mcpAllowlist` 硬隔离 + 边界提示词 | `core/members/capability-guard.ts` |
| 配额 | `maxMembers` 插件级自管（ADR-008） | `core/config/team-config.ts` |

### 3.2 缺口（要补什么）

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| G1-1 | **成员不能派生** | `limits.memberMaxDepth` 默认 0 且 `PATCH_CEILINGS` 硬上限 0 | 再分工只能回队长，上下文单点 |
| G1-2 | **成员侧无 spawn/release 工具** | 成员 9 工具集不含 `spawn_member` / `release_member` | 成员即使被授权也调不到 |
| G1-3 | **投影无父子字段** | `MemberProjection` 只有 `id/roleId/...` | 名册无法画树、级联释放无从判断 |
| G1-4 | **角色 schema 无委派声明** | `RoleDefinition` 只有 `toolPolicy` | 「谁能派生谁」没有数据位 |
| G1-5 | **释放无级联语义** | `release_member` 只看单个成员 | 父成员释放后子成员成孤儿 |

### 3.3 目标口径（DoD）

1. **角色可复用**：任意来源角色可被聘任为成员；成员可在授权范围内再聘任**子成员**（同一团队、同一账本）。
2. **父子可追溯**：`member.spawned` 带 `parentMemberId` / `depth` / `rootMemberId`；投影可重建出成员树。
3. **权限只收窄**：子成员的工具集 **⊆** 父成员（allow 取交集、deny 取并集）；未授权一律 `MT_UNAVAILABLE`。
4. **配额硬约束**：`memberMaxDepth` 默认 **1**、硬上限 **2**；`maxMembers`（含子成员）默认 6；单成员 `maxChildren` 默认 3。
5. **生命周期安全**：父成员释放前必须排空子成员（默认拒绝，`cascade:true` 才级联）；崩溃按根树对账。
6. **归属可审计**：子成员 claim 的任务仍属团队；`task.claimed.memberId` 可上溯到 `rootMemberId`。

### 3.4 数据模型

**角色 schema 扩展**（`RoleDefinition`）：

```ts
delegation?: {
  canSpawn: boolean               // 默认 false（只收窄）
  allowedRoles?: string[]         // 可派生的角色白名单；空 = 不可派生
  maxDepth?: number               // 该角色可再派生的深度（默认 0；受全局上限 2 约束）
  maxChildren?: number            // 单成员子 Agent 上限（默认 3）
}
```

**成员事件 payload 扩展**（`member.spawned`；**不新增事件型**，保持 40 型）：

```ts
{
  teamId, memberId, roleId, instanceName, sessionId, status,
  parentMemberId?: string,   // 缺省 = 根成员（向后兼容）
  depth: number,             // 根 = 0
  rootMemberId?: string      // 缺省 = 自身
}
```

**投影扩展**（`MemberProjection`）：

```ts
parentMemberId?: string
depth: number
children?: string[]          // 派生视图（fold 时维护；也可由 parentMemberId 现算）
```

**配置**（`limits`）：

| 字段 | 现在 | v4.0 | 硬上限 |
|---|---|---|---|
| `memberMaxDepth` | 0 | **1** | **2**（`PATCH_CEILINGS`） |
| `maxMembers` | 6 | 6（含子成员） | 6 |
| `maxChildren` | — | 3（新增，角色级可覆写） | 6 |

### 3.5 能力面（工具 / 档位 / 权限）

| 工具 | 现在 | v4.0 | 说明 |
|---|---|---|---|
| `myteam_spawn_member` | C（仅队长） | **CM** | 成员需角色 `delegation.canSpawn` 显式授权才可见 |
| `myteam_release_member` | C（仅队长） | **CM** | 同上；父成员释放子成员需 `cascade:true` 或先排空 |
| `myteam_list_members` | — | **A（新增）** | 全员可见（子成员发现 / 等待 / 名册树） |

**口径变化**：工具 63 → **64**（+`list_members`）；成员工具 9 → **12**（+spawn/release/list）；档位分布 A 18→**19** · C 37→**35** · CM 2→**4** · H 6。

**C5 铁律扩展（新增第 9 条）**：

> 9. **子成员能力 ⊆ 父成员**：派生时先算父成员的有效工具集，子成员只能在此集合内再收窄；`delegation.allowedRoles` 只能指向「父成员可聘任的角色」，不能借派生提权。

### 3.6 生命周期与级联

```
队长/授权成员 --spawn_member--> provisioning（先落账）
                                   │
                                   ├─ agents.create 成功 --> active（同 memberId 结算）
                                   └─ 失败/超时 --------> failed + reason
父成员释放：
  ├─ 有 active 子成员 且未 cascade --> 拒绝（MT_HAS_CHILDREN，先排空或级联）
  └─ cascade:true -----------------> 按深度倒序 release 子成员 --> 再释放父成员
崩溃恢复：
  └─ 按 rootMemberId 拉整棵树，只对账 provisioning 且不在 live registry 的节点
```

### 3.7 验收场景（编号接 [08](08-验收报告.md)）

| # | 场景 | 断言 |
|---|---|---|
| 37 | 授权角色派生 1 层子成员 | 落 `member.spawned{parentMemberId,depth:1}`；子成员可见；名册树展开正确 |
| 38 | 未授权派生 | 角色无 `delegation.canSpawn` → `MT_UNAVAILABLE`；不落任何账 |
| 39 | 深度 / 配额 | 第 2 层允许、第 3 层 `MT_DEPTH_EXCEEDED`；`maxChildren` 超限拒绝；`maxMembers` 按含子成员计 |
| 40 | 权限收窄 | 子成员工具集 ⊆ 父成员；父成员 deny 的工具子成员不可见 |
| 41 | 级联释放 | 无 `cascade` 拒绝（`MT_HAS_CHILDREN`）；`cascade:true` 倒序释放；孤儿 = 0 |
| 42 | 归属可审计 | 子成员 claim 的任务，`rootMemberId` 可上溯；token 按成员树汇总、明细保留 |

## 4. 支柱二（FR-33）：任务即资源 → 项目共享看板

### 4.1 现状（已有什么）

| 能力 | 现状 | 位置 |
|---|---|---|
| 任务项目级实体 | 任务独立于团队存在（CHG-64~68），参与关系主责 1 / 协作 N | `core/scheduler/state.ts` |
| 四视图 | 列表 / 看板 / 流程 / 依赖图同源读账本 | `plugin/client/client.js` `g6.tasks.*` |
| 派单唤醒 | 任务新建/解锁/重规划后按角色唤醒 | ADR-012 |
| 汇总指标 | 进行中 / 门禁待审 / 已完成 | `g6.tasks.summary*` |

### 4.2 缺口（要补什么）

| # | 缺口 | 现状 | 影响 |
|---|---|---|---|
| G2-1 | **最外层不是看板** | 项目默认落地是全局库 / 角色；任务看板是二级 tab | 「最外面看到整套任务」不成立 |
| G2-2 | **跨团队聚合不完整** | 项目任务页有聚合，但团队视图只列本团队参与；缺「按团队/按角色/按父子根」分组 | 全局进度要逐个团队点 |
| G2-3 | **无项目级任务索引** | 读任务要逐团队重放账本 | 团队一多，看板首屏慢 |
| G2-4 | **角色 × 任务无反向视图** | 只能从任务看 `requiredRole` | 「这个角色手上还有哪些任务」看不到 |
| G2-5 | **汇总口径散** | 各 tab 各算各的 | 数字对不上时没有唯一口径 |

### 4.3 目标口径（DoD）

1. **一张项目看板**：项目内全部团队 / 全部层级（含子成员）的任务聚合到同一张看板；四视图同源。
2. **最外层落地**：项目有活跃团队时，面板默认落地 = **任务看板**（`scope='project'` + `tab='tasks'`），不再默认全局库。
3. **三种分组 + 五个汇总**：分组 = 按团队 / 按角色 / 按父子根；汇总 = 总任务 · 进行中 · 门禁待审 · 已完成 · 阻塞（+ 证据过期）。
4. **单一事实源**：所有数字从账本派生；`state/index/tasks.json` 只是可重建索引，删掉重算结果必须一致。
5. **反向视图**：角色详情可看「该角色在跑 / 待领的任务」；团队视图保留只读「参与任务」子集。

### 4.4 数据模型

| 对象 | 变化 |
|---|---|
| 账本 | **不变**（40 型事件；任务仍带 `teamId` 分区） |
| 项目任务索引 | 新增 `state/index/tasks.json`（派生缓存，可重建）：`{ tasks: [...], byTeam, byRole, byRootMember, updatedAt }` |
| 参与关系 | 不变（主责 1 / 协作 N；跨团队依赖仍不建模，见非目标） |
| 任务父子 | **不引入**（保持扁平 DAG；层级只在成员树，见 R4 与 ADR-010） |

### 4.5 能力面（端点 / UI）

| 能力 | 现在 | v4.0 |
|---|---|---|
| 项目看板聚合 | 端点 `getBoard`（团队级） | 新增 `getProjectBoard`（项目级，含三种分组） |
| 项目汇总 | 前端各算 | 新增 `getProjectSummary`（五指标 + 口径说明） |
| Remote 端点 | 40 | **42** |
| 门面方法 | 58 | **60** |
| 面板默认落地 | 全局库 | 项目有活跃团队时 = 任务看板 |
| 设计稿 | 27 屏 | **+1 屏（名册树）**；看板复用既有 `tasks` 四视图 |

### 4.6 验收场景（编号接上）

| # | 场景 | 断言 |
|---|---|---|
| 43 | 跨团队聚合 | 两个团队各 2 个任务 → 项目看板 4 个；按团队分组正确 |
| 44 | 父子归属 | 子成员领取的任务出现在「按父子根」分组下；根成员可展开 |

- **ADR-015 子 Agent 编队：同团队成员树，深度受控，能力只收窄**

## 6. 非目标（v4.0）

- **不做全局任务**（跨项目汇总）——任务只属于项目；跨项目看任务属于宿主层。
- **不做成员树无限深度**——硬上限 2 层；再深说明团队该拆，而不是继续嵌套。
- **不做无授权派生**——没有 `delegation.canSpawn` 一律拒绝，且子成员能力 ⊆ 父成员。
- **不做子团队**（team 树）——子 Agent 仍在同一团队、同一账本；团队树是 M4 之后另议。
- **不做任务父子层级**——任务保持扁平 DAG（拆任务不建层级）。
- **不做多 Workspace 多活跃团队**（v1 起不变）。
- **不做跨进程并发协调**（诚实沿用单进程串行）。
- **不代用户连接 MCP、不代管凭据**。

## 8. 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R42 | 成员树成本失控（深度 × 每层人数 × 并发） | P1 | 三层硬上限（depth 2 / maxChildren 3 / maxMembers 6）+ token 按树汇总 |
| R43 | 权限提升（派生成为提权通道） | P1 | C5 第 9 条：子成员工具集 ⊆ 父成员；`allowedRoles` 只指向父可聘任角色 |
| R44 | 看板聚合性能（团队多、账本长） | P2 | 项目任务索引可重建；首屏只读索引，详情按需重放 |
| R45 | 兼容性（老账本无 `parentMemberId`） | P2 | 缺省 = 根成员；fold 零随机 id，重放逐字不变 |
| R46 | 归属歧义（子成员 claim 后父成员被释放） | P2 | 释放前强制排空子成员；`MT_HAS_CHILDREN` 拒绝式 |
