# 17-项目级存储架构（CHG-102，现行口径）

> **本文档是「项目级内容落在哪里」的唯一权威。** 与 `docs/03`/`docs/04`/`docs/11` 里的
> `.team-workplace/` 表述冲突时以本文档为准——那三份是历史记录（CHG-3~CHG-101 的落盘约定），
> 本文件是 CHG-102 之后的现行契约。

## 1. 为什么改（用户提出的两个 P0）

### P0-1：项目级内容写进了用户全局 profile

旧实现的项目根 = `ctx.workspace.root ?? process.cwd()`。在 DSH desktop profile 下
`workspace.root` 是 **`~/.dsh/profiles/desktop`**，于是：

- `myteam_create_role` 写出的项目角色落在 `~/.dsh/profiles/desktop/.team-workplace/config/roles/`；
- 面板的「项目」视图读的是**用户打开的那个项目** → 永远看不到这些角色；
- 换个项目打开，看到的还是同一批内置/全局角色 —— **每个项目看起来都一模一样**；
- 用户还没开始团队模式的对话，面板就已经渲染出角色库/团队/任务（内置 + 全局 + 别的项目的离线团队）。

复现证据：`C:\Users\Hanes\.dsh\profiles\desktop\.team-workplace\config\roles\{project-manager,architect,ui-designer,frontend-developer,backend-developer}.json`。

### P0-2：落盘根名与插件名不一致，且 `.gitignore` 写错位置

- 落盘根叫 `.team-workplace`，插件叫 `dsh-plugin-myteam`，用户认知无法对齐（用户定案改回 `.dsh-myteam/`）；
- 旧实现把「托管块」追加到**项目根** `.gitignore`（甚至在 profile 目录里生成垃圾规则），
  而不是存储目录自己的 `.gitignore`。

## 2. 目录契约（v1，`.dsh-myteam/`）

```
<project>/.dsh-myteam/
├── .gitignore                 # 本目录自己的提交纪律（哪些能上传）
├── manifest.json              # 项目清单：schemaVersion / layoutVersion / projectName / defaultTeamId
├── README.md                  # 目录说明（人读）
├── structure.md               # 团队章程（队长维护的项目结构约定）
├── config/                    # ① 配置资产 —— 入库、可 review、可共享
│   ├── team.config.json       #    行为配置（看板列 / 泳道 / 门禁 / 限制）
│   ├── workflow.json          #    整体流程：阶段 + 门禁链 + 交接规则
│   ├── project-role.json      #    项目自身角色（不属于任何团队）
│   ├── session-defaults.json  #    单角色调用（/myteam+id）的会话默认值
│   ├── roles/<roleId>.json    #    角色
│   ├── teams/<teamId>.json    #    团队（名册模板；旧目录名 presets/）
│   ├── skills/<skillId>.json  #    项目技能
│   ├── tools/<toolId>.json    #    工具策略（只能收窄）
│   └── knowledge/             #    团队知识库（index.json + <topic>.md）
├── tasks/                     # ② 任务及依赖 —— 入库
│   ├── <teamId>/ledger.jsonl  #    append-only 账本（任务/依赖的唯一权威）
│   └── <teamId>/team.config.json  # 团队级生效配置（建团时按模板落盘）
├── history/                   # ③ 整体流程过程 —— 不入库
│   ├── archive/<teamId>/      #    归档快照（MANIFEST/team/tokens/members/artifacts）
│   ├── tokens/<teamId>.json   #    token 计量侧车
│   └── members/<teamId>/<memberId>/  # 身份快照 + 私有记忆（memory/）
├── state/                     # 运行时派生数据 —— 不入库
│   ├── teams.json             #    工作区索引（可从账本重建）
│   ├── scratch/<teamId>/<memberId>/
│   └── logs/
└── export/                    # 导出快照 —— 不入库
```

### 2.1 上传纪律（`.dsh-myteam/.gitignore`）

| 能上传（随仓库共享） | 不能上传（clone 后自动重建） |
|---|---|
| `manifest.json`、`README.md`、`structure.md` | `state/`（索引 / scratch / 日志） |
| `config/`（角色 / 团队 / 技能 / 工具 / 流程 / 知识） | `history/`（归档 / token 计量 / 成员记忆） |
| `tasks/`（任务与依赖账本） | `export/`、`*.tmp` |

**为什么放在存储目录里**：用户明确要求「在该文件夹下设置一个 `.gitignore` 文件」。
放到项目根会污染用户仓库（旧实现还顺手在 profile 目录里写了一条垃圾规则）。

## 3. 作用域矩阵（CHG-103，用户定案）

「任务、历史、状态这些内容只有项目级别才有；全局级别只有团队、角色和角色内的东西，knowledge 也可以有。
历史、状态、导出明显就是项目级别的任务。」

| 内容 | 全局（`$DSH_HOME/myteam/`） | 项目（`<project>/.dsh-myteam/`） |
|---|---|---|
| 角色 `roles/` | ✅（跨项目可见，**必须明示**） | ✅ 默认 |
| 团队模板 `teams/` | ✅ | ✅ |
| 技能 `skills/` | ✅ | ✅ |
| 工具策略 `tools/` | ✅ | ✅ |
| 知识 `knowledge/` | ✅ | ✅ |
| 团队运行期配置 `team.config.json` | ❌ 项目级专属 | ✅ |
| 流程 `workflow.json` | ❌ | ✅ |
| 任务与依赖 `tasks/<teamId>/ledger.jsonl` | ❌（append-only 单写者，跨项目没有语义） | ✅ |
| 历史 `history/`（归档 / token 计量 / 成员记忆） | ❌ | ✅ |
| 状态 `state/`（索引 / scratch / 日志） | ❌ | ✅ |
| 导出 `export/` | ❌ | ✅ |
| 成员实例 `history/members/` | ❌ | ✅ |

守卫：`core/workspace/scope.ts` 的 `assertWritableAtScope(scope, kind)` —— 项目级专属内容传 `global`
一律 `MT_SCOPE_PROJECT_ONLY`（拒绝式，附「全局只有哪五类」）。**任何写路径都必须过这道门。**

### 3.1 全局角色的创建规则（用户第 1~3 条）

| 用户指令 | 行为 |
|---|---|
| 没提「全局」（「建个架构师」） | **只建项目级**（`scope` 缺省 = `project`）——这是绝大多数情况，不许猜 |
| 明确说「全局 / 所有项目共用 / 放全局库」 | 可以建全局：先 `scope:"global"` 不带确认 → 返回 `confirm-required`，把影响面讲给用户，**用户确认后**再带 `confirmGlobal:true` 落盘 |
| 含糊（「给我搞个角色，别的地方也能用」） | 先弹窗问清作用域；问到「全局」再按上一条走 |

代码落点：`myteam_create_role` / `myteam_update_role` / `myteam_delete_role` 的 `scope` + `confirmGlobal`
参数；`core/roles/role-ops.ts` 的 `save`/`delete` 分支；面板 `saveRole`/`deleteRole` 走同一份实现。

## 4. 项目根解析（唯一入口 `resolveProjectRoot`）

优先级（`plugin/src/core/workspace/layout.ts`）：

1. **会话工作目录**（`agents.currentInitiator().session.cwd` / `workspaceDirectory.get`）——最权威；
2. 行 config 显式 `workspaceRoot`（单测 / 运维兜底）；
3. 宿主 `workspace.root`——**必须先过 `rejectProjectRoot`**；
4. 进程 cwd（兜底，记 warn）。

`rejectProjectRoot` 硬规则：路径落在 `$DSH_HOME`（缺省 `~/.dsh`）内 → 拒绝并告警。
这是 P0-1 的回归防线：**DSH profile 永远不是项目**。

## 4. 面板作用域（P0「所有项目看起来都一样」）

| 作用域 | 数据面 | 纪律 |
|---|---|---|
| 全局 | 内置角色 + `$DSH_HOME/myteam/roles` + 插件贡献 | 只读展示；**不**代表本项目已有团队 |
| 项目 | `getProject({workspaceRoot})`：本项目 `.dsh-myteam/` 的团队/任务/角色 | 只读本项目；**不合并**跨工作区全局索引 |
| 项目未初始化 | `getStoreState({workspaceRoot})` → `initialized:false` | 只画一屏空态 + 「初始化 .dsh-myteam」（`initStore` 只建目录与元文件，不建团队不写账本） |

**空态门**：`scope === 'project' && !storeState.initialized` 时，一个角色/团队/任务都不渲染——
否则内置角色与全局库会被误读成「这个项目已经有团队了」。

## 5. 迁移（一次性、幂等）

`ensureStore()` 在初始化时执行 `migrateLegacyStore()`：

1. 存在 `.team-workplace/` 且 `.dsh-myteam/` 不存在 → `rename` 整目录；
2. 旧 `config/presets/` → 新 `config/teams/`；
3. 清掉项目根 `.gitignore` 里的旧托管块（只删自己那几行，保留用户规则）；
4. 跨设备 rename 失败 → 保留旧目录 + 告警，**不静默丢数据**。

| 队长技能（建角色 / 建团队 / 写章程） | `plugin/src/core/roles/captain-skills.ts` |
