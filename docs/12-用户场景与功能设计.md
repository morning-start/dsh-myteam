## 0. 用户、入口与边界

| 维度 | 现状 |
|------|------|
| 用户在哪 | DSH 桌面 GUI：侧栏 **myteam** → 面板（全局 / 项目两作用域） |
| 谁在写 | **面板内日常写入口（CHG-72）**：任务新建/编辑/指派/协作（走账本，`actor=human`）、角色新建/编辑（配置资产，两段确认 + 审计）、暂存裁决/队员三态/解散/留言；**建团队与结构重规划仍走「团队模式」队长会话**（建队只做引导与预填首条消息，ADR-006 R1） |
| 权威数据 | 团队与任务：账本 `ledger.jsonl`（append-only，可重放）；角色/模板/配置：项目内 JSON 文件 |
| 两个身份 | 人类用户（点面板、开会话）；队长（LLM，在团队模式会话里调工具） |

关键结论：**面板已经能完成建队引导、建/改任务、建/改角色这些日常操作**（CHG-72）；**建团队本身与结构重规划仍由队长会话承担**——团队必须经 `submit_plan` + 人工批准产生（ADR-005 R2 不变）。

## 1. 场景一：用户如何自己创建一个团队

### 现状（可走通，但绕）

1. 用户新建一个「团队模式」会话（`myteam-captain` 预设）。
2. 对队长说：「建一个团队：目标 X，用标准三人组模板」。
3. 队长调 `myteam_submit_plan`（可选 `presetId` 模板）→ 落 `team.created` + `plan.staged`，团队进入 **draft**。
4. 面板出现「草稿待批准」横幅 → 用户点 **Approve & Run**（或让队长批准）→ 召唤队员、计划任务入库，团队进入 **active**。
5. 面板「项目 · 团队」里出现该团队，进入后可看队员 / 参与任务 / 知识 / 审计 / 设置。

### 缺口

- **G1 入口断层**：面板团队列表空态只说「去团队模式会话创建」，没有一键跳转或预填提示；新用户不知道该开哪个预设。
- **G2 待批准不可见**：草稿批准只在该团队页的横幅里；团队列表/全局没有「待你批准」角标。
- **G3 改名/改目标无入口**：本轮已加工具 `myteam_update_team`（`team.updated`），但面板还不能点。
- **G4 空团队语义没暴露**：`submit_plan` 允许空任务（CHG-16），但 UI 没有「先建队、后加任务」的路径提示。
- **G5 模板与名册的关系不直观**：模板（`presetId`）会锁定名册与看板列/门禁；自定义名册又得逐条写 `roleId`。

### 目标流程（建议）

1. 面板「团队」tab 空态 + 顶部「新建团队」按钮。
2. 点击 → 二选一（按投入分级）：
   - **P1（低成本）**：打开/聚焦一个团队模式会话，并把「团队名 + 目标 + 模板」预填成首条消息（不新增写路径）。
   - **P2**：面板内表单（团队名 / 目标 / 模板下拉（预设目录）/ 名册（角色库多选，队长固定）/ 可选初始任务）→ 调用队长工具（需要一次面板写边界修订，见 §5）。
3. 提交后团队为 **draft**；面板团队列表顶部出现「待批准」区（含影响面：将召唤 N 名队员、入库 M 个任务）。
4. 批准 → active；列表/头部/索引同步（已具备）。
5. 团队页「编辑」→ 改名/改目标（`myteam_update_team`，已有）；「解散」保持两段确认。

### 验收

- 新用户从零到 active 团队 ≤ 3 步，且全程不需要记 preset 名称。
- 空团队可建、可后补队员与任务；草稿在列表可见可批准。
- 改名后列表、团队头、索引、面板参与任务页同时更新。

## 2. 场景二：如何创建角色

### 现状（能力有，入口是「跟队长说」）

- 队长技能 `create-role` / `modify-role`，工具 `myteam_create_role` / `myteam_update_role`（CHG-53/69）。
- 写 `.team-workplace/config/roles/<id>.json`，字段：`id/name/description/systemPrompt/toolPolicy/skills/mcpAllowlist/interestWords/model/version`。
- 内置/全局角色只读；运行时只认项目库（引用即复制，`copyToProject`）；运行中成员用身份快照，不受后续修改影响。

### 缺口

- **G1 没有表单**：提示词、边界、技能、MCP、兴趣词全要用户口述，队长代填，来回多轮。
- **G2 没有即时校验**：id 规则、提示词非空、兴趣词 ≤8 个、技能/MCP 是否存在、工具策略只能收窄——现在只有工具报错，用户看到的是错误码。
- **G3 fork 不可见**：想改内置角色，不知道要先复制进项目。
- **G4 没有「这个角色适合什么任务」的预览**（兴趣词与 `requiredRole` 的匹配关系）。

### 目标流程（建议）

- 角色库页「新建角色」→ 表单：
  - 基本信息：id（自动从名称派生、可改）、名称、职责一句话。
  - 设定：系统提示词（多行）、兴趣词（chips 输入，≤8）、工具策略（默认 `myteam_*`）。
  - 能力：技能多选（宿主技能目录）、MCP 多选（已连接 server）、模型路由（可空）。
- 保存路径（二选一，建议 A）：
  - **A. 面板直接写文件**：复用 `assertValidRole` + 名称解析校验，写 `config/roles`。角色是配置资产、不参与账本单写者；需要一次显式的边界修订（ADR-006：面板写 = 仅配置资产 + 两段确认 + 审计行）。
  - **B. 表单生成结构化指令**发给队长执行：零新写路径，但体验割裂、错误回传慢。
- 「复制到项目」入口：内置/全局角色卡 → 一键 fork（已有 `copyToProject`）。
- 保存后提示影响面：在跑实例不变；下次召唤生效。

### 验收

- 3 分钟内建出一个可用角色（含提示词与兴趣词），错误就地提示。
- 内置角色可一键复制后修改，原文件不被写。
- 角色卡、任务详情「派单依据」、审计里都能看到兴趣词。

## 3. 场景三：如何创建一个任务，让整个团队去执行

### 现状（本轮才真正走通）

- 队长 `myteam_create_task`（或 `submit_plan.tasks` 内联）→ `task.created`，任务进 **backlog**；deps 全 done 时进入 **ready**。
- 成员只能 claim（角色匹配 + deps done + 优先级 + FIFO），一次一个 attempt。
- **CHG-71 新增派单唤醒（dispatch）**：任务新建/上游完成解锁/重规划后，若该角色有空闲成员，host 主动 wake 一名（节流 400ms/团队、3s/成员）；否则团队会停在原地（此前只有 assign/message/resume/revoke 四种唤醒）。
- **CHG-71 同时修了门禁链终态**：自定义链最后一道不是 `archive`（如只有 `review`）时，旧状态机不允许 `gate:review → done`，任务会卡死；现在任意 `gate:*` 最后一道 pass 都可 done。

### 缺口

- **G1 面板不能建任务**：只能回队长会话；且一次建任务要「创建 → 指派 → 登记协作」三次调用，中间态可见。
- **G2 看不到「为什么没人领」**：任务卡没有「角色不匹配 / 成员都在忙 / 依赖未完成」诊断。
- **G3 指派 ≠ 执行**：`assign_task` 只标注负责队员，不改 claim 语义，用户容易误解为「派给他了」。
- **G4 没有批量编排**：一个目标拆 10 条任务、依赖关系、并行度，目前全在队长提示词里。

### 目标流程（建议）

1. 任务 tab →「新建任务」表单：标题、描述、AC（逐条）、交付物、依赖（选已有任务，实时环检测）、所需角色（名册）、优先级、门禁链（模板默认/自定义）、**负责队员（多选）**、**协作团队（多选）**。
2. 一次提交（建议扩展 `myteam_create_task` 支持 `assignees[]` / `participants[]`，避免三连调用）。
3. 就绪判定：无依赖 → 立即 ready；有依赖 → 上游 done 时自动 ready。
4. 派单：dispatch 唤醒匹配角色的一名空闲成员 → 成员 claim → in_progress；面板显示执行者、attempt、进度、证据。
5. 无人可领时任务卡显示诊断（例如「名册缺少 reviewer」「implementer 正在跑 t3」）。

### 验收

- 建任务后 ≤ 5s 有成员 claim，或给出明确「无人可领」原因。
- 上游完成 → 下游自动 ready 且有人被唤醒。
- 看板/列表/DAG/团队「参与任务」四处对同一任务的状态一致。

## 4. 场景四：执行过程中如何编辑和补充任务

### 现状（CHG-70/71/73）

- 元数据编辑（标题/描述/优先级/体量/标签）：随时可改，落 `task.updated`，**不改状态机 / attempt / 证据**。
- **结构字段**（AC / 交付物 / 依赖 / 所需角色 / 门禁链）：
  - 任务未开跑：直接改。
  - 任务 in_progress 或在门禁：**拒绝** `MT_TASK_STRUCTURAL_EDIT`，必须走 `rescope`。
- **一键重新规划（CHG-73）**：`myteam_rescope_task` / 面板「重新规划」= 撤当前 attempt → 任务回 ready（新依赖未完成则回 backlog）→ 可选带结构补丁 → 可选重派队员；**理由必填**；终态任务（done/failed/cancelled）拒绝。
- **改动可读（CHG-73）**：每次编辑把字段级 diff 一起落账（`changes: [{field, from, to}]`），任务详情有「改动记录」（谁、何时、改了什么、为什么）。
- **证据过期（CHG-73）**：结构字段一改、而此前已有证据 → 投影打 `evidenceStale`（看板卡徽标 + 详情横幅「证据早于本次定义变更」）；新证据覆盖后自动清除。
- **取消任务（CHG-73）**：`myteam_cancel_task` 两段确认（先给影响面：下游清单 + 是否有活跃 attempt），理由必填；下游策略 `leave`（只停本任务，下游诊断报「上游已取消」）/ `cancel`（级联取消下游闭包）；落 `task.cancelled` 终态。
- **取消后重接线（CHG-75，P3）**：取消时第三档 `downstream:'rewire'`——把**直接下游**的依赖改挂到新上游（不指定新上游 = 解除依赖让下游变独立任务）；落 `task.rewired`（每条下游一条独立事件，可逐条审计）；改挂非法（新上游不存在/自身/已取消/成环 `MT_TASK_CYCLE`）在**取消落账前**就被拒，不留「上游已死、下游还挂着」的半吊子状态；解除依赖后若已无待完成依赖，下游从 backlog 进 ready。
- **批量编排（CHG-73）**：`myteam_batch_task_op` 对多任务执行同一操作（cancel / rescope / assign / priority），逐条独立落账（同一 `batchId`），部分失败不影响其余，面板逐条回显结果。
- **批量档的下游策略（CHG-76）**：批量取消也支持三档——`leave` / `cancel` / **`rewire`**（整批统一改挂到 `rewireTo`，缺省 = 逐条解除依赖）；`rewireTo` 在本批要取消的任务里 → 整批拒（否则改挂完立刻又死）。
- **从目标出草稿（CHG-76）**：「写一批任务」不再是一条条建——`myteam_create_tasks` 收草稿列表，`after` 声明批内依赖，预览给影响面（条数/角色分布/名册缺角色/依赖边/补齐项），确认后按拓扑序逐条落账；缺 AC / 叶子缺交付物自动补齐并留痕。
- **无人可领的一键修复（CHG-76）**：诊断不只说"为什么没人领"，还给 `fix`——同角色有人空闲就指派、名册里有别的空闲角色就换角色、都没有就提示召唤；动作仍走既有 `assignTask` / `updateTask` 管线（不新增写路径）。
- 编辑后：若任务在执行，host 会给当前执行者一条 `task-updated` 提醒（重读任务再继续）。
- 补充信息：队长 `myteam_message` 发给成员；人类可在面板任务详情留言（`message.sent`，actor=human）。

### 缺口

- 无（G1~G5 已在 CHG-72/73 关闭；G6 的「重接线」已在 CHG-75 关闭）。
- **G6 剩余**：跨团队 claim 与主责迁移仍不支持（协作团队只能被指定队员、不能执行）。

### 目标流程（已实现，供复核）

1. 任务详情 →「编辑」：元数据直接保存；结构字段若在执行 → 面板给「保存并重新规划」（理由必填）或「只保存元数据」两个出口。
2. 重新规划：撤 attempt → 回 ready → 重新派单；账本记 `task.attempt.revoked` + `task.rescoped`（含 reason 与 changes）。
3. 详情「改动记录」渲染字段 diff（`acceptanceCriteria: 1 条 → 2 条`）；看板卡出现「证据已过期」徽标。
4. 取消任务：两段确认 → `task.cancelled`（含 reason / downstream）；下游任务诊断报「上游已取消」。
5. 批量：看板多选 → 底部操作条（取消 / 重新规划 / 指派 / 改优先级）→ 逐条回显成功与失败原因。

### 验收

- 跑中改 AC 必须经 rescope，且执行者收到通知；审计能看到「谁、为什么、改了什么」。
- 改依赖后 DAG 立即更新且无环（已校验）。
- 取消任务后下游状态明确（有诊断「上游已取消」，不留悬空依赖无提示）。
- 交付后改 AC → 证据过期徽标出现；重新提交证据后消失。

## 5. 数据与接口增量

### 已实现（CHG-71）

| 项 | 说明 |
|---|---|
| `task.updated` / `team.updated` | 账本 37 型；白名单补丁；团队名/目标编辑 |

| 门禁链终态 | 任意 `gate:*` 最后一道 pass → done（修「自定义单门链卡死」） |

| 项 | 落点 |
|---|---|
| 面板「新建团队」引导 | 团队页空态/工具条 → 抽屉（名称/目标/模板）→ `uiWorkspace.startSession({agentPreset:'myteam-captain', prompt})` 预填首条消息；无工作区入口时复制指令 |

### 已实现（CHG-73，P2 收口）

| 项 | 落点 |
|---|---|
| 一键重新规划 | 工具 `myteam_rescope_task` + 门面 `rescopeTask`；撤 attempt → ready/backlog → 可选结构补丁 → 可选重派；理由必填；终态拒绝；撤 attempt 现在也能离开门禁态（旧实现 gate:* 撤销后卡死） |

| 角色删除（C7 守门） | `deleteProjectRoleSafe`：只能删项目库、captain 不可删、被模板/团队/项目自身角色占用则拒绝并列占用方；两段确认 + `.audit.jsonl`（action=deleted）；门面 `deleteRole`；`getProject().roles[].canDelete` |
| 技能 / MCP 目录 | 门面 `getCapabilityCatalog`：宿主 skills 服务 + 工具表 `mcp__<server>__*` 推导，读不到降级为「已有角色声明」并如实回 warnings；角色表单做 chips 多选 + 自由输入（目录不是白名单） |
| 动作可用性由服务端算 | `BoardTaskView.actions` / `TaskDetailView.actions`（{rescope, cancel, edit}）：终态不可重规划/取消，cancelled/failed 连编辑也没有意义——UI 不重复实现状态机规则 |

### 已实现（CHG-75，P3：取消后重接线）

| 项 | 落点 |
|---|---|
| 账本事件 `task.rewired` | payload：`teamId`/`taskId`/`removed`/`reason` 必填 + 可选 `added`；落账顺序 = 先 `task.cancelled` → 再逐个直接下游一条 `task.rewired`（每条独立事件，可逐条审计/重放） |
| 改挂语义 | `removed` = 被换掉的依赖；`added` = 新上游，**缺省 = 解除依赖**（下游变独立任务）；只改**直接下游**，传递下游随链条自动受益 |
| 预检先于不可逆写 | 新上游必须存在、非 cancelled/failed、不能是它自己、改挂后不成环（`MT_TASK_CYCLE`）；**不合法时取消也不落账**（不留半吊子状态） |
| 状态推进 | 解除依赖后若已无待完成依赖 → `backlog → ready`（看板列与 claim 口径一致） |
| 面板 | `CancelDialog` 第三档「改挂到新上游」+ 上游下拉（候选 = 同团队未取消任务，空 = 解除依赖）；影响面文案分三档；成功后提示「已改挂 N 个」 |
| 视图 | 详情 `rewiredFrom {removed, added?, ts}`（依赖已从 X 改挂到 Y）；看板 `rewired` 标记 |

### 已实现（CHG-76，P3：批量改挂 / 批量建任务 / 无人可领一键修复）

| 项 | 落点 |
|---|---|
| 批量取消的重接线档 | `myteam_batch_task_op` 的 `downstream` 增 `rewire` + `rewireTo`：整批统一新上游（缺省 = 逐条解除依赖）；预览 `impact.rewireByTask[{taskId,directDependents}]` 逐任务列出要被改挂的直接下游，确认后 `results[].rewired` 逐条回显 |
| 批量级前置校验 | `rewireTo` 不能是本批要取消的任务（改挂到即将取消的任务 = 把死锁换个位置）、不能不存在/已取消/失败 → 整批 `MT_VALIDATION`，账本一笔取消都不落；同批里自己也要取消的任务不算"要改挂的下游"（`rewireSkip`） |
| 批量建任务（从目标出草稿） | 工具 `myteam_create_tasks` + 门面 `createTasks`：草稿列表 → 预览 `impact{tasks,byRole,rolesMissing,edges,ids,warnings}` → 两段确认后逐条 `task.created`（同一 `batchId`）；`after` 用本批 1-based 序号声明批内依赖，服务端按拓扑序创建（自指/越界/成环 `MT_TASK_CYCLE` 拒绝且不写账本） |
| 草稿缺省补齐并留痕 | 缺验收标准 → 「完成「标题」」；叶子任务缺交付物 → `docs/<taskId>.md`；都写进 `warnings`（草稿阶段卡"必须先想好验收标准"只会让人放弃批量） |
| 部分失败语义 | 一条失败不影响其余；依赖失败条目的后续条目 → `MT_DEPENDENCY_FAILED`「依赖的第 N 条没建成，本任务跳过」（不留悬空依赖） |
| 无人可领一键修复 | 诊断 `fix{assignable,roleSwap,spawnRole}`（`core/tasks/readiness.ts` 纯投影推导）：同角色有人空闲 → 指派（`assignTask`）；名册里有别的空闲角色 → 改 `requiredRole`（`updateTask`）；都没有 → 提示召唤。`team-inactive` / `dep-cancelled` 不给 `fix`（前者做什么都没用、后者的出口是重新规划/改挂） |
| 面板 | 批量条三档下游策略（leave/cancel/rewire）+ 新上游下拉 + 三档影响面；任务页「批量新建」抽屉（草稿行 → 预览 → 创建）；详情诊断区「一键修复」动作（指派 / 换角色 / 召唤提示），离线团队一律 disabled |
| 边界（如实登记） | 面板在**跨团队混选**时禁用「改挂到新上游」档（`rewireTo` 是单值，同一个上游对另一个团队非法会整批拒）——提示「先按团队筛选再批量取消」；批量新建的 `requiredRole` 只能选团队在册角色（同单条 create 约束）；批量新建部分失败后抽屉仍关闭，失败原因进 notice |
