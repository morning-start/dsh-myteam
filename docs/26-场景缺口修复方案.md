## 0. 为什么是这些、按这个顺序

排序依据三条：

1. **用户伤害**：数据被污染 > 状态卡死 > 看不懂错误 > 体验不顺
2. **改动风险**：纯后端 < 加事件 < 改状态机 < 改协议
3. **依赖关系**：错误码透传是后面所有「让用户看懂」的前提；身份校验是权限类修复的前提

**一条贯穿全程的纪律**：所有「写了、测了、没接线」的债，都靠批 0 的门禁守住。清一条就把 `maxTodo` 下调一条，防止假进度。

## 8. 明确不做（写下来防止反复讨论）

| 不做 | 理由 |
|---|---|
| **跨文件事务 / WAL** | 参考项目两家都没有；成本远高于收益，且账本追加本身是单文件原子 |
| **可逆归档（un-archive）** | 两家都没有；只做「只读回看入口」，这才是真实需求 |
| **token 预算 / 熔断** | 缺「一次成员 turn 大概烧多少」的实测依据，先只暴露数据 |
| **账本链式完整性（prev + 重放重验）** | 威胁模型是「AI 或误操作改 jsonl」，不是外部攻击者；改动面大，留待后续 |
| **跨团队 claim / 主责迁移** | docs/12 已列为 P3，不在本轮 |
| **死 CSS 清理** | 需要可靠的 DOM 遍历器，独立议题 |
