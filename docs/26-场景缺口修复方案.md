## 0. 为什么是这些、按这个顺序

排序依据三条：

1. **用户伤害**：数据被污染 > 状态卡死 > 看不懂错误 > 体验不顺
2. **改动风险**：纯后端 < 加事件 < 改状态机 < 改协议
3. **依赖关系**：错误码透传是后面所有「让用户看懂」的前提；身份校验是权限类修复的前提

**一条贯穿全程的纪律**：所有「写了、测了、没接线」的债，都靠批 0 的门禁守住。清一条就把 `maxTodo` 下调一条，防止假进度。

### ⓒ 6.4b 级联释放真正归还任务

**现状**：`drained.running` 已改成按 `currentTaskId` 真算（CHG-210 批 6.4a），但**只记录不归还**——子成员手上跑着的任务仍留在 `in_progress`。

**做法**：在 `runWithRollback('release-cascade', ...)` 的循环里，`commit` 释放事件**之前**，若该成员有 `currentTaskId`：

```ts
const runningTaskId = proj.members[id]?.currentTaskId
if (runningTaskId) {
  const t = proj.tasks[runningTaskId]
  // 撤票据（attemptId 不清会让任务回 ready 也领不走——见 task.gate.result fail 分支的注释）
  this.commit(teamId, { actor, type: 'task.attempt.revoked', payload: { teamId, taskId: runningTaskId, attemptId: t?.attemptId, reason: 'cascade-release' } })
  // 回 ready 需要「清 attemptId + 转移」——现有 fold 里 `task.attempt.revoked` 不负责这件事，
  // 所以要么补一个 `task.released` 事件，要么复用 rescope 管线（推荐后者，语义已经是「撤下重排」）
}
```

**卡点**：和 5.5 同源——**「回 ready」目前只在 `task.gate.result` 的 fail 分支里发生**，没有通用入口。所以 ⓒ 的正确做法可能是**先做 ⓓ 的状态出口**，再回来用它。

### ⓓ 5.5 任务暂停（要新状态，单独一轮）

**已探明**（上一轮结论）：`task.attempt.revoked` **不**让任务回 `ready`；全仓只有一处 `transition(t, 'ready')`（gate fail 回流）。所以「暂停」必须新造状态。

**改动清单**（4 个 core 文件 + 4 处断言）：
1. `core/ledger/ledger.ts` 的 `EVENT_TYPES` 加 `'task.paused'`（参照 `'task.blocked'` 那行）
2. `core/scheduler/state.ts`：`TaskState` 加 `'paused'`；`LEGAL_TRANSITIONS` 加 `in_progress → paused`、`paused → ready / backlog / cancelled`；`TaskProjection` 加 `pausedAt` / `pausedReason`（参照 `blockedAt` / `blockedReason`）
3. `core/scheduler/fold.ts` 加 `case 'task.paused'`（清 `attemptId` + `transition(t, 'paused')`）
4. `host/tasks.ts` 的 `update` 加分支：`const eventType = ... : status === 'paused' ? 'task.paused' : 'task.failed'`，payload 带 `reason`；**这一步不动 `host.ts`（A6 安全）**
5. 修复断言：`toolsByTier` 类工具契约锁不受影响，但凡是遍历 `TaskState` 的测试（看板列、状态机断言）都要更新

**验收**：claim → pause → 任务离开 in_progress 且可被再次 claim；pause 后再 claim 拿到新 attemptId；`gate:*` 状态不允许 pause（明确报错）。

| `preset-minimal` | 显式列 `tool-fs` 且 `read: false` | 证明**不列就是没有** |

**后果**：队长会话能调 60 个 `myteam_*`，但读不了项目文件、写不了 `structure.md`、跑不了命令。

### CHG-211a：第一次修法把 preset 弄没了（用户实测发现）

`tool-fs-search` 那行漏了 `sampleOverCapGlobResults`，于是：

| 项 | 事实 |
|---|---|
| 实际诊断 | `tool-fs-search (@deepseek-ai/dsh-tool-fs-search): invalid config:\n  - $.sampleOverCapGlobResults missing required value` |
| 后果 | preset 被判 `broken`，**「团队模式」从新建会话的 preset 选择器里静默消失**（用户报「现在没有团队模式预设了」） |
| 为什么静默 | `dsh-client-ui-agent-preset/src/client/settings-store.ts` 的 `presetOptions()` 只返回 `broken === undefined` 的行；broken 只在**设置页的预设管理**里可见 |
| 为什么门禁没抓到 | `dsh --dump-config` 只组合 YAML，**不校验每行 config 的 schema**；仓库单测不挂真实 DSH preset |
| 正确修法 | 补 `config: { sampleOverCapGlobResults: false }`（与 `preset-standard` 同值）——该字段**必填且无 schema 默认值** |

**判据教训**：`dump-config` 里有这行 ≠ 这行能挂载。要证明 preset 可用，必须读
`agentPresets.list()` 的 `broken` 字段（客户端选择器用的就是它）。

**自查方法**（一次性探针，不进仓库）：用一个 `inject: ['agentPresets']` 的插件，
在真实 profile 里延时调 `ctx.agentPresets.list()` 打印 `{id, broken}`：

```js
export const inject = ['agentPresets']
export function apply(ctx) {
  setTimeout(async () => {
    console.log(JSON.stringify((await ctx.agentPresets.list()).map(r => ({ id: r.id, broken: r.broken })), null, 2))
  }, 4000)
}
```

`name: 'file:///…/index.mjs'` 通过 `--patch` 插进 profile 顶层即可（不必改仓库）。

修复后实测：`{ "id": "myteam-captain", "name": "团队模式" }`——无 `broken`。

**成员侧并不是「无此问题」**（本轮可用性实测推翻了这个判断）：`agents.create` 让成员继承的
是**根 host 工具面**，preset 里追加的工具到不了成员。详见 CHG-212。

## CHG-212：真实可用性测试（P0-1）——成员只能思考、不能动手

**测试口径**：真模型 / 真团队 / 3 个任务 / 跑到 `done`，全程走工具面。结果 **7/9 环节通过，卡在第 8 步**。

| # | 环节 | 结果 |
|---|---|---|
| 1–6 | 建队 → 澄清落账 → 批准召唤成员 → 成员真实唤醒（token 计量）→ claim → 派单送达 | ✅ |
| 7 | **产出交付物** | ❌ 一个文件都没有；成员主动 escalate 报「无命令执行、无文件写入」 |
| 8 | done / 门禁 | ⛔ 无交付物到不了 |
| 9 | escalate 上报 | ✅ 理由 300+ 字，质量很高 |

### 根因（决定性对照）

| | 工具面 |
|---|---|
| 队长会话 | 根层工具 **+ preset 追加项**（CHG-211 的 fs）→ 有 read/write/edit |
| **成员会话** | **只有根层工具**（它自己列出设计类 / MCP / github / session / memory）→ **无 fs、无 shell** |

`agents.create` 继承的是 **root 工具面**；`setup` 里只注册成员工具 + `restrict` 收窄，没有任何工具来源。
所以 CHG-211 把 fs 只加进 preset，等于只修好了队长。

### 修法（本提交，零代码：全在 `plugin/cordis.patch.yml`）

把能力开在**根层**，让队长与成员同时继承：

```yaml
- id: tool-fs          # disabled: false（base/web-app 层原本是 true，只写 config 打不开）
- id: tool-fs-search   # disabled: false + sampleOverCapGlobResults（必填无默认）
- id: tool-pwsh        # win32 开
- id: tool-bash        # 非 win32 开
```

preset 里 CHG-211 加的两行**删掉**——重复声明 = 两处配置漂移；preset 变体仍可遮蔽根层
（`preset-minimal` 的 `read: false` 照旧生效）。

**实测验证**（mt-desk = desktop profile 副本 + 探针）：

```
PROBE_PRESETS  7 个 preset 全部无 broken
PROBE_ROOT_TOOLS total=90
  read=true write=true edit=true glob=true grep=true
  pwsh=true bash=false(非 win32 关闭) apply_patch=false
```

成员继承 root → 拿到同一组工具。

### 同一轮实测暴露的其余缺陷（按状态）

| # | 缺陷 | 状态 |
|---|---|---|
| 1 | `myteam_read_session` 炸 `signal.throwIfAborted` | ✅ **本提交修复**：`resolveSessionHistoryCapability` 补 never-abort `AbortSignal`（宿主实现无条件调用，类型却标可选）；回归锁 `t93-4b` |
| 2 | `escalate` 理由在 `read_task` 时间线不可见（只有 `{seq,ts,actor,type}`） | ❌ 未修。理由在账本 `payload.reason` 里，投影层没带出来——**队长裁决时看不到理由**，等于 P0 |
| 3 | project root 跟的是**进程 cwd**，desktop 下 = `~/.dsh/profiles/desktop` | ❌ 未修。`initialize()` 在建队前就取 `workspaceRoot`，此时 `agents.currentInitiator()` 无会话 → 全部候选被 `rejectProjectRoot` 拒 → 兜底 `resolveProjectRoot` **仍然返回被拒的 cwd** 并缓存。修它要动「启动期解析 vs 会话期解析」+ 存量团队迁移，单独排期 |
| 4 | token 侧车 `calls` 恒 0 | ❌ 未修。宿主 `tokenUsage` 投影 `totals` **只有四桶、没有 `calls` 字段**（`dsh-token-meter/src/usage-projection.ts:39-46`）。不是取值写错，是宿主没这个能力；要么改口径（按 `assistant/message` 计数），要么标注「不可用」 |
| 5 | `member.spawned` 每成员两条（lead provisioning + host active） | ❌ 未修。审计计数会失真 |
| 6 | `deps` 只接受 `task-N`，不接受计划里的 `taskKey` | ❌ 未修。提交时 `dep "T1" does not exist`，与用户自然写法冲突 |

**结论**：P0（成员没有手）已解，P1 读面已解。剩下 4 项里，**#2 escalate 理由**与 **#3 project root** 是下一步优先级最高的两条。
