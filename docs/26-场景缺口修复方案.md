## 0. 为什么是这些、按这个顺序

排序依据三条：

1. **用户伤害**：数据被污染 > 状态卡死 > 看不懂错误 > 体验不顺
2. **改动风险**：纯后端 < 加事件 < 改状态机 < 改协议
3. **依赖关系**：错误码透传是后面所有「让用户看懂」的前提；身份校验是权限类修复的前提

**一条贯穿全程的纪律**：所有「写了、测了、没接线」的债，都靠批 0 的门禁守住。清一条就把 `maxTodo` 下调一条，防止假进度。

### ⓒ 6.4b 级联释放真正归还任务

**现状**：`drained.running` 已改成按 `currentTaskId` 真算（CHG-210 批 6.4a），但**只记录不归还**——子成员手上跑着的任务仍留在 `in_progress`。

**做法**：在 `runWithRollback('release-cascade', ...)` 的循环里，`commit` 释放事件**之前**，若该成员有 `currentTaskId`：

```ts
const runningTaskId = proj.members[id]?.currentTaskId
if (runningTaskId) {
  const t = proj.tasks[runningTaskId]
  // 撤票据（attemptId 不清会让任务回 ready 也领不走——见 task.gate.result fail 分支的注释）
  this.commit(teamId, { actor, type: 'task.attempt.revoked', payload: { teamId, taskId: runningTaskId, attemptId: t?.attemptId, reason: 'cascade-release' } })
  // 回 ready 需要「清 attemptId + 转移」——现有 fold 里 `task.attempt.revoked` 不负责这件事，
  // 所以要么补一个 `task.released` 事件，要么复用 rescope 管线（推荐后者，语义已经是「撤下重排」）
}
```

**卡点**：和 5.5 同源——**「回 ready」目前只在 `task.gate.result` 的 fail 分支里发生**，没有通用入口。所以 ⓒ 的正确做法可能是**先做 ⓓ 的状态出口**，再回来用它。

### ⓓ 5.5 任务暂停（要新状态，单独一轮）

**已探明**（上一轮结论）：`task.attempt.revoked` **不**让任务回 `ready`；全仓只有一处 `transition(t, 'ready')`（gate fail 回流）。所以「暂停」必须新造状态。

**改动清单**（4 个 core 文件 + 4 处断言）：
1. `core/ledger/ledger.ts` 的 `EVENT_TYPES` 加 `'task.paused'`（参照 `'task.blocked'` 那行）
2. `core/scheduler/state.ts`：`TaskState` 加 `'paused'`；`LEGAL_TRANSITIONS` 加 `in_progress → paused`、`paused → ready / backlog / cancelled`；`TaskProjection` 加 `pausedAt` / `pausedReason`（参照 `blockedAt` / `blockedReason`）
3. `core/scheduler/fold.ts` 加 `case 'task.paused'`（清 `attemptId` + `transition(t, 'paused')`）
4. `host/tasks.ts` 的 `update` 加分支：`const eventType = ... : status === 'paused' ? 'task.paused' : 'task.failed'`，payload 带 `reason`；**这一步不动 `host.ts`（A6 安全）**
5. 修复断言：`toolsByTier` 类工具契约锁不受影响，但凡是遍历 `TaskState` 的测试（看板列、状态机断言）都要更新

**验收**：claim → pause → 任务离开 in_progress 且可被再次 claim；pause 后再 claim 拿到新 attemptId；`gate:*` 状态不允许 pause（明确报错）。
