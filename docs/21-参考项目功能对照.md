## 0. 一句话结论

**当前版本在「运行时自有度」上与所有参考项目形成了断层**：它是唯一同时具备「独立账本 + 角色库 + 门禁链 + 知识库 + token 侧车 + 可写面板」的实现。15 个维度里 **14 维有且成体系、1 维部分（恢复 / 并发）、0 维缺失**；按「是否领先」再分：**6 维独占**（D2 角色库 / D3 状态机 / D4 真实退出码门禁 / D6 知识库 / D12 档位权限 / D13 贡献契约）、**8 维同档**、**1 维落后**（D11 恢复 / 并发，官方更强）。

> **CHG-142~157 已补**：**P0 3/3 · P1 6/6 · P2 4/5 全部落地**（两阶段 spawn 对账 / `revision` 连续性 / `flush` 后通知 / 产物新鲜度 / 交付判定 / 投影缓存 / dispose 有界 / 单调用护栏 / 工具输出契约 / 跨提交零 frame / `wait_agent` 短路 / attempt 四字段 / 并发波次 / 计量覆盖率）。**唯一剩余是 P2-4 单文件客户端拆分**（903 KB `client.js`，体量大、需先补客户端单测）。

**但领先不平均**，短板集中在三类：

| 类型 | 具体 | 性质 |
|---|---|---|
| **工程化短板（官方更强）** | ~~两阶段 spawn 对账~~ ✅ / ~~`revision` 连续性~~ ✅ / ~~`flush` 后通知~~ ✅ / ~~投影视图缓存~~ ✅ / ~~dispose 有界结算~~ ✅ / ~~工具输出契约~~ ✅ | 不是能力缺口，是**同一件事做得不够稳**——**6 项已全部补完**（CHG-142/143/145/146/148/150） |
| **能力缺口（TeamFlow 更强）** | ~~产物新鲜度指纹~~ ✅ / ~~空收尾兜底~~ ✅ / ~~并发波次调度~~ ✅ / ~~单调用护栏~~ ✅ | 对应「假绿」与「烧 token」两类真实事故——**4 项已全部补完**（P1-1/P1-2 接线 CHG-145、护栏接线 CHG-151、波次纯函数 CHG-154） |
| **形态差异（不是差距）** | 固定阶段流水线、产品线分层、git 收口面、Recipes 配方 | 与 PRD 定位冲突，**明确不抄**（§8） |

> 一句话：**能力面已经领先一个身位，接下来该补的是「同样的能力，崩溃/并发/长会话下还成不成立」。**

## 4. 逐维差异解读（只写「为什么」和「差在哪」）

### 4.1 架构定位：我们与官方是**相反取舍**，与 CX 是**同路不同实现**

- **官方**：账本 = Lead 的 Session 日志。收益是零自研存储、崩溃恢复/回放/导出全部白嫖宿主；代价是「Lead 会话没了团队就没了」，一个 workspace 里多团队要靠多个 root 会话。
- **CX**：独立 SQLite operation ledger（`agent-team/src/ledger.ts:534`）。与我们的 JSONL 账本思路一致，但它用 SQLite + 32 型闭合 union，我们用 JSONL + 40 型。**差异在可读性**：JSONL 可 grep / 可 diff / 可人工救场，SQLite 需要工具。
- **TC / BA / TF**：都不真正拥有运行时——TC 寄生于 `storageDomain`、BA 明确「运行时交原生」、TF 是固定流水线。
- **判断**：这条**不改**。PRD §1 的定位（通用团队平台 / Agent Resource 管理）与 FR-19 的两作用域，隐含团队必须独立于会话。

### 4.2 团队与成员：角色库是我们唯一的**结构性独占**

六个来源里，**只有 BA 有「预设」概念，但它是配置层不是聘任层**；官方、NM、TF 都没有「角色」这个设计原子。我们的「角色 × 团队聘任 + 不可变快照 + 实例名编号」是**独一份**。

- 值得注意的反例：BA 的 `TeamPreset` 字段比我们细（slot / captain / agent 三层 + `reasoningEffort`），且「配置快照不可变」写在 `member-store.ts:61-67` 的注释里。
- 我们的成员卡（`members/<memberId>/member.json`）解决的是「重启后这个成员用哪个会话」，与 BA 的 `(rootSessionId, memberName)` 复合键同源。

### 4.3 任务模型：11 态是**最重的**，但不是每一条都被用到

| 项目 | 状态数 | DAG | attempt | 重规划 |
|---|---|---|---|---|
| myteam | **11** | ✅ `deps` + 环检测 | ✅ `attemptId` | ✅ `rescope` / `rewired` / 批量 |
| 官方 | 4 | ✅ 全图校验 | ❌（只有 revision CAS） | ❌ |
| NM | 6 | ✅ 只认 completed | ✅ 四字段拆分 | ✅ `edit_plan` |
| TC | 9 run + 7 phase | ✅ 拓扑校验 | ✅ revision | ✅ continuation 闭包 |
| TF | 3 套（6/9/6） | ❌（文件交集算波次） | ❌（只有 `retries`） | ❌ |
| CX | 5 | ❌ | ❌ | ❌ |
| BA | — | — | — | — |

**结论**：状态机与 DAG 我们领先；但 **attempt 的粒度不如 NM**（NM 把「执行世代 / 能力票据 / 交接冷却」拆成 4 个正交字段，我们只有 `attemptId`），这是 §6 P2 项。

### 4.4 门禁与证据：**只有我们有「真实退出码」**

这是全部六个来源里唯一一个「我们比所有人都硬」的维度：

- 官方：`completed` 即终态，无门禁。
- NM：证据块 + review verdict 齐全，但 `exitCode` 由**调用方自报**（全仓无 `child_process`）。
- TF：最接近——交付判定三级信号 + `[Verification evidence]` 块 + QA 打回闭环，但退出码是**从子代理回复文本里正则提取**的（`host/util.ts:885-907`）。
- 我们：`gate:verify` 由 **host 跑 argv 取真实 exit code** 落账。

**但 TF 有两条我们没有的客观判据**（§6 P1）：
1. **产物新鲜度指纹** `artifactBaseline = "size:mtimeMs"`——治「上游越界写下游产物 → 下游凭旧文件判已交付」这类**假绿**。
2. **交付判定三级信号 + 空收尾兜底**——治「模型如实汇报环境限制被误杀」与「推理模型空收尾整轮重跑（TF 实测一次 ≈150 万 token）」。

### 4.5 消息与通道：我们与 CX 是**唯一的两个完整实现**

NC 的「投递租约 60s + `agent/pre-step` 批量 ack + 代际过滤」是一套值得抄的工程细节（§7 B5）。官方只有 inbox 直投，没有人类收件箱；TC / TF 没有成员间通道。

### 4.6 知识库：**我们独占**

六个来源全部 ❌ 或 🟡：
- NM / TC / 官方：无。
- CX：只有**成员私有**记忆（`memory.md` ≤ 8 KiB 硬顶，超限整块不注入）。
- BA：Team Skills 库（资产 + 绑定 + 依赖声明），但**没有证据指针**。
- TF：产品记忆 + 状态索引，且 ADR-0009 **明确否决**了「插件级用户记忆层」。

> 我们与 TF 的分歧值得记下：TF 否决记忆层的四条理由是「场所错位 / 输入不足以判断普适性 / 两条替代路径已够 / 突破写域边界」。我们的知识库是**项目级、带证据、可审计**的，恰好绕开了这四条——这是设计上的一次正确取舍。

### 4.7 token 计量：我们与 TC / TF 三家各有侧重

| 项目 | 口径 | 侧车 | 进上下文 | 特色 |
|---|---|---|---|---|
| myteam | 四桶 + 按天桶 | `tokens.json` | ❌ | 永不计金额（REV-5） |
| TC | 四桶 + `totalTokens` | `OfficialUsageMeter` | ✅（run 结果字段） | `coverage: full/partial/none` 三态 |
| TF | 双口径（展示四桶 / 熔断排除 cacheRead） | `run.log` + `journal.engine` | ❌ | 命中率公式 |

**差距**：TC 的 `coverage` 三态（「token 数看起来对但样本不全」）我们没有，成本 **小**（§7 B3）。

### 4.8 工具面：62 : 9 是**能力差**，但输出契约是**质量差**

- 数量：62 vs 官方 9（6.9 倍）、NM 14、TF 12、BA 8、CX 7、TC 2。
- 质量：官方的 `jsonOutput()` **双声明**（完整结果 schema + 紧凑 JSON render + 编译期检查）比我们的 `toolOutput()`（只声明 `{ status: string }`）严一档。这是 §6 P1 项——62 个工具逐个补 schema，**必须分批**。

### 4.9 UI 面板：27 屏是**设计资产**，不是运行时代码量

- 我们：27 屏设计稿 + 903 KB 单文件客户端。
- CX：12 屏 + 862 行单文件页面。
- 官方：1 个只读 header slot，25 个 i18n key。

**风险提示**：`plugin/client/client.js` 903 KB / 单文件，CX 的 `audit/D-engineering.md` 已把我们的「单文件客户端」判定为**比标杆更严重**的工程债（E5）。这是本文唯一一条「我们自己也需要修」的项（§6 P1）。

### 4.10 存储：两种根、两种纪律

我们：`$DSH_HOME/myteam/` + `<workspace>/.dsh-myteam/`，定义态/运行态分离，新路径「不存在即空」不阻断迁移。
CX：`agent_team` domain 单表 + 30+ 派生索引，读时 spelling 归一（Channel→Project 改名不改字节）。
TC：domain 版本钉死 0，**明确拒绝迁移 API**。

**判断**：这套不可比。但 CX 的「读时归一」手法值得记：改名不改字节，是对「账本一旦写下就不能重写」的尊重。

### 4.11 恢复 / 并发：**这是我们最该补的一维**

| 子问题 | 官方 | 我们 |
|---|---|---|
| spawn 崩溃安全 | 两阶段（`provisioning` → 建 child → 等初始 prompt durable → `settle(active)`）+ 三条件对账 | `spawnMember` 直接 `agents.create`；失败只能落 `member.spawned{status:'failed'}` 事后报告 |
| 写串行化 | `transact` 按 LeadId 串行 + `flush` 后才通知 | 单写者 `commit()`；「durable 才算成功」靠代码顺序**隐式**保证 |
| 冷启动 | 宿主投影自动恢复 | `openLedger` 全量重放（O(n)），尾部截断 + 坏行跳过 |
| dispose | 准入截止 + 有界结算 + `AggregateError` + 预期取消识别 | 尽力而为排空 |

> 四条都是**同一件事**：我们的正确性依赖「代码顺序看起来对」，官方的正确性有**显式断言**。一次无关重构就可能破坏。§6 P0-1。

### 4.12 权限：四档是**独占**，但官方「领域掌握裁决权」是原则

- 我们：A/C/CM/H 四档 + 确认级 + 作用域 + 不可越权 8 条，`t107` 双向锁死。
- 官方：「领域掌握裁决权，适配器不加更弱的路径」——Lead-only 由**领域服务运行时拒绝**（`TEAM_LEAD_REQUIRED`），适配器层不判断角色。
- 这条原则我们**已经有对应实现**（`TeamService.commit` 是唯一写入口），但没写成不变量（§7 B8）。

### 4.13 第三方贡献契约：**我们独占**

六个来源最多做到「配置面」（NM 的 `profiles`）或「数据面」（TC 的 recipe、BA 的分享文档），**没有一家提供插件级贡献 API**（第三方在运行时注册角色/团队/技能）。我们的 `plugin.json` + roles + teams + 版本协商 + 失败隔离是独一份。

### 4.14 安装分发：`engines.dsh` 是**装载期真校验**，我们写对了

- 我们：`dsh >=0.2.1-rc.0 <0.3.0`。
- 官方四包：**都没有** `engines` 字段（靠 peer 精确锁）。
- NM / TC：也没有 `engines.dsh`（靠 peer 区间 + `compatibility.json`）。
- CX / BA / TF：有，区间与我们同量级。

### 4.15 测试：113 文件 / 800 条是**当前最强**，但有三个盲区

1. **GUI 目检**依赖人类在桌面宿主上配合（KI-2）。
2. **动态冒烟**只覆盖了两次真实安装（CHG-93/94），不是 CI 硬门禁——NM 的「10 宿主矩阵 + tarball SHA-256 绑定」比我们强（§7 B10）。
3. **单文件客户端无单测**（903 KB），CX 已判定这是最严重的一项工程债。

## 10. 取证方法与偏差声明

### 10.1 取证方式

- 4 名只读调研员并行：NM 单包、CX + TM、TC + BA、TF + 官方四包；每人逐文件通读 + `file:line` 取证，产出报告写入 `.tmp/compare/`（不入库）。
- 本仓库侧：`plugin/src`、`plugin/test`、`design/`、`plugin/client/client.js` 只读盘点 + 全量单测实跑。
- 官方四包：`.tmp/asar-current/dsh/node_modules/@deepseek-ai/`（**0.2.2-rc.1**）。`refs/host-src/` 是更旧的 0.2.1-rc.3，**未用作口径**。

### 10.2 数字核实命令

```powershell
# 工具数 / 档位
(Select-String plugin/src/tools/defs.ts -Pattern "name:\s*'myteam_" -AllMatches).Matches.Count   # 62
# 事件型
(Select-String plugin/src/core/ledger/ledger.ts -Pattern "'[a-z]+\.[a-z_.]+'" -AllMatches).Matches | Sort-Object -Unique   # 40
# 端点

# 漂移
node tools/check-drift.mjs                             # MISMATCH: 0
```

### 10.3 已知偏差（照抄会错的地方）

1. **行数口径**：仓库混用 CRLF/LF，`Measure-Object -Line`、`split("\n")`、`read` 工具三种口径差 ±3%~10%。**本文只给量级，不给精确行数**（旧文档的 `3,318 行`、`16,000 行` 都属于这一类，不要再引用）。
2. **工具数口径**：`defs.ts` 里 62 处 `name: 'myteam_*'` 是**全集**（Lead 53 + 成员 9 的子集关系需看注册点，不是相加）。
3. **端点数口径**：`MyTeamPanelFacade` 包含 `MyTeamRemote` 的全部方法（门面转发 + 离线降级），**两者不是相加关系**，报数时分别列。
4. **竞品文档 vs 源码**：NM 的 `docs/architecture/package-ownership.zh.md:10` 图里只列 5 个工具（源码 7 个）；CX 的 README 与源码也有冲突。**本文一律以源码为准**并在原始报告里标注。
5. **版本时点**：本文写于 HEAD `94a9c31`。仓库仍在演进，数字会变；**以重跑命令为准**。

### 10.4 未覆盖 / 无证据

- 官方单测的实际覆盖度（包内 0 测试，只能从 `/* v8 ignore */` 反推）。
- 各竞品 CI 的真实通过状态（仓库里只有配置，没有运行产物）。
- 6 个来源的「逐工具语义等价性」——本文只做**能力面**对照，不做参数级逐一比对。
- 动态性能（各项目在 8 成员 / 31 节点规模下的实测）——NM 有压测记录，其余无。
