## 1. 资源模型（用户定案）

**v4.0 重排（CHG-178）**：

```
资源 A：角色（role）                 资源 B：任务（task）
├─ global   全局库（可到处复用）      └─ project 项目库（**唯一作用域**；不存在全局任务）
│    $DSH_HOME/myteam/roles/               <ws>/.dsh-myteam/tasks/<teamId>/ledger.jsonl
└─ project  项目库（仅本项目）
     <ws>/.dsh-myteam/config/roles/
     ↑ 全局 → 项目单向复制（publish 反向仅人类）

聘任容器：团队（team）
 └─ 成员（member）= 角色 × 团队的聘任记录（**不是资源**；快照固化 C3）
     └─ 子成员（sub-member）= 成员在授权范围内再聘任一次角色（**同一团队内**父子树，FR-32）
         └─ skill / 工具（**不属于本项目**：宿主技能 / 插件贡献 / MCP 连接，只做**引用绑定**）
```

> 旧口径（v3.x）是「项目 → 团队 → 角色」三层，把成员当实体、任务当团队附属；v4.0 把任务提为一等资源、成员降为关系、团队降为容器。

### 1.1 三条推论

| # | 推论 | 落地含义 |
|---|---|---|
| R1 | **项目管到「角色」为止** | skill / tool 是外部资产；项目只维护「角色绑定了哪些」（`role.skills` / `role.mcpAllowlist` / 成员级覆盖），**不维护它们本身** |
| R2 | **团队也是资源，且必然分作用域** | 全局团队库 = 跨项目的**复制源**；项目团队 = 本项目实际在跑的团队 |
| R3 | **复制是单向的** | `global → project`（复制下来用）；反向只有「发布」，且是**人类专属**的不可逆动作 |

### 1.2 资源四态（`origin`）

| origin | 含义 | 可写 | 说明 |
|---|---|---|---|
| `builtin` | 随插件分发 | ❌ | 只读；想改先「复制到项目」 |
| `plugin` | 插件贡献（docs/16 契约 v1） | ❌ | 只读；`plugin:<id>` 标记来源 |
| `global` | 全局库（`$DSH_HOME/myteam/`） | 人类 + `confirmGlobal` | 跨项目复制源 |
| `project` | 项目库（`<workspace>/.dsh-myteam/`） | 队长（默认） | 运行时**只认这份**（R13） |

> **运行时真相恒为项目库**：改全局/内置不生效不是 bug——是单向流动的设计（docs/09 CHG-89 口径）。

## 3. 档位定义（调用者）

| 档 | 含义 | 谁属于 |
|---|---|---|
| **A 全员** | 队长 + 全部成员默认可用 | 只读、认领、上报、消息、**创建技能/工具** |
| **C 仅队长** | 只有队长（captain）可调 | 规划、角色/团队写、门禁裁决 |
| **CM 队长 + 显式授权成员** | 默认只有队长；成员需在 `toolPolicy.allow` **显式点名** | 协作型写（改元数据、评论、知识提案、会话考古） |
| **H 仅人类** | 模型不可调，只能人点面板 | 全局凭据、发布/解散/导出等不可逆操作 |

**确认级**：`-` 无 · `c` 二段确认 · `g` 全局明示（`confirmGlobal`）· `i` 影响面（成员/在跑任务）。

> **C5 铁律**：`toolPolicy.allow` **只能把 CM 降成 C 或更小**，永远不能把 C 升成 A——成员拿不到队长工具。

> **档位已元数据化（CHG-137）**：63 个工具的档位登记在 `plugin/src/core/tools/tool-tiers.ts`
> 的 `TOOL_TIERS`（**单一事实源**），`canCall(name, caller, authorized?)` 是门禁判定：
> captain 可 A/C/CM 不可 H；member 只可 A（CM 需 `toolPolicy.allow` 显式点名）；human 全可；
> **未登记默认拒绝**。`t107` 双向锁死「工具定义 ↔ 档位表」——改工具忘改档位、删工具留孤儿都会变红。
> 当前分布：**A 18 · C 36 · CM 2 · H 6**。

## 5. 复制语义（**核心**）

### 5.1 复制角色（`global → project`，fork）

| 复制 | 不复制 |
|---|---|
| `systemPrompt` / `description` / `interestWords` | 角色 `id`（复制后**新 id**，可改名） |
| `toolPolicy`（只收窄） | 原角色的在册成员（成员在团队里，不随角色走） |
| `skills` / `mcpAllowlist` / `model` | 原角色的审计历史（新角色从 `version:1` 起） |
| `origin: 'builtin:<id>' | 'global:<id>'` 来源标记 | — |

**结果**：项目库新增一份**可改**的角色定义（R13：运行时只认这份）。

### 5.2 复制团队（`global → project`，**本轮新增**）

| 复制 | **不复制** |
|---|---|
| `name` / `goal` / `state`（落 `draft`） | **账本事件**（`ledger.jsonl`）——唯一权威，复制即分叉 |
| 名册（`roster`: roleId + instanceName + 成员级 skills/mcpAllowlist） | 任务 / attempt / 门禁结果 / 证据 |
| 团队配置（`board / pipeline / gates / taskTypes / clarify / memory / audit`） | 成员会话 id / 记忆 / token 计量 |
| `charter`（团队章程） | 团队 `id`（新 id；旧 id 只作 `copiedFrom` 审计字段） |
| `presetId`（来源模板，仅记录） | 归档 / 历史快照 |

**结果**：项目内新增一个 **`draft` 团队**（不是 `active`）——名册与任务由新队长按新项目重新规划，走「`submit_plan` → `approve_plan`」人审链路。

**为什么 `draft`**：团队是「计划批准后才存在的实体」（FR-1.1）；复制来的团队若直接 `active`，等于绕过人审。

### 5.3 发布（`project → global`，单向）

| 资源 | 谁能做 | 确认 | 结果 |
|---|---|---|---|
| 角色（`publish_role`） | **H 人类** | `g + c` | 全局库新增/覆盖（同名覆盖需二次确认） |
| 团队（`publish_team`） | **H 人类** | `g + c` | 全局团队库新增/覆盖 |

**不可逆**：发布后全局库变更**不会**回流到已复制/已建团队（快照语义）。

## 6. 不可越权 8 条（硬规则）

1. **成员拿不到队长工具**：`toolPolicy.allow` 只能收窄，不能把 C 升成 A（C5）。
2. **成员写全局 = 拒绝**：写 `global` 必须 H + `confirmGlobal`；成员一律 `MT_UNAVAILABLE`。
3. **成员不能跨读会话**：会话考古/检索默认 `CM`，未显式授权即拒（C5）。
4. **不可逆操作归人类**：解散、发布角色/团队、导出/导入、MCP 连接配置——**模型只能提案，人类执行**。
5. **账本无物理删除**：任务「删除」= `cancel_task`（终态、留痕）；任何工具不得物理删账本。
6. **写全局必须可定位 + 可审计**：路径固定 + 记「谁建 / 谁绑 / 谁发布」。
7. **成员只看自己的 token / 审计**；队长看全团队；跨团队汇总只给人类面板。
8. **能力缺失诚实报错**：旧宿主缺端点 → `MT_UNAVAILABLE`，不得伪造成功（docs/09 CHG-104 纪律）。
