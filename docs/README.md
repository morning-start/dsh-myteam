## 4. 文档状态

| 状态 | 含义 |
|---|---|
| `proposed` | 评审中，不能作为代码施工承诺 |
| `accepted` | 当前有效设计，可指导功能设计与实现 |
| `superseded` | 已被新文档/ADR 替代，保留演化记录 |
| `historical` | 时点实现、审计或验收记录 |
| `generated` | 由代码或 schema 生成，只能改生成源 |

被替代文档应写 `supersededBy`；替代文档写 `supersedes`。不得再使用“定稿草案”“待裁决但唯一权威”等混合状态。

## 5. 变更纪律

1. **先设计，后代码**：架构或行为变化先更新相应设计并评审，再进入实现；完成后登记变更与真实验收。
2. **一个事项一个权威**：目标、架构、功能契约、执行状态分别归档，不在多份文档中复制成多份“定稿”。
3. **历史不回填成现状**：历史报告保留原始数字和结论；当前数字由重新运行命令获得。
4. **生成内容不手改**：工具数、RPC 数、事件数、错误码和 schema 后续由代码生成。
5. **旧文档逐项处置**：具体保留、合并、替代与历史化关系见 [02 §4](architecture/02-文档重构与迁移蓝图.md#4-旧文档逐项处置)。
6. **本轮不动运行数据**：文档重写不等于数据迁移；任何 cutover 都必须单独分析、验证并由用户确认。
