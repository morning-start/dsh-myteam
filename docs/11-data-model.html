myteam · 功能关系与数据存储结构

对应 docs/11-数据模型与存储设计（CHG-44）· 一句话模型：一个工作区 = 一个 .team-workplace；权威只有账本，其余皆派生 / 配置 / 归档

一、关系总览

Workspace ──1:N── Team Team ──1:N── Member / Task / Message / KnowledgeProposal Team ──1:N── TokenBucket（按天 × 成员） Task ──N:N── Task （deps 依赖） Task ──1:N── Attempt （claim 生命周期） Task ──1:N── GateResult （review/verify/archive） Role（内置/全局/项目）──1:N── Member └ spawn 时快照进 identity.json Preset（团队模式）──1── Captain Session ──1── Team KnowledgeEntry ──N:N── Task（evidence 指针）
不变量：①面板永远不是事实源（数字全从账本投影派生）；②角色=引用+快照，改角色不影响已召唤成员；③任务=attempt 级绑定，释放/撤销即失效；④知识=多对多证据关系；⑤token 是派生计量，不进账本、不进模型上下文。

三、存储分层

L0 权威 append-only

ledger.jsonl（每团队一份）
单写者 commit + fsync
首事件 rules.version.adopted
丢失 = 团队历史丢失

L1 派生 内存

TeamProjection：成员/任务/提案/inbox
commit 后增量折叠
丢失零后果
重建：冷启动全量重放

L2 侧车/配置 可重建或人工

tokens.json · identity.json
config/roles · config/knowledge
成员 memory/notes
tokens 由账本重算；identity 为快照

L3 归档/导出 快照

archive/<teamId>/
export/
解散时归档；可重新导出

五、写入与数据流

工具调用 / 面板动作→ TeamService.commit()→ ① 领域校验→ ② schema + seq→ ③ 副本 applyEvent（O(1)）→ ④ append + fsync→ ⑤ 切换投影 + 侧车
写路径固定「先算后写」：副本 apply 成功才 append，折返失败不落账本、不动投影（CHG-59）；投影只存内存，不落 team.json（ADR-002 R2 决策 B），冷启动从账本全量重放一次。
task.created → backlog → ready → in_progress → evidence → completed → gate → done 异常：escalate → re-scoping → rescope | split | abort 知识：knowledge.proposed → 队长采纳 → knowledge.adopted
