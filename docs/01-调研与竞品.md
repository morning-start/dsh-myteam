## TeamFlow（TF）补充调研 —— 清单缺失的第 6 来源

**定位**：把「一句话需求 → 多 Agent 研发流水线」做成宿主能力（PRD→设计→脚手架→技术方案→并行开发→QA→验收）。固定阶段流水线，阶段子代理为 one-shot。

**与 myteam 的关系**：清单把 E8/E9/G4/G5 等标为"自建差异点（三家均缺）"——TF 不在"三家"里但已做了其中关键部分。结论：**从"自建"改为"借鉴 TF 成熟设计 + 在 host 执行命令上超越"**。

### 可直接借鉴（已转化为需求池候选，见 00-需求池）

1. **证据块协议** `[Verification evidence]`：命令 + 退出码 + 断言计数（或显式 N/A），host 提取落账本；缺失按 policy 分级 warn。→ 新增 FR-5.0
2. **结论行判定**：验收/审查只认**显式结论行**（字面量、行首标记），无结论行 = needs-human，不回退解析自由文本；**明令禁止"全文拒绝词即否决"**。→ FR-5.1 细化
3. **澄清硬终止**：轮数上限 + 用户可随时喊停 + 同问题不重复问；taste/fact 分型（有 taste 才停，纯 fact 用默认值兜底）。→ 新增 FR-1.6
4. **打回预算**：QA 打回 + 复验 ≤2 轮，超限转"已知问题"需人工、不放行合并；P3 缺陷不触发整轮复验（严重级分档）。→ REV-2
5. **token 双口径分离**：计量口径（官方三桶 input/cacheRead/cacheWrite/output + 命中率）与熔断口径（fresh = 排除 cacheRead）**不得合并**；金额不做（单价各异、套餐式计费下算式不成立）。→ REV-5
6. **外部故障 ≠ 交付缺陷**：供应商 429/超时走长退避、不计入任务失败统计与熔断，用尽落 externalFailure。→ REV-3
7. **AGENTS.md 最小侵入**：托管块标记、退出干净可复原、稳定共识层与活文档分离。→ myteam 若写 workspace 共享文件时沿用

### 必须避免的坑（TF 已踩，含数据）

- 澄清无硬终止 → 6 轮零 run（流失级体验）
- **统计盲区**：`journal.triage.blockers` 恒为 0 是结构性假象——澄清命中时那次裁决不落盘。教训：**myteam 账本必须为"被拦截的启动"留事件位**（`plan.clarify`），统计前先问"该字段在哪条路径上被写入"
- 常驻（continuable）子代理五项隐性成本：不主动 drain 累积占池；结算通知进父级上下文吃 token；interrupt 只停当前轮不销毁；初始 prompt 被宿主追加 return guidance（动 prompt 契约）；`run.result` 需 inbox/turn 适配层
- 上下文全文回传式"假隔离"（清单 K3 的 TF 同源教训）
- 假优化勿再投入（TF 优化禁令清单）：如"子 agent 共享已读文件全文"

### TF vs myteam 差异定位（不照抄的部分）

- TF 是**固定阶段流水线**（阶段即角色、one-shot）；myteam 是**持久成员制**（驻留、跨任务复用、流程可配）。TF 的"模式分档"（patch/lite/tech/medium/full）思路可借鉴为"团队准入/分诊档位"（待用户决策，见问题 Q2）
- TF 门禁靠模型自述 + 证据块；myteam 目标是 **host 执行命令取真实 exit code**（FR-5.3）——这是超越 TF 的点，保留并坚持
