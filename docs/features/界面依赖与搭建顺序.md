# 界面依赖与搭建顺序（39 页 → 分层施工）

> 状态：`as-is`（2026-11-23 分析）。目的：**先看清依赖，再从底层往上搭**，避免出现
> 「上层的屏做完了、下层的能力还没有」这种对不上的返工。
> 相关：设计稿在 `design-v2/`（39 页）、机器契约在 [contracts](../contracts/README.md)、
> 现状对账在 [实现对齐](实现对齐.md)。

## 1. 三种逻辑，分别看什么

| 逻辑 | 回答的问题 | 落到哪 |
|---|---|---|
| **设计逻辑** | 一屏放什么、信息怎么分层、空/错/未初始化怎么表达 | 设计稿的层级（指标卡 → 列表 → 详情）、`p-states` 的横向规范 |
| **交互逻辑** | 从哪进、点什么、怎么确认、做完回到哪、失败怎么办 | 面板方法（读）+ 写动作（读写的成对关系）、返回路径 |
| **依赖逻辑** | 这屏要什么数据、要发什么写、依赖哪屏的结果才能成立 | 面板 16 读 / 12 写、域命令、事件与状态机 |

判断一屏能不能现在做，只看依赖逻辑：**数据有了、写动作有了、状态机允许了**，才动手画交互。

  \+ 直接确认类 9（`gateVerdict` `taskCreate` `taskMove` `teamCreate` `memberAppoint`
  `memberRelease` `definitionSave` `memoryRemember` `memoryForget`）。

- 域命令里**已经存在但面板没暴露**的：`completeTaskCommand`、`reopenTaskCommand`、
  `cancelTaskCommand`（后两条已由 `taskMove` 覆盖）、`rewireDependenciesCommand`。

```powershell

node tools/gen-tool-contract.mjs  --check    # 15 + 3
```

## 6. 怎么判断「走错路」了

| 症状 | 说明什么 |
|---|---|
| 屏做完了，按钮点下去报 `INVALID_COMMAND` / 405 | 写了 UI 没补写动作（跳过了 L0） |
| 屏做完了，但只能显示加载失败，因为查不到依赖边 | 数据面没准备（G7） |
| 确认条只能做一半（"影响面"预览拿不到） | 写动作的预览路径没先设计 |
| 同一块信息在两个屏各写一套渲染 | L1 共用件没抽 |
| `p-states` 里的空/错态在实现里是空白 | L5 没做，或 L2 没按三态实现 |

## 7. 第一批（L0）动手清单

按「域命令 → 面板写动作 → 契约生成 → 负路径测试」的顺序，一次一条，**不并行改代码**：

1. `memberRelease`（G3）：`domain/teams/member.ts` 加状态迁移 + `application/commands.ts` 加命令；
2. `teamCreate`（G1）、`memberAppoint`（G2）：把已有域命令接到面板写（含蓝图快照与名册校验）；
3. `taskMove`（G5）：把 claim/complete/reopen/cancel 收成一个带 targetStatus 的写动作，逐条校验合法迁移；
4. `definitionSave`（G4）：草稿校验 + revision 递增，发布仍是现有的 `definitionPublish`；
5. ~~archiveQuery（G6）~~：**结论是不需要**——`board` 的八列已含 done / cancelled，归档回放直接用；
6. 每加一条就 `node tools/gen-panel-contract.mjs` + `node tools/verify.mjs`，契约与 UI 同步推进。

L0 全部落地的判定：`gen-panel-contract --check` 通过、**12 个写动作**各有拒绝用例、`board` 带完整依赖边、`verify.mjs` 全绿。

组成：

| 文件 | 作用 |

为什么不是「起真实实例点 tab」：那要先驱动 DSH 外壳打开会话、再点「团队视图」，
一步错整轮白跑；这里验的是**组件在真样式表下的排版**，宿主装配另有
`node tmp/verify-iso.mjs`（46 项 HTTP 判据）覆盖。两者互补，不是替代。

写的时候踩过三个坑，记在这里免得下次重来：

1. **hook 槽位不能按渲染路径分配**：路径会随条件分支（表单展开/收起）变化，一变槽位就串，
   state 互相污染。改成按「组件函数 + 本轮第几次出现」分配。
2. **槽位形状要统一成 `{kind, value}`**：早期让 `useCallback` 直接存对象，结果 `kind` 判断
   永远不成立、每轮都换新函数身份，`useEffect([load])` 无限重启。
3. **根组件也要走带槽位分配的那个渲染入口**：直接调用组件函数会让第二轮渲染从上一轮的
   hook 游标继续，每个 hook 都落到空槽位上——现象是 fetch 打不完、渲染次数爆表。
   所以渲染器里有 `RENDER_CAP` 兜底，超了就把次数写进 `data-harness-overflow` 停下来。

一个必须记住的限制（我先后判断错两次，量了才明白）：

1. `chrome --headless --window-size=375,812` **不是** 375 的视口 —— headless 有最小窗口宽度，
   实测 `window.innerWidth = 512`，截图是「按 512 排版再裁到 375」。我一度把图里的右侧裁切
   当成窄宽溢出，是错的；
2. 所以脚本改成走 CDP，用 `Emulation.setDeviceMetricsOverride` 定视口，并在每次截图的输出里
   把 `{inner, slot, scroll}` 打出来 —— 现在 375 就是真 375（`inner=375 slot=375 scroll=375`）。

用真 375 复核之后：**窄宽排版是好的**，chrome 断行、卡片收窄、「释放」按钮都在视口内，
不需要为它改样式。之前那条「375 宽溢出」的结论作废。
