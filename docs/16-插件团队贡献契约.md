# 16-插件团队贡献契约（Plugin Team Contribution Contract v1）

> **状态**：**已冻结并实装**（v1，2026-11-06 提出 → CHG-92 实装）。§14 的 4 个未决项已按建议裁决（PM 2026-11-06 确认「可以」），契约与实现同步落地。
> **适用版本**：`dsh-plugin-myteam` ≥ 0.1.0 · `contractVersion = 1`
> **本文是唯一权威**：任何「第三方插件怎么把自己的团队带进 myteam」的实现、文档、skill 都必须以本文为准；实现与本文冲突时**改实现**，不改本文（要改本文走 CHG）。

---

## 1. 这个契约解决什么问题

### 1.1 场景

生态里会有两类插件：

- **A 类：能力插件**（提供技能 / MCP / 工具）。它们已经在别的插件里定义好了一套「人怎么干活」的角色与团队。
- **B 类：团队插件**（本契约的目标）。它自己**不带运行时**，只是「一套已经配置好的团队」——角色名册、分工、门禁链、看板列。

A 类作者应该说：**「我这个插件里有一套团队，装上以后 myteam 里就能直接用。」**

### 1.2 为什么要先定契约

反例（不允许出现的形态）：每个插件自定义一种「注册方式」——有的写 `teams.json`、有的调私有 RPC、有的往 myteam 的账本里塞事件。结果是：

- myteam 没法统一校验（非法角色进库 → 面板整页崩，见 CHG-87 踩过的 `MT_ROLE_CORRUPT` 坑）；
- 卸载插件后残留幽灵角色；
- 插件之间互相覆盖，用户看不出「这个角色是谁给的」；
- 每个新插件都要改 myteam 一行代码——**贡献点不成立**。

所以本契约先定四件事，**然后才允许实现**：

| # | 定什么 | 在哪一节 |
|---|---|---|
| C1 | 贡献落在哪个**目录**、长什么样 | §3 §4 §5 §6 |
| C2 | 与既有角色库/团队模板的**优先级与冲突裁决** | §7 |
| C3 | **装载 / 卸载 / 升级**的语义与**失败隔离** | §8 §9 |
| C4 | 插件**能做什么、不能做什么**（安全边界） | §11 |

### 1.3 一句话契约

> 插件把**数据**（不是代码）写进 `$DSH_HOME/myteam/plugins/<pluginId>/`；
> myteam 启动时**扫描目录**、**逐插件校验**、**注册为 `plugin` 来源**；
> 贡献的角色与团队模板**全局可见、只读、可被用户覆盖**；插件卸载 = 目录消失 = 贡献消失。

## 2. 设计原则（四条，全部可判定）

### P1 契约先行，实现跟随

- 本契约的**每个字段**都必须能回答「谁读它、错了报什么码」。
- 不允许出现「先实现一个字段，文档后面补」——上一轮 CHG-86 的教训是：文档承诺 `roleOp` / `expectedRevision` 而代码零命中，最后要靠审计才发现。

### P2 数据不是代码（Data, not Code）

贡献物是 **JSON 数据**，不是可执行模块。myteam **不 `import()` 插件代码**，只 `JSON.parse` 文件。

- 好处：装载失败可回滚、卸载无残留、无需关心插件的运行期状态。
- 代价：贡献者不能「运行时动态生成角色」。需要动态？那说明你要的是 **A 类能力插件**，不是本契约。

### P3 单向流动（One-way Flow）

`插件 → 全局库 → 项目库`，**不可逆**。

- 插件贡献的角色**只读**：面板里不能编辑/删除（`MT_ROLE_READONLY`）。
- 想改？`copyToProject`（引用即复制）→ 改项目库那份；此后项目库优先级更高，自动生效。
- 插件**升级不追溯**：已召唤的成员用召唤时快照（沿用 CHG-6 既有语义）。

### P4 失败隔离 + 大声（Isolate & Loud）

- 一个插件坏了，**不能拖垮其它插件**，也不能拖垮 myteam 启动。
- 但**必须大声**：每个失败都进 `warnings[]`，面板角色库页顶部显示红色横幅，日志 `logger.warn`。
- 严禁「静默跳过」——静默跳过等于「用户以为装上了」。

## 3. 贡献点：目录布局

### 3.1 根目录

```
$DSH_HOME/myteam/plugins/<pluginId>/
```

- `$DSH_HOME` 缺省 `~/.dsh`（Windows：`%USERPROFILE%\.dsh`）。
- 与既有路径同级：`$DSH_HOME/myteam/roles/`（全局角色库）、`$DSH_HOME/myteam/workspaces.json`（全局索引）。
- 解析函数：`resolveMyteamHome(env?)`（`core/index/team-index.ts`，已有）→ 本契约新增 `contributionsRoot(env?)`。

### 3.2 单个插件的目录

```
$DSH_HOME/myteam/plugins/<pluginId>/
├── plugin.json          # 清单（必需，唯一必需文件）
├── roles/               # 角色定义（0..N）
│   ├── <roleId>.json
│   └── ...
├── teams/               # 团队模板（0..N）
│   ├── <templateId>.json
│   └── ...
└── assets/              # 可选：图标等静态资源（myteam 不解析，只透传路径）
```

### 3.3 硬规则

| 规则 | 违反后果 |
|---|---|
| 目录名 = `pluginId`，且 `plugin.json.pluginId` 必须**逐字相等** | 该插件整体跳过，`MT_PLUGIN_ID_MISMATCH` |
| `pluginId` 必须匹配 `^[a-z][a-z0-9-]{1,63}$` | `MT_PLUGIN_ID_INVALID` |
| 目录里**只允许**上述文件/子目录；出现其它 `.js` / `.mjs` / `.cjs` **不执行**（P2），但记 warning | 不阻断，只警告 |
| 不跟随符号链接（防越权读） | 该条目跳过 + warning |
| 单个 `roles/*.json` / `teams/*.json` 大小 ≤ 256 KiB | 该文件跳过，`MT_CONTRIBUTION_TOO_LARGE` |

## 4. 清单契约：`plugin.json`

### 4.1 Schema（JSON Schema 2020-12 语义，手写实现）

```jsonc
{
  "contractVersion": 1,                  // 必需，整数；本契约 = 1
  "pluginId": "acme-workflow",           // 必需，与目录名逐字相等
  "displayName": "Acme 工作流插件",       // 必需，面板显示名
  "version": "1.2.3",                    // 必需，semver（只校验形状，不比较）
  "description": "一句话说明带进来的团队",   // 可选
  "homepage": "https://...",             // 可选
  "namespace": "acme",                   // 可选，面板分组用；缺省 = pluginId 第一段
  "roles": [                             // 可选，显式清单（推荐）
    { "id": "acme-reviewer", "file": "roles/reviewer.json" }
  ],
  "teams": [                             // 可选，显式清单（推荐）
    { "id": "acme-trio", "file": "teams/trio.json" }
  ]
}
```

### 4.2 字段语义

| 字段 | 必需 | 说明 |
|---|---|---|
| `contractVersion` | ✅ | 本契约版本。myteam 支持集合 = `[1]`。**高版本 → 整个插件跳过**（§10） |
| `pluginId` | ✅ | 全局唯一标识。与目录名比对；与**其它插件**比对，重复 → 后装载者失败 |
| `displayName` | ✅ | 面板里的来源名（角色卡的 `mt-src` chip 显示它） |
| `version` | ✅ | 只做形状校验（`^\d+\.\d+\.\d+`）。**不做版本协商**（§10） |
| `namespace` | ❌ | 面板分组；缺省取 `pluginId.split('-')[0]` |
| `roles[]` | ❌ | 空/缺省 = 本插件不带角色。每项 `{id, file}`；`file` 相对插件目录，**不允许 `..`** |
| `teams[]` | ❌ | 同上 |

### 4.3 显式清单 vs 目录扫描

**v1 只认显式清单**（`roles[]` / `teams[]`）。

- 为什么：目录扫描无法表达「这个文件我暂时不想启用」，也无法做「文件在但清单没列」这种拼写错误的检测。
- 清单里列了但文件不存在 → `MT_CONTRIBUTION_FILE_MISSING`（该条目跳过）。
- 文件存在但清单没列 → **忽略**（不是错误，但记 info 日志），避免误加载编辑器备份文件。

### 4.4 校验顺序（决定错误码）

```
0. 去 UTF-8 BOM（EF BB BF）              → BOM 不构成「清单非法」
1. plugin.json 能读、能 JSON.parse        → 否则 MT_PLUGIN_MANIFEST_INVALID（含行号/列号）
2. contractVersion ∈ {1}                  → 否则 MT_PLUGIN_CONTRACT_UNSUPPORTED
3. pluginId 形状 + 与目录名相等            → MT_PLUGIN_ID_INVALID / MT_PLUGIN_ID_MISMATCH
4. pluginId 不与已装载插件重复              → MT_PLUGIN_ID_DUPLICATE（按目录名字典序，后者失败）
5. displayName / version 非空且形状合法     → MT_PLUGIN_MANIFEST_INVALID
6. 逐条 roles[]：文件存在 → 解析 → 角色校验 → 冲突裁决（§7）
7. 逐条 teams[]：文件存在 → 解析 → 模板校验 → 角色可解析 → 冲突裁决（§7）
```

> **第 0 步不是洁癖**：Windows 上 PowerShell `Set-Content -Encoding UTF8`（PS 5.1）与记事本「UTF-8」都会写 `EF BB BF`，而 `JSON.parse('\uFEFF{...}')` 直接抛 `Unexpected token`。插件作者 100% 会踩 —— 契约明确「BOM 不算清单非法」，实现必须去掉再解析（`t76-23` 锁定）。

**任一条目级失败只丢该条目**，不丢整个插件（除非是 1~5 的清单级失败）。

## 5. 角色契约：`roles/*.json`

### 5.1 与既有 `RoleDefinition` 的关系

**完全复用** `core/roles/builtin-roles.ts` 的 `RoleDefinition`（不新造 schema）。字段见该文件；本契约只加**约束**：

| 字段 | 额外约束 |
|---|---|
| `id` | 必须匹配 `^[a-z][a-z0-9-]{2,63}$`；**必须是 `roles[]` 里声明的那个 id**（文件内容与清单不一致 → `MT_CONTRIBUTION_ID_MISMATCH`） |
| `isCaptain` | **禁止为 `true`** → `MT_ROLE_CAPTAIN_RESERVED`（队长是名册锚点，只能来自内置 `captain`） |
| `toolPolicy.allow` | 只接受**宿主已注册工具名**。出现未知工具名 → **该名字被丢弃**并记 warning（**不是扩权**，是「声明了不存在的工具」） |
| `toolPolicy.deny` | 同上 |
| `skills` / `mcpAllowlist` | **只是名字**，不校验存在性（技能/MCP 可能后装） |
| `origin` | **作者不得写**。myteam 装载时**盖章**为 `plugin:<pluginId>`（与 fork 内置写 `builtin:<id>` 同构，CHG-6） |
| `version` | 可选；缺省 `1` |

### 5.2 示例

```json
{
  "id": "acme-reviewer",
  "name": "Acme 评审员",
  "description": "对 Acme 风格产出的独立复核者",
  "systemPrompt": "你负责复核 Acme 风格产出：先看验收标准是否可测，再看实现是否越界。不做具体实现。",
  "toolPolicy": { "allow": ["myteam_*", "Read"] },
  "skills": ["acme-style-guide"],
  "mcpAllowlist": ["acme-figma"],
  "interestWords": ["风格一致性", "越界检查"],
  "version": 1
}
```

`Level` 说明：`systemPrompt` 是**唯一必需的语义字段**（其余都有缺省）。空字符串 → `MT_ROLE_INVALID`。

## 6. 团队模板契约：`teams/*.json`

### 6.1 为什么要有它（而不是只给角色）

用户原话：「**方便在功能上使用他们已经设置好的团队**」。

只给角色 = 用户还要自己配名册、看板列、门禁链 → 等于没带团队。
给模板 = 建队向导里直接选「Acme 三人组」→ 一次到位。

### 6.2 Schema

复用 `core/presets/preset-store.ts` 的 `PresetDefinition`，**新增 2 个可选字段**：

```jsonc
{
  "id": "acme-trio",                       // 必需，SAFE_ID
  "name": "Acme 三人组",                    // 必需
  "description": "需求 → 实现 → 复核",        // 可选
  "members": [                             // 必需，≥1；队长不在其中（队长固定 myteam-captain）
    {
      "roleId": "acme-reviewer",           // 必须是「装载后可解析」的角色 id
      "instanceName": "评审员",              // 可选，缺省 = roleId
      "skills": ["acme-style-guide"],      // 可选，覆盖角色声明的 skills
      "mcpAllowlist": ["acme-figma"]       // 可选，覆盖角色声明的 mcpAllowlist
    }
  ],
  "board": { "columns": ["待办", "进行中", "门禁", "完成"] },   // 可选
  "pipeline": { "swimlaneBy": "role" },                      // 可选
  "gates": { "enabled": true, "commandTimeoutMs": 120000 },  // 可选
  "taskTypes": { "impl": { "gateChain": ["review", "verify"] } }, // 可选
  "version": 1,                            // 可选

  // ── 本契约新增 ──
  "namespace": "acme",                     // 可选，面板分组
  "charter": "## Acme 团队章程\n\n- 产出先用 acme-lint 过一遍\n" // 可选，团队章程 markdown
}
```

### 6.3 三个硬约束

| 约束 | 错误码 |
|---|---|
| `members[].roleId` 必须在**装载后的合并角色库**里可解析（builtin ∪ 已装载插件 ∪ 全局库 ∪ 项目库 ∪ project-role） | `MT_TEAM_TEMPLATE_UNRESOLVED`（该模板跳过，消息里列出解析不到的 id 与「它可能属于哪个未安装的插件」） |
| `members` 不许含 `captain`（队长由预设隐式提供） | `MT_TEAM_TEMPLATE_CAPTAIN` |
| 模板 `id` 不与 builtin 预设 / 其它插件 / 同名冲突（§7） | `MT_TEAM_TEMPLATE_CONFLICT` |

### 6.4 跨项目可见性（对 CHG-52 的修订）

CHG-52 定过「**全局只保留角色，不存团队模板**」。本契约**修订**它：

> `PresetOrigin` 从 `'builtin' | 'project'` 扩为 `'builtin' | 'plugin' | 'project'`；
> **`plugin` 来源的团队模板跨项目可见**（与 `builtin` 同级可见性，但来源可区分）。

**修订理由**：插件带来的开箱团队如果只能在单个项目里用，用户每开一个新项目都要手动复制一次 —— 那就不叫「插件带了团队」。而「全局库不存**用户自建**模板」这条 CHG-52 的原意（模板是任务维度的组合，不该全局污染）**仍然成立**：插件模板是**插件资产**，不是用户资产。

## 7. 优先级与冲突裁决

### 7.1 角色来源优先级（`ROLE_ORIGIN_PRECEDENCE` 扩展）

| 来源 | 优先级 | 可编辑 | 说明 |
|---|---|---|---|
| `builtin` | 0 | ❌ | 随 myteam 分发（`captain` / `implementer` / ...） |
| **`plugin`** | **1** | **❌** | **本契约新增**。插件贡献，全局可见 |
| `global` | 2 | ✅ | `$DSH_HOME/myteam/roles/`（用户维护的全局库） |
| `project-role` | 3 | ✅ | 项目自身角色（`config/project-role.json`，FR-19） |
| `project` | 4 | ✅ | 项目角色库（`config/roles/`） |

> 现有 4 个来源的**相对顺序不变**，`plugin` 插在 `builtin` 与 `global` 之间。
> 语义：**用户的全局/项目库永远压得过插件**（用户想改插件给的默认，写一份同 id 的进全局库即可）。
> 实现注意：现有数值 `global:1 / project-role:2 / project:3` 需整体 +1 变成 `2/3/4`——**这是本次唯一的破坏性改动**，需同步 `markShadowedRoles` / `resolveEffectiveRole` / 面板 `role.origin.*` 词条。

### 7.2 冲突裁决（三档，全部可判定）

| 冲突形态 | 裁决 | 错误码 |
|---|---|---|
| 插件角色 id **撞 builtin** | **硬失败**，该角色跳过 | `MT_ROLE_CONTRIBUTION_CONFLICT`（消息：「`implementer` 是内置角色，插件请改用带前缀的 id，如 `acme-implementer`」） |
| 插件角色 id **撞另一个插件** | **硬失败**，后装载者（目录名字典序）该条跳过 | `MT_ROLE_CONTRIBUTION_CONFLICT`（消息里点名两个 pluginId） |
| 插件角色 id **撞全局库 / 项目库** | **允许**（不动插件文件） | 无错误。按 §7.1 优先级，用户那份生效；面板把插件那份标 `shadowedBy`（既有 CHG-74 机制） |
| 团队模板 id 撞 builtin / 其它插件 | **硬失败**，后装载者跳过 | `MT_TEAM_TEMPLATE_CONFLICT` |
| 团队模板 id 撞项目预设 | **允许**（项目预设优先） | 无错误 |

**为什么撞 builtin 是硬失败而不是 shadow**：内置角色是名册的锚点（`captain` 必须存在且唯一）。如果允许插件静默 shadow `implementer`，那么「名册里有 implementer」这句话就不可预测了——用户以为在训内置实现者，实际在被插件角色驱动。**静默替换语义字段是最危险的一类 bug**。

### 7.3 命名建议（写进 skill）

插件角色建议 `<namespace>-<role>`：`acme-reviewer` / `acme-implementer`。
myteam **不强制**（不强制前缀，因为强制会让 id 变丑且破坏既有 short id 习惯），但**冲突时要求改名**，所以推荐前缀。

## 8. 装载生命周期

### 8.1 装载时机

| 时机 | 触发 |
|---|---|
| **myteam 启动** | `MyTeamHost.initialize()` 内，**在** `rolePaths` 构造之后、注册工具之前 |
| **显式重载** | 面板「角色库 → 重新扫描插件」按钮 / 队长工具 `myteam_reload_contributions` |
| **不监听文件系统** | v1 不做 `fs.watch`（跨平台不一致 + 热重载语义复杂）；要重载就显式触发 |

### 8.2 装载流水线（纯函数化，可单测）

```
discoverContributions(root)        → ContributionSource[]      // 只做目录发现，不解析
parseContributions(sources, opts)  → ContributionCatalog       // 纯函数：解析 + 校验 + 冲突裁决
mergeIntoCatalog(catalog, paths)   → RoleEntry[] / PresetEntry[]  // 与既有 listRoleCatalog / readPresetCatalog 合并
```

- `parseContributions` **不碰磁盘以外的东西**（无状态、无全局变量），这样才能对「坏插件」写穷举测试。
- 合并只发生在**读**这一侧：`listRoleCatalog(paths)` 内部追加 plugin 来源条目；`readPresetCatalog(workspaceRoot)` 同理。

### 8.3 数据结构

```ts
export interface ContributionSource {
  pluginId: string          // = 目录名
  dir: string               // 绝对路径
  manifestPath: string
}

export interface ContributingPlugin {
  pluginId: string
  displayName: string
  version: string
  namespace: string
  dir: string
  /** 该插件贡献的角色（已盖章 origin: 'plugin:<pluginId>'） */
  roles: RoleDefinition[]
  /** 该插件贡献的团队模板 */
  teams: PresetDefinition[]
  /** 条目级失败（插件整体可用，但某些角色/模板被跳过） */
  warnings: ContributionWarning[]
  status: 'ok' | 'invalid' | 'unsupported'
}

export interface ContributionWarning {
  code: string              // MT_* 错误码
  message: string           // 中文可读
  pluginId: string
  /** 出问题的相对路径（roles/x.json / plugin.json） */
  path?: string
  /** 冲突时点名另一方 */
  conflictsWith?: string
}

export interface ContributionCatalog {
  root: string
  plugins: ContributingPlugin[]
  roles: RoleDefinition[]
  teams: PresetDefinition[]
  warnings: ContributionWarning[]
  scannedAt: string
}
```

### 8.4 卸载

- 目录消失 → 下次装载时角色/模板消失。
- **已召唤成员不受影响**（召唤时快照，CHG-6 语义）。
- **已建团队的任务**：`task.requiredRole` 指向一个消失的插件角色 → 既有诊断码 `no-role`（`docs/04` 已定义）会提示「名册缺人」。**不新增错误码**。

### 8.5 升级

- `pluginId` 不变、文件替换 → 下次装载生效。
- **不追溯**已召唤成员（同上）。
- 模板的 `version` 不参与任何比较（§10）。

## 9. 错误码表

全部以 `MT_` 前缀，与既有错误码同族。**新增 9 个**：

| 错误码 | 级别 | 含义 | 用户可见文案（面板） | 修法 |
|---|---|---|---|---|
| `MT_PLUGIN_MANIFEST_INVALID` | 插件级 | `plugin.json` 解析失败或缺必需字段 | 「插件 `<id>` 的清单不合法：<原因>」 | 修 `plugin.json` |
| `MT_PLUGIN_CONTRACT_UNSUPPORTED` | 插件级 | `contractVersion` 高于 myteam 支持 | 「插件 `<id>` 要求契约 v`<n>`，当前 myteam 支持 v1，请升级 myteam」 | 升级 myteam 或降 contractVersion |
| `MT_PLUGIN_ID_INVALID` | 插件级 | `pluginId` 不合规 | 「插件 `<id>` 的 id 不合规（需小写字母开头，`a-z0-9-`）」 | 改目录名 + 清单 |
| `MT_PLUGIN_ID_MISMATCH` | 插件级 | 清单 `pluginId` ≠ 目录名 | 「插件目录 `<dir>` 与清单声明不一致」 | 对齐两者 |
| `MT_PLUGIN_ID_DUPLICATE` | 插件级 | 两个目录声明同一 pluginId | 「插件 id `<id>` 重复（`<a>` 与 `<b>`）」 | 删掉一份 |
| `MT_CONTRIBUTION_FILE_MISSING` | 条目级 | 清单列了但文件不存在 | 「插件 `<id>` 声明了 `<file>` 但文件不存在」 | 补文件或删清单项 |
| `MT_CONTRIBUTION_TOO_LARGE` | 条目级 | 单文件 > 256 KiB | 「`<file>` 超过 256 KiB」 | 拆分 |
| `MT_CONTRIBUTION_ID_MISMATCH` | 条目级 | 文件内 `id` ≠ 清单声明 | 「`<file>` 内 id 与清单不一致」 | 对齐 |
| `MT_ROLE_CONTRIBUTION_CONFLICT` | 条目级 | 角色 id 撞 builtin / 其它插件 | 「角色 `<id>` 与 <来源> 冲突」 | 改名（加前缀） |
| `MT_ROLE_CAPTAIN_RESERVED` | 条目级 | 贡献了 `isCaptain: true` | 「插件不能声明队长角色」 | 去掉 `isCaptain` |
| `MT_TEAM_TEMPLATE_CONFLICT` | 条目级 | 模板 id 撞 builtin / 其它插件 | 「团队模板 `<id>` 与 <来源> 冲突」 | 改名 |
| `MT_TEAM_TEMPLATE_CAPTAIN` | 条目级 | `members` 里含 `captain` | 「名册不能含队长（队长由预设隐式提供）」 | 删掉该成员 |

| `MT_ROLE_READONLY` | 写操作 | 对 `plugin` 来源角色做 save/delete | 「插件贡献的角色只读；想改请先『复制到项目』」 | 用 `copyToProject` |

## 10. 版本协商

| 版本字段 | 语义 | 不做什么 |
|---|---|---|
| `contractVersion` | **契约形状**（字段集合 + 语义）。整数。myteam 支持集合 = `[1]` | 不做「前向兼容猜测」。高版本 → 整个插件跳过 + `MT_PLUGIN_CONTRACT_UNSUPPORTED` |
| `version` | 插件自身 semver | **不比较**。不做「myteam 0.1.0 需要插件 ≥1.2」。需要的话用 `requires`（见下） |
| `requires.myteam` | 可选 semver range | v1 **只记录不校验**（面板显示「要求 myteam ≥x」但不阻断）。理由：range 求值器是额外依赖面，v1 不值得 |

**为什么 `contractVersion` 高版本要整插件跳过而不是尽力解析**：尽力解析的失败模式是「字段被静默丢弃」，用户拿到一个少了门禁链的团队却不知道——这比直接报错危险得多。

## 11. 安全边界（插件能做什么、不能做什么）

### 11.1 能做

- 贡献**角色**（纯数据：提示词 + 工具白名单 + 技能/MCP 名字）
- 贡献**团队模板**（名册 + 看板列 + 门禁链 + 章程）
- 在面板里**显示来源**（`displayName` + `namespace` 分组）
- 被 `copyToProject` / `fork` 成用户自己的副本（用户侧动作）

### 11.2 不能做（每一条都有测试）

| 不能 | 强制手段 |
|---|---|
| 声明**队长**角色 | `MT_ROLE_CAPTAIN_RESERVED` |
| 覆盖 **builtin** 角色 | `MT_ROLE_CONTRIBUTION_CONFLICT` |
| 绕过 `toolPolicy` **扩权** | `allow` 只收窄；未知工具名丢弃并警告（C5 不变） |
| 写**团队账本** | 装载是只读的（`parseContributions` 只有 `readFileSync`） |
| 执行**代码** | 不 `import()`，只 `JSON.parse`（P2） |
| 读**插件目录外**的文件 | `file` 字段禁止 `..`、禁止绝对路径、不跟随符号链接 |
| 修改**用户**的角色/团队 | 贡献物只读；用户资产的写入口只有 `roleOp` |

### 11.3 威胁模型（v1 明确不防）

- **恶意插件**：能往 `$DSH_HOME/myteam/plugins/` 写文件的进程本来就能干任意事。本契约防的是**意外**（写坏了、写错了、写重了），不是**敌意**。
- 若未来要防敌意：需要签名/沙箱——**v1 不做，也不假装做了**。

## 16. 与 skill 的关系

本契约是**权威**，`skills/myteam-plugin-team/` 是它的**使用说明 + 模板 + 校验器**：

| 文件 | 职责 | 冲突时 |

| `skills/myteam-plugin-team/reference/*.md` | 字段级速查 | 服从本文 |
| `skills/myteam-plugin-team/templates/*` | 可直接拷的骨架 | 服从本文 |
| `skills/myteam-plugin-team/tools/check-contribution.mjs` | **可执行**契约校验器 | 服从本文；它报的错就是本文 §9 的错误码 |

> 校验器存在的意义：让插件作者在**自己的仓库里**就能验证契约，而不是装进 DSH 之后才发现角色被跳过。
