## 新增需求（TF 调研触发，2026-10-25 用户确认纳入，CHG-1）

### FR-1.6 规划前澄清硬终止（已定稿，M1）
- 目标用户：发起 `/myteam new` 的人
- 核心场景：信息不足时 Lead 先澄清再出名册/DAG 草稿，但绝不无限追问
- 方案要点：澄清只在主会话进行；问题分 taste/fact 两型（taste 才必须停，fact 用默认值 + 假设标注兜底）；硬终止三条件（≤N 问 / 用户喊停 / 同问题不重复问）；**被拦截的启动在账本留 `plan.clarify` 事件**（防 TF 式统计盲区）
- 业务验收标准：一条模糊需求在 ≤3 问内出草稿或显式放弃；不存在"反复追问无产出"形态；账本可追溯澄清拦截
- 风险：N 值与 taste 判定靠模型自律，先 warn 后加拦截（TF 经验：依赖模型自律的判据在量出真阳性率前不得有阻断权）

### FR-5.0 交付证据块（已定稿，M1，先于 command 门禁）
- 核心场景：M2 的 host 执行门禁落地前，M1 的 done 申报不能只靠模型自述
- 方案要点：成员 `update_task`（申报完成/进度时）必须附证据块 `[Verification evidence]`（命令 + 退出码 + 断言计数，或显式 N/A + 原因）；host 提取落账本（事件 `task.evidence`）；review 门禁先审证据块；**禁止"全文拒绝词即否决"式判定**
- 业务验收标准：无证据块的 done 申报在账本中被标记；证据可按 seq 追溯
- 依赖：纯协议层，无需 subprocess 服务，M1 可做

### FR-11.7 运行中重规划（v1.8，CHG-8，用户提出，已定稿）

"做着做着发现是困难任务"的显式机制：

| 环节 | 设计 |
|---|---|
| 触发（成员） | `myteam_escalate_task` 申报受阻 `{reason, evidence(已尝试+卡在哪), suggestion}`；**立即生效**（非提案）：attempt 撤销 → 任务入 **re-scoping** 态 → 队长 Inbox 提醒；语义 = 收窄活动，符合 C5 |
| 重规划态 | re-scoping：看板可见带升级徽标；成员已释放可领其他任务；deps 冻结 |
| 裁决（队长三出口） | **rescope**（缩窄 AC → 回 ready 重新调度，新 attempt 引用原产出不浪费）/ **split**（子任务 + 原任务 cancelled + 下游依赖重接线）/ **abort**（转 blocked 转人工，不伪装完成）——均用既有 Lead 工具 |
| 预算 | 每任务 escalate 计数 >2 → 裁决面建议人工介入（提示不强制） |

- 状态机增量：`in_progress ──escalate──► re-scoping ──► ready / cancelled / blocked`（PRD §7.1 已更新）
- 账本事件 +`task.escalated` / `task.rescoped`；验收场景 17

### FR-19 作用域分层（CHG-66）
- **全局**：只有角色（内置只读 + 全局个人资产），不设团队、没有任务；附随行资产入口（预设 = 建团模板、技能 & MCP）。
- **项目**：比全局多「团队」「任务」两个实体；**项目自身也有一个角色**（不属于任何团队，可被本项目各团队聘任）。

### FR-20 队员 = 聘任记录（CHG-64；对 FR-12/FR-14 词汇修订）
- 系统以**角色**为设计原子；团队 = 把角色拉进来而形成。
- UI 不出现「成员」：团队内称**队员** = 角色 × 团队的聘任记录（逻辑关系，不是实体）；快照在召唤时固化，同名角色多次召唤自动 -2 编号。
- 兴趣词进角色 schema（interestWords[]）：角色卡 chips / 任务详情「派单依据」/ 审计追溯三落点；派单软信号，非权限。

### FR-21 任务 = 项目级实体；参与关系（CHG-67；对 FR-11 修订）
- 任务与团队是两个实体，多对多：一张任务可多团队参与（主责 1 / 协作 N），一个团队参与多张任务。
- 参与关系显性化三处：看板左侧「参与团队」轨 / 任务卡团队 chip（实线主责 · 虚线协作）/ 任务详情「参与团队」区块；团队页「参与任务」tab（本队角色 / 本队队员 / 其他参与团队）。

- 任务视图四件套升项目级：列表 / 看板 / 流程 / 依赖图。

### FR-29 执行期编辑与补充（CHG-70/71 核心；CHG-72/73/75 已实现）
- 已实现：元数据随时改（`task.updated`，不动状态/attempt/证据）；结构字段（AC/交付物/依赖/角色/门禁链）在 in_progress/gate 阶段拒绝（`MT_TASK_STRUCTURAL_EDIT`），必须 rescope；编辑通知执行者；面板任务详情「编辑」抽屉（执行中改结构字段会提示，并提供「保存并重新规划 / 只保存元数据」两个出口）；人类留言（`message.sent` actor=human）。
- 已实现（P2，CHG-73）：**一键 rescope**（`myteam_rescope_task` / 门面 `rescopeTask`：撤 attempt → ready/backlog → 可选结构补丁 → 可选重派；理由必填；终态拒绝；撤 attempt 也能离开门禁态）；**字段级 diff**（`changes` 落账 + 详情「改动记录」）；**证据过期标记**（`evidenceStale`：结构编辑晚于证据，看板徽标 + 详情横幅，新证据清除）；**任务取消**（`task.cancelled` 终态 + `dep-cancelled` 下游诊断 + leave/cancel 两档下行策略）。
- 已实现（P3，CHG-75）：**取消后的「重接线」**（第三档 `downstream:'rewire'`：把**直接下游**的依赖改挂到新上游，不指定新上游 = 解除依赖让下游变独立任务；账本 `task.rewired`；**预检先于不可逆写**——改挂非法时取消也不落账，不留半吊子状态；解除依赖后无待完成依赖则下游 `backlog → ready`）；面板 `CancelDialog` 第三档 + 上游下拉 + 影响面分档文案。
- 已实现（P3，CHG-76）：**批量档的重接线**——`myteam_batch_task_op` 的 `downstream` 增加 `rewire` + `rewireTo`（整批统一新上游，缺省 = 逐条解除依赖）；**批量级前置校验**（新上游不能是本批要取消的任务、不能已取消/失败），预览给 `impact.rewireByTask` 逐任务列出要被改挂的直接下游。
- 待做（P3）：跨团队 claim；改挂支持**跨团队**上游（当前限本团队，跨团队依赖本身尚未建模）。

### FR-30 派单唤醒（CHG-71，已实现）

### 设计原则（用户多次强调，实现与后续设计必须遵守）
1. 角色是设计原子；团队由角色组成；**队员与「参与」都是关系，不是实体**。
2. UI 词汇不出现「成员」；**实现细节不出 UI**（存储路径、复制方向只进文档）。
3. 全局与项目严格分开；项目自身有角色。
4. 任务与团队解耦，多对多参与；任务上标注负责队员。
5. 依赖图必须有箭头，且提供横向 / 竖向两种布局。
6. 面板宽度撑满页面（任意窗口尺寸不留白）。
7. 演示数据一律虚构（工作区 / 会话 / 用户名不引用真实环境）。
8. 骨架对齐真实 DSH Web（实拍 + 宿主 token），不自创外壳。
