# 24 · 设计稿架构对齐审计

> **审计对象**：`design/` 下 28 屏设计稿（HTML 终稿）是否**如实承载功能设计架构**。
> **不是**评好看不好看 —— 是好坏看「实体与关系、信息架构与入口、状态与动作、数据口径、术语纪律、覆盖」六条是否成立。
> **审计方式**：两轮多子 Agent 并行（第一轮 7 组屏 + 5 个横切面 + 4 组回源核验；第二轮 4 条 P0 复核 + 7 组全量回归），合计 36 个子 Agent。所有 P0 结论均由人工回源复核过。
> **审计时点**：2026-11-14（CHG-194 ~ CHG-197 之后）。

## 0. 结论先看

| 严重度 | 数量 | 状态 |
|---|---|---|
| **P0**（架构错：实体 / 关系 / 作用域 / 状态机画错） | **4** | ✅ **全部已修**（CHG-195 + CHG-196 残留补修） |
| **P1**（口径不一致：字段 / 计数 / 术语 / 动作缺失或矛盾） | **14** | ✅ **全部已修**（CHG-198） |
| **P2**（可疑 / 需确认 / 文档自身口径打架） | ~14 | ⬜ 待定（本文 §4） |
| 设计稿缺屏 | — | ✅ 已补：27 → **28 屏**（+`roster-tree.html`，CHG-197） |

**一句话**：骨架（实体模型、作用域分层、三视图同源、门禁链、账本派生）是成立的，错的是**数字与「可逆性承诺」两处最容易传播的口径**——都已收口。

## 1. 审计判据（六条）

1. **实体与关系**：role / instance / team / task / participate（主责·协作）/ preset / skill / knowledge 是否都画出来、层级对不对；**成员 = 角色 × 团队的聘任记录，不是第三种实体**。
2. **信息架构与入口**：六个宿主插槽落点（`sidebar.panellist` / `conversation.view` / `composer.dock` / `tool.call.toolview` / `settings.section` / `sidebar.session.row.leading`）；全局 vs 项目作用域；四层来源（内置 / 全局 / 项目 / 角色绑定）；**跨层只有「复制」没有「同步」**；**运行时只认项目层**（`resolveRuntimeRole` 不回退）。
3. **状态与动作**：团队 `draft → active → archived → discarded`；任务 11 态；门禁链 `review / verify / archive`；两段确认；attempt 防陈旧写；排空可见。
4. **数据口径**：屏上的字段 / 计数 / 成本数字能否从真实数据源派生（Remote 端点 / 门面方法 / 账本 40 型事件），有没有自造「第二事实源」。
5. **术语纪律**：团队内界面**不出现「成员」**（只有「角色」与「实例」）；任务必须说成「项目级」、团队通过「参与」接手。
6. **覆盖**：功能设计里有、设计稿里没有落点的；或设计稿里有、功能设计里根本不存在的。
