# 28-数据源与配置分层（草案，待用户定案）

> 背景：团队视图打不开的直接原因是 `myteam_list_members` 把 `undefined` 字段透传（已修），
> 但**根因是存储模型没定义清楚**：同一实体有多份副本，谁权威、谁派生、坏了怎么办，全都没写下来。
> 这份文档只做一件事：把「实体 → 唯一真源 → 派生物 → 重建方式」钉死，然后分批迁移。

## 1. 现状（实测，2026-11-22）

### 1.1 磁盘上真实存在的东西

```
.dsh-myteam/
├── config/                         # ① 配置资产（入库、可 review）
│   ├── roles/<roleId>.json         #   项目角色库
│   ├── knowledge/<topic>.md        #   团队知识库（策展制：adopt 后才有）
│   └── teams/<id>.json             #   团队**模板**（preset）
├── tasks/<teamId>/
│   ├── ledger.jsonl                #   账本：任务/名册/门禁/消息的**事件真源**
│   └── team.config.json            #   团队级行为配置（看板/门禁/limits）★语义是配置，位置在 tasks/
├── history/                        # ③ 过程（不入库）
│   ├── memory.db                   #   记忆（SQLite，唯一读写通道）
│   ├── members/<team>/<member>/memory/memory.md   # 记忆**播种**副本（后续不再更新）
│   ├── archive/<teamId>/           #   归档快照
│   └── tokens/<teamId>.json        #   token 计量侧车
├── state/                          # ④ 运行时派生（不入库）
│   ├── teams.json                  #   工作区索引（团队列表 + 更新时间）
│   └── index/tasks.json            #   任务索引（派生）
└── config/team.config.json         # ② 项目级配置默认值（覆盖链的中层）
```

### 1.2 配置的解析链（代码里已经是对的，但没写在文档上）

`内置默认 ← 项目 config/team.config.json ← 团队 tasks/<teamId>/team.config.json`
→ `loadEffectiveConfig()` 产出**运行时 effectiveConfig**（`core/config/team-config.ts:238`），
不做持久化。也就是说：**配置的真源是两层文件，生效值是一次函数调用**。

### 1.3 实体 → 当前真源（问题表）

| 实体 | 当前"真源" | 其它副本 | 问题 |
|---|---|---|---|
| 团队身份 / 目标 / 名册 | 账本 `team.created`、`team.updated` | `state/teams.json` 索引 | 索引与账本可漂移，无校验 |
| 任务 / 依赖 / 状态 | 账本事件 | `state/index/tasks.json` | 同上 |
| 团队行为配置 | `config/team.config.json` + `tasks/<t>/team.config.json` | 内存 `effectiveConfig` | 默认值与文件混读；团队层放在 `tasks/` 下语义错位 |
| 角色 | `config/roles/*.json`（+ 内置/全局/插件贡献） | 成员 `identity.json` 的 roleSnapshot | 「改角色对在岗成员是否生效」无明文规则（实际是快照，不改） |
| 知识 | `config/knowledge/` | 账本 `knowledge.proposed`（提案） | 提案与入库条目无 linkage 校验 |
| 记忆 | `history/memory.db`（SQLite） | `memory.md` 播种副本 | md 从不更新、也没标「只读快照」→ 用户会去改它 |
| 成员卡 | 账本投影（`member.spawned`） | `history/members/*/identity.json`、成员卡文件 | 快照与投影各写一份，无一致性检查 |
| token 计量 | `history/tokens/<t>.json` | 账本事件（若有） | 侧车与事件口径未声明 |

## 2. 目标模型：三类数据 + 一条不变量

### A. 事件真源（append-only）
**只经 `Service.commit()` 写**（A4 门禁已保证）：团队身份、名册、任务与依赖、门禁裁决、消息、
知识提案、成员生命周期、**配置生效记录**。读方一律"回放账本得投影"，不直接读派生文件。

### B. 配置资产（文件，入库，可 review）
```
config/project.config.json          # 项目默认值（覆盖链中层）
config/teams/<teamId>.config.json   # 团队级覆盖（★从 tasks/<t>/team.config.json 迁出）
config/roles/<roleId>.json          # 角色
config/teams/<teamId>.json          # 团队模板（preset）——与上面的 .config.json 用后缀区分
config/knowledge/                   # 知识（策展制）
```
解析顺序固定：`内置默认 < 项目 < 团队级`；**解析结果写一条 `config.applied` 事件**（带两层文件 hash），
这样「当时生效的是哪份配置」可以回放，出问题不用猜。

### C. 派生缓存（可重建，永不作读源）
`state/teams.json`、`state/index/tasks.json`、成员卡、`memory.md`、`identity.json`：
- 每个文件带 `derivedFrom: { ledgerSeq, sourceHash, version }`；
- 读方只用于 UI 加速，**校验不过就重建**；
- 提供 `myteam_doctor`（体检 + 重建）与 `myteam_rebuild_index`（只重建）。

### D. 记忆（SQLite 唯一真源）
`history/memory.db`：`entries`（bank/kind/title/body/evidence/supersedes/archived_at）。
`memory.md` 降级为**导出视图**（只读、可删、带 `# generated` 头），或干脆删掉（见待定问题 Q3）。

### 一条不变量

> **一个实体只有一个写入口；其余一切要么是事件回放结果，要么是带血缘标记的可重建缓存。**

## 3. 分批落地（每批：测试 + 8 门禁 + 真机验证）

| 批 | 做什么 | 验收 |
|---|---|---|
| S1 | 团队级配置迁到 `config/teams/<teamId>.config.json`（旧路径读一版并 warn） | 老工作区照常起；面板保存配置后新路径生效 |
| S2 | 派生缓存加 `derivedFrom` + `myteam_rebuild_index` + 校验失败自动重建（留 warn） | 手改 `state/index/tasks.json` 后能自愈 |
| S3 | `memory.md` 改为导出视图（`# generated` 头 + `myteam_export_memory`） | 改 md 不影响召回；导出可复现 |
| S4 | `myteam_doctor`：账本 ↔ 索引 ↔ 成员卡 ↔ 投影字段完整性（含 undefined 扫描） | 人为制造漂移能被点名并给修法 |
| S5 | 读路径审计 + grep 门禁：除 rebuild 路径外不许直接读 `state/**` | 门禁拦住新增直读 |

## 5. 明确不做

- 不引入数据库存任务/团队（账本已是 append-only 事件流，回放即可）；
- 不做双向同步（配置文件 ↔ 账本）——那正是"多真源"的来源；
- 不在本轮改 `state/` 的目录名（先把语义与校验补上，改名留到 S1 之后评估）。
