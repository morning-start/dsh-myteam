# 29-作用域模型（全局 vs 项目）与配置设计（草案，待定案）

> 用户定案的两条原则：
> 1. **全局级 = 跨项目复用**；任何进入 / 修改全局级的内容**必须用户确认**。
> 2. **项目级 = 本项目内跨会话与时间复用**，**agent 是主要操作者**。
>
> 这份文档把「哪些实体活在哪个作用域 / 谁能写 / 怎么解析 / 怎么 fork」钉死，接 docs/28 的数据源三分法。

## 1. 作用域矩阵

| 实体 | 全局（复用） | 项目（工作区） | 说明 |
|---|---|---|---|
| 角色定义 | ✅ 全局角色库 | ✅ 项目角色库 | 项目里可 fork 全局角色（`origin: global:<id>`）后改 |
| 团队定义/模板 | ✅ 全局团队库 | ✅ 项目模板库 | 全局是"可复用定义"，**不含账本** |
| 运行中团队（live team） | ❌ | ✅ | 团队一建就绑项目：账本、名册、任务都在项目里 |
| 任务 / 依赖 / 门禁裁决 | ❌ | ✅ | 只经账本 `commit()` |
| 行为配置（看板/门禁/limits） | ⚠️ 可选"全局默认值"（见 Q2） | ✅ 项目默认 + 团队级覆盖 | 生效值 = 解析结果，不落盘 |
| 知识库 | ❌（本轮不做） | ✅ | 策展：成员提案 → 队长采纳 |
| 记忆（SQLite） | ❌ | ✅ | 团队 bank / 成员 bank 都是项目内 |
| 派生缓存（索引、成员卡、md 导出） | ❌ | ✅ | 随真源，跨项目没有意义 |

## 2. 写权限矩阵（谁能写）

| 实体 | 全局 | 项目 |
|---|---|---|
| 角色 | **只有人**（H 档：`publish_role` + 面板确认）；agent 只能 `copy_to_project` | agent 可写（`create_role`/`update_role`/`delete_role` 默认 `scope:project`） |
| 团队定义/模板 | **只有人**（`publish_team`） | agent 可写（`save_preset`） |
| 运行中团队 / 任务 / 门禁 | — | agent 写（经账本），人可介入 |
| 行为配置 | —（若做全局默认值，也归人） | agent 写（`save_team_config`） |
| 知识 | — | 成员提案 + 队长采纳（策展门） |

**强制手段**（不是靠自觉）：
- 工具层：写全局的入口只有 H 档工具（本来就要人确认），agent 工具面里**没有**直写全局的角色/团队写口；
- 门禁层：grep 门禁扫代码——除 `publish_*` 路径外，不许出现 `resolveMyteamHome(...)` 写操作；
- 读取层：任何"写全局"必须走 `confirm` 两段确认，账本/日志留痕（谁、什么时候、改了什么）。

## 3. 解析链（读的时候先看谁）

| 实体 | 解析顺序（后者覆盖前者） | 冲突时怎么表现 |
|---|---|---|
| 角色 | `builtin < global < project` | 项目副本胜出；**返回 `sharedFrom` 提示全局版本**（见 §4） |
| 团队模板 | `builtin < 插件贡献 < global < project` | 同上 |
| 行为配置 | `代码内置默认 < （全局默认值）< `config/project.config.json` < `config/teams/<teamId>.config.json` | 逐层合并；非法层被忽略并 warn |
| 知识 / 记忆 | 项目内唯一，无继承 | — |

**不变量**：`roleId` / `teamId` 在**同一作用域内唯一**；跨作用域靠 `origin` 标来源，不靠 id 前缀区分。

## 4. fork 与发布（单向，永不双向同步）

```
global 角色/团队 ──copy_to_project（agent 可做，只读正向）──▶ 项目副本 { origin: 'global:<id>', originHash }
项目副本 ──publish_*（仅人，两段确认）──▶ global（单向覆盖，记 hash 与时间）
```

- **项目副本是快照**：全局后续更新**不会**悄悄改变项目行为；
- 读取面要能回答"我从哪来、落后没有"：返回值带 `origin` / `originHash` / `sharedLatestHash`（可选，代价是一次全局读取）；
- `publish` 前必须给出影响面（哪些项目在用、覆盖会改什么），已实现，保留。

## 5. 落盘布局（项目级，拟改）

```
<workspace>/.dsh-myteam/
├── config/                          # 配置资产（入库，可 review）
│   ├── project.config.json          #   项目级默认（原 config/team.config.json）
│   ├── teammates/                   #   ← 拟改名（避免与"团队"混淆）
│   │   ├── <teamId>.json            #     团队模板
│   │   └── <teamId>.config.json     #     团队级配置覆盖
│   ├── roles/<roleId>.json          #   项目角色（可 fork 自全局）
│   └── knowledge/                   #   团队知识（策展）
├── teams/<teamId>/                  # ★拟由 tasks/ 改名：一个团队一个目录
│   ├── ledger.jsonl                 #   事件真源
│   └── derived/                     #   派生缓存（成员卡、看板快照；带 derivedFrom）
├── memory/memory.db                 # ★拟由 history/memory.db 迁来：记忆唯一真源
└── state/                           # 项目级派生索引（teams.json、index/）
```

全局：`$DSH_HOME/myteam/{roles,teams,plugins}`（现状已如此；`plugins/` 只读、由插件安装贡献）。

## 6. 分批落地（修订 docs/28 的 S 序列）

| 批 | 内容 | 验收 |
|---|---|---|
| **S0** | 作用域可见化：`list_roles` / `get_team` / 面板角色卡返回 `scope` + `origin` + 冲突提示（**只读，先让人看得见**） | 同一 `roleId` 在两作用域都有时，返回里能看出"用哪个、另一个是什么" |
| **S1** | 写权限矩阵落地：审计所有写路径；global 写只剩 H 档工具；补 grep/架构门禁 | 造一个"agent 直写全局"的调用 → 门禁红 |
| **S2** | 配置落点迁移：`tasks/` → `teams/<teamId>/{ledger.jsonl,derived/}`；团队配置迁到 `config/teammates/`；旧路径兼容一版并 warn | 老工作区照常起；新路径生效、旧路径告警 |
| **S3** | 派生缓存血缘 + `myteam_rebuild_index` + 校验失败自动重建（策略见 Q4） | 手改派生文件能自愈或点名 |
| **S4** | 记忆归一：`memory/memory.db` 唯一真源；`memory.md` 降级为导出（`# generated`） | 改 md 不影响召回 |
| **S5** | `myteam_doctor`：账本 ↔ 派生 ↔ 投影字段完整性 + 作用域漂移（fork 落后/被遮蔽）一次体检 | 人为制造漂移能被点名并给修法 |

## 7. 待定案

- **Q1** 目录改名：`tasks/` → `teams/`（我建议，语义更正）+ 模板目录 `config/teams` → `config/teammates`（避免与"团队目录"混淆）？
- **Q2** 要不要"全局行为默认值"这一层？我倾向**不要**：行为默认值要么在代码（发版即改），要么在项目（agent 可调）；多一层全局默认会让"为什么这个门禁没开"更难查。
- **Q3** fork 后的"上游已更新"提示：只做**提示**（读时比 hash），还是也做一键 rebase（覆盖项目副本、可能丢改动）？我建议先只提示。
- **Q4** 派生缓存坏了：自动重建 + warn（省事）／报错并给命令（严格）？
