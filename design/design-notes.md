## 零、只管理一种实体：角色；成员是一条聘任记录（CHG-64，用户拍板）

用户定的模型：**系统以角色为设计** —— 每个 Agent 以角色为概念存在，团队是把不同角色拉进来而形成的。据此：

- **角色（Role）是唯一要用户管理的实体**：职责描述、系统提示词、工具策略（只收窄）、技能引用、模型路由、**兴趣词**（新属性：结算 / 契约 / 灰度…，软信号，用于分派理由与认领排序，不是权限）。
- **团队（Team）是一次角色编排**：把不同角色拉进来；配置来源 = 预设（名册 + 看板列 + 门禁链）。
- **成员（Member）不是第三种实体，是「角色 × 团队」的聘任记录**：`{ teamId, roleId, instanceName, 快照, joinedAt }`。快照在召唤那一刻固化（C3 不变）—— 改角色不影响已聘任的实例。
- **多团队（并行）成立**（用户拍板）：同一角色可被两个团队同时聘任 = 两条记录、两个实例、两份独立上下文与 token 账。单团队项目里这条边隐形，界面只有"团队 + 角色"。
- **UI 词汇纪律：界面上不出现"成员"一词。** 团队内只说「角色」（名册 = 本团队拉进来的角色）与「实例」（同一角色召唤几次的记号）；"成员"只存在于数据模型与文档。实例名团队内唯一；跨团队视图用「团队名 · 角色名」消歧。

| | 角色（Role） | 实例（Instance）＝聘任记录的运行面 |
|---|---|---|
| 是什么 | 配置单元：职责、提示词、工具策略、技能引用、模型路由、兴趣词 | 一次聘任的运行面：独立 Session、独立上下文快照、独立私有空间、独立 token 账 |
| 有多少 | 内置 6 个 + 全局/项目自建 | 每团队 ≤ 团队规模（默认 6，不含队长） |
| 改动影响谁 | 不影响已召唤的实例（快照不可变） | 归档只排空；移除连私有空间一起删 |
| 兴趣词 | 定义在角色上，随快照固化 | 认领/分派按兴趣词匹配，任务详情给「派单依据」 |

三条容易画错的推论：

1. **队长不在名册里。** 队长是 team 预设会话本身，不是被聘任的角色。名册卡按角色组织（实现者 ×2 是一张卡），tab 上写「角色 5」（在册实例数）。
2. **名册卡主标题是角色名**（实现者 / 评审者…），实例（mono `implementer` / `implementer-2`）作为名册卡里的实例行；同角色多团队时给一枚「同时在 t-xxx 在跑」标记。角色库卡片同样是角色名为主，展开占用实例。
3. **兴趣词出现在三处**：角色卡（库 + 名册）一行 chips；任务详情「派单依据 · 角色兴趣词『服务边界』」；审计里分派理由可追溯。它不产生任何权限。

## 零点五、两个正交维度：多团队 × 作用域分层

第一版把 myteam 画成"一个团队的一个看板"，漏了两件事。这两件事是正交的，必须同时表达。

**维度一：同时有多个团队。** 落盘结构 `state/teams/<teamId>/` 本身就是按 teamId 分目录的，所以多团队并存是天然成立的 —— 每个团队有自己的 `ledger.jsonl` / `team.json` / `tokens.json` / `members/`。UI 的对应动作有三个：`overview.html`（全局页，跨团队横向比）、`team-switch.html`（顶条切换器展开态，纵向选）、`board.html` 等团队内页（单团队纵深）。切换只换视图，**不停止后台成员**（H8）—— 别的团队继续跑。

> 与 PRD 的关系：v2.11 line 38 把"多 Workspace 多活跃团队"列为 v1 非目标，line 505 因此把切换器描述成"主要是状态展示与归档跳转"。但实现侧的存储结构（`state/teams/<teamId>/`）与 `listTeams()`（遍历 `ctx.agents.list()` 收集每个队长会话的 teamId）都已经支持多团队。所以本设计**按能力画、按里程碑收**：切换器的多团队列表与 `overview.html` 的活跃团队卡是同一套组件，M1 只在有多团队数据时显示多行，只有 1 个团队时退化成"当前团队 + 归档入口"，不改变布局。

**维度二：库按作用域分三层。** 同一类东西（角色、预设、技能、知识）都有「内置 / 全局 / 项目」三层，规则统一：

| 层 | 位置（按实现口径） | 权限 | 谁会看到 |
|---|---|---|---|
| 内置 | `plugin/config/roles`、`plugin/config/presets` | 只读，随插件版本分发 | 所有项目同一份 |
| 全局 | `../.dsh/myteam/roles`（`host.ts:269` 的 `globalRolesDir` 默认值，不是字面 `$DSH_HOME`） | 可增删改 | 你的所有项目 |
| 项目 | `.team-workplace/config/roles`、`config/presets`、`config/knowledge` | 可增删改 | 当前项目 |

三条必须画对的规则：

1. **运行时只认项目层**（`role-store.ts:97` 的 `resolveRuntimeRole` 只查 `projectRolesDir`，未命中返回 `undefined`，**绝不静默回退**）。所以角色库里"全局有、项目没有"的角色，卡脚写的是「本项目 0 实例」+「复制进项目」，而不是"已启用"。
2. **三层之间只复制、不同步**（`copyToProject`）。UI 用 `.note.info` 明写「每一跳都是显式复制，绝不自动同步」，复制按钮是主动作，编辑不是。
3. **同名冲突要拒绝而不是覆盖**（`MT_ROLE_EXISTS`，`copy refused (no silent overwrite)`）。所以项目层已有的角色，内置卡上给的是「对比差异」而不是「复制到项目」。

对应组件（都在 `app.css`）：

- `.layers` / `.layer` / `.layer-ico.builtin|global|project` / `.layer-path` / `.layer-n` —— 三层清单。用于 `overview.html`（库的作用域）、`roles.html`（三个来源）、`knowledge.html`（三层记忆）、`settings.html`（配置来源）。
- `.merge-chain` + `b.cur` —— 「插件默认 `<` **项目配置（生效）** `<` 临时参数」的合并链，当前生效层高亮。（注意类名用 `cur` 不用 `win`：`.win` 已被窗口外壳的 grid 容器占用，同名会把整页变成一块浅绿圆角块 —— 踩过一次。）
- `.team-pop`（浮层）/ `.team-pop.inline` + `.poprow` + `.popnote` —— 团队切换器。展开态专屏用 `.inline` 就地展开（否则绝对定位会压住下方 tabbar 与看板列，实测如此）。

## 一、结论先说：面板怎么展示

**一句话**：面板是 `main` 插槽里的一个**完整页面**（不是浮层、不是 iframe），横向三段式 —— 顶部团队信息条、中间五个功能域 tab、底部一条成本栏；看板类视图在中间区再切三视图（看板 / 泳道 / 依赖图），名册收成 76px 头像轨常驻左侧。

这样排的三个理由：

1. **宽屏礼让（H6）**：`main` 是宿主给的最大一块地，占满它才能一次看清 9 个任务 + 5 名成员 + 成本。做成 overlay 会遮住会话，用户改完计划还得关掉才能看队长说了什么。
2. **一屏一焦点**：看板屏只回答"现在到哪一步了、谁在干什么、哪里卡住了"；任务细节一律进独立详情页（`detail.html`），不在看板上开侧抽屉把五列挤成两列。
3. **状态不靠颜色（H4）**：每个状态都是**文字 + 图标 + 形状**三通道同时编码。颜色只是第三顺位提示，色弱/黑白打印也能读。

## 三、信息架构

```
全局页（overview）  ── 库的作用域三层 · 活跃团队卡 ×N · 已归档 run 列表
团队信息条          ── 团队切换 ▾ · 状态 · 目标一句话 · 4/9 已完成 · 2 待裁决 · 1.24M token · 刷新 · ⋯
                     └─ 切换 ▾ 展开：活跃团队 ×N（各带"N 在跑"）+ 归档入口 + 全部团队 / 新团队
                     └─ ⋯ 打开：改名 / 归档 / 解散
暂存横幅            ── draft 态：计划已暂存，等待你裁决；active 态：队长重排了计划，等待你裁决
                     └─ 两种都是 Approve & Run / Revise / Discard，Discard 走两段确认
功能域 tab          ── 看板 11 · 角色 5 · 知识 23 · 审计 · 设置（收件箱已删；角色 tab = 名册，seg 切 角色库/预设/技能；成员=聘任记录，界面只说角色）
内容区
  ├─ 看板域：视图条 [看板|泳道|依赖图] + 搜索 + 筛选 │ 76px 名册轨 │ 五列阶段看板
  ├─ 成员域：成员卡网格（实例名 + 角色标签 / 双状态 / 交付 x/y / token / 上下文 / 管理菜单）——成员即角色实例，tab「成员」与库 seg「在册 5 / 角色库 13 / 预设 4 / 技能 9」同一组互跳
  ├─ 角色域：三层来源分区（项目 / 全局 / 内置）+ 引用计数 + 复制与发布流向
  ├─ 知识域：三层记忆（共识 / 项目共享 / 成员私有）+ 证据数 + 可能过期 + 提案入口
  └─ 设置域：配置来源三层合并链 + 行为配置（含硬上限只读列）+ 状态目录 + 生命周期
成本栏              ── 累计 token · 缓存命中率 · 今日未命中/输出 · 门禁重跑 · 上下文环 · 「归因为估算」
```

**为什么名册不占一列**：需求里名册"常驻左栏、不算第四视图"，但 232px 卡片列表会把五列阶段各挤到 180px 以下、标题全折行（第一版实测如此）。改成头像轨后：头像 + 角色名（同名第二实例跟一个编号）+ 状态点，鼠标悬停出气泡（实例名 / 任务号 / 模型 / token），点开进成员详情。**名册要的是"谁在跑"，不是"每个人的简历"。**

## 五、交互约定

- **三视图同源同抽屉**：看板卡、泳道节点、DAG 节点点开都是**同一个** `detail.html`。不做两套详情。
- **会话页不重复造面板**：`conversation.view` 里的「团队视图」不复制看板，只做一层壳 —— 会话头给「对话 / 团队视图」切换，切过去就是 `board.html` 那套组件换挂载点。工具卡（`tool.call.toolview`）只给**摘要 + 两个出口**（在面板打开 / 看任务详情），不把整个看板塞进对话流。
- **两段确认**：Discard / 解散 / 移除成员 / 团队归档都走「先说影响面 → 再输入或再点一次」。解散要求输入 teamId，因为它是唯一真删数据的动作。
- **排空可见**：归档成员/团队时确认框里给「在跑 x 个、待处理 y 条」，归档后状态显示「排空中 2/3」，不让用户以为卡死。
- **暂存横幅两种语义，同一个组件**：团队还是 draft 时写「计划已暂存，等待你裁决」（FR-1.1）；团队已 active、队长重排了计划时写「队长重排了计划，等待你裁决 · 改动 3 项」，并明确「批准后才生效，当前在跑的任务不受影响」（FR-11.6 运行中变更）。批完即消失；Discard 之后团队回到 draft 但不自动重建计划。
- **成本数字一律带「估算」字样**（FR-8.3）：任务级归因是 best-effort，不能写成精确值。
- **空状态给下一步**：空列写「拖动卡片改阶段，门禁未过会驳回」，不写「暂无数据」。
- **切换不打断**：切团队只换视图，后台成员继续跑（H8）；切换器每行右侧标「N 在跑」，让人不必切过去就知道别的团队还在动。
- **分层只复制**：跨层动作一律是「复制进项目 / 发布到全局」，UI 不给"同步"字样；同名冲突给「对比差异」而不是覆盖。
- **入口不藏**：从卡片就能发起下游动作 —— 角色卡的「用它单干」直接进 `guest.html` 的单角色调用语境，预设卡的「用这个建团队」进 `new-team.html`，库的三层各行右侧「看库」跳到对应的库页。不给"去别的地方找"的空白。

## 八、落地建议（给实现的六个约束）

1. **单一事实源（I2）**：所有数字从 `getBoard` / `getTokens` 派生，UI 不缓存自己的计数（收件箱已从 IA 删除，`getInbox` 不再是 tab 数据源；等人裁决的事就地落在成员卡与门禁列上）。
2. **轮询而非自建订阅**：`DockChip` 20s 轮询 `getBoard` 的做法可以保留；面板打开时降到 5s，`document.hidden` 时停轮询。宿主没有给团队面板的事件流之前，不要自造 WebSocket。
3. **非队长会话降级**：`panel.mjs` 的 `UNAVAILABLE` 分支要落到 UI —— 面板整体换成空状态卡「当前会话不是 team 预设，团队面板不可用」，附「如何用 `/myteam+<roleId>` 单角色调用」的一行说明，而不是白屏或转圈。
4. **别把角色当成员渲染**：`getRoles()` 返回的是角色（配置），`getBoard().roster` 返回的是成员实例。两个列表的 key 不同（`roleId` vs `instanceName`），UI 不要用角色名当成员卡的主键 —— 同名角色有两个实例时会互相覆盖。成员卡永远用 `instanceName`，角色名只作副标签。
5. **多团队要按 teamId 取数，不要只取"当前团队"**：`listTeams()` 只返回 `{ sessionId, teamId }`，够做切换器与全局页的骨架；每个团队的完成度/token 要再按 teamId 各调一次 `getBoard`/`getTokens`。别把第一个团队的数据当全局数字用。跨团队聚合会随团队数线性增长，全局页按需拉取（先骨架后补数），不要一次并发 N 个团队的全量 board。
6. **三层来源别在前端自己算**：`getRoles()` 已经带 `origin: 'builtin'|'global'|'project'`（`role-store.ts:104`），直接按它分区渲染；不要靠路径字符串猜来源，也不要自己合并同名角色 —— 运行时只认项目层（`resolveRuntimeRole` 不回退），前端"帮我合并一下"会造出第二事实源。

## 十三、依赖图补连线与双布局（2026-11-01，CHG-68）

用户指出依赖图没有箭头看不懂。重做为真实连线的图：

- **数据驱动渲染**：`dag.js` 从节点/边清单（11 节点 · 13 条边）排版，节点用真实 DOM 测量矩形，SVG 贝塞尔连线 + `marker` 箭头，箭头永远指向下游（上游完成即解锁下游）。
- **两种布局**：`dag.html` 横向（左→右，按依赖层级分列）、`dag-vertical.html` 竖向（上→下，按层级分行），视图条右上「方向」seg 互链。
